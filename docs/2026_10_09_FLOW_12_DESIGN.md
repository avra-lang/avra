# FLOW 12 — `t.await catch`, `Cancelled`, `t.await?`: design and the blocker (v1)

Ladder 12 of `docs/2026_10_06_FLOW_03_DESIGN.md` §2 D2 option C. Base `origin/main` (`3a562c5`).
Every claim carries `file:line`; every number is READ unless marked. Nothing here is built
except `t.cancel()` (the verb, its row, its IR).

## The one hard predecessor: ladder 9 is not landed
A cancel cuts a wait only where the EMITTED test after the call reads the unwind bit
(`compiler/backend/interp.av:1003` `RtFlag.Unwinding` -> `avra_vtask_unwinding`). Ladder 9
(`#499`, `compiler: the test after a call that may reach`) emits that test; it is BLOCKED, not
merged. Without it:
- native, `avra_fiber.c:2013` `fiber_cancelled` claims a parked FIBER under a cancel, the park
  returns, the body runs on to its natural end and ends cancelled — a `t.cancel()` task's
  `defer` runs and `t.done` is true (MEASURED: `AVRA_FLOW_TRACE=1`, output `1 1 1 true`);
- evaluated, `fiber_cancelled` skips a `legacy && virtual` park (same line), and nothing in
  `interp_tasks.av` reads `avra_vtask_unwinding` when the task resumes, so the task stays
  parked (MEASURED: `avra run` of the same program prints `1 0 0 false`).
So a program test for `t.cancel()` is `eval != native` until #499 lands. This slice lands the
VERB (a `Task` method over the armed `avra_task_cancel` row, `features/rt.av:629`) and its IR
spec, not the runtime semantics.

## The join must stop trapping
`avra_task_join` traps on a cancelled task (`runtime/avra_fiber.c:1880` `join_refused`,
called `:1891`), and so does the evaluator (`backend/interp_tasks.av:212`). D2 needs two
outcomes from one join:
- a BARE `.await` PASSES the cancel through: the awaiter is cancelled by the same asker (the
  join sets `avra_unwinding` and the after-call test — #499 — unwinds it). No trap.
- `t.await catch c -> …` joins WITHOUT passing it and reads how the task ended, then runs the
  arm only for `.Cancelled`. That is a second row (`avra_task_join_caught`) and a reader
  (`avra_task_ended`, `avra_fiber.c:1942`), because `avra_task_join`'s one answer cannot be
  both a trap-free pass-through and the caught value.

Both rows are new runtime symbols: the THREE-RUNG ladder (row, evaluator arm, declaration)
in `core/runtime_api.av`, and a `[C]` adversarial round per the design's ladder note.

## The typing side
`catch` reads its subject's sides from its TYPE alone (`features/results/check.av:29`
`res_parts`). `t.await` is typed as `T` (`features/tasks/check.av:23` `check_await`), so a
`catch` over it sees no sides. D2 adds a FAILURE VIEW to `PropertyRow`
(`features/mod.av:135`), and ONE verb `cx.failure_view(e)`:
- a `Result`'s `res_parts`, or
- the row the subject's own `.Prop` selected (`features/checks.av:536` `property_row`),
  whose view for `await` is `{ ok: T, err: Cancelled }`.

The pair is NEVER interned as a `Res` — a task answering nothing needs no `Result<void, …>`.
`Cancelled` is a record (`{ by: int, at: int }`, spec §5.4) declared where `Frame` is
(`@std/errors/src/errors.av:14`); the view resolves its `TypeId` from the declaration table
the way `declared_type` does, at the await's declaration, never mid-flight
(`CLAUDE.md`'s named-type law).
- the results feature still matches no tasks node: the view and its caught lowering are
  COLUMNS of the row (`features/results/lower.av:18` `catched_reg` asks `cx.failure_view` and
  calls the row's `caught` lowering when the subject is not a `Res`).
- `t.await?` refuses by NAME (`features/nullable/check.av:149` `propagate_type`): the subject
  carries a failure view whose channel already passes through, so `?` cannot promise it —
  "catch it, or drop the `?`". A `let v = t.await` then `v catch` stays refused.
- `match t.await { … }` is the `T` (unchanged); only `catch` sees the cancel.
- `main`'s cancelled end is one stderr line and exit 1 (spec §3.6): the runtime's
  `avra_task_ended` names the asker, `compiler/build.av`'s entry prints it.

## Tests (§5, each failing first, eval == native)
- a cancelled task's `defer` runs, nothing after its cancel point does — BLOCKED on #499.
- `t.await catch c -> { … }` runs with `c.by`/`c.at`; a bare `.await` cancels the awaiter,
  whose own watcher catches it; a task answering nothing caught as a statement.
- `t.await?` and `v catch` refused, each by its voice.
- `within ms(10) { t.await catch … }` over a slow `t` never runs the arm (the awaiter's own
  cancel claims the join).
