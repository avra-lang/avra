# CONFIG — `@std/config`: typed config, secrets, flags, one source

**Status:** DECIDED WITH OWNER 2026-11-24 (§14). C1 is built (§8.4), C2 (§8.5), C3 (§8.6), C4 (§8.7).
**Epic:** `avra-8sb5.64.7` (PLATFORM_MAP: "Config, secrets, feature flags, i18n | gap").
**Base read:** `program` at `d423b79`. Probes in §13 name the compiler that answered them.
**Scope:** config, secrets, feature flags. i18n shares the epic and is not designed here.

---

## 0. The model in one table

> **Config is a typed record, filled from a list of sources, read as a
> snapshot.** It adds no new kind of thing to the language.

| Piece | What it is | Already exists as |
|---|---|---|
| The schema | a plain `type` record with defaults and rules | records, field defaults, `@std/validate` rules |
| The spelling | a component declaration: its fields the schema, its body the sources (§2.0) | component declarations, `@derive(Decode)`, the body law's `@composes` |
| The sources | a list of `dyn Source` values: defaults, files, env, flags, providers | `@std/validate`'s neutral `Value` tree |
| Provenance | every leaf carries an `Origin` (source, locator, version) | issues already carry a path and a received value |
| A secret | `Secret<T>`: a **handle** into the process's secret store, never the bytes | `@secret`'s redaction, which today covers issues only |
| Live config | `state app: Live<App>`, a place whose writer is the source list | `state` places (SHARING_MODEL §4.5 wrappers) |
| A feature flag | a config field of type `Flag<T, Cx>`, evaluated locally | a record field |
| An environment | one input (`stage`) that picks overlays. It is data, never a code branch | `deploy staging from production` (TOUR §11) |
| Composition | a dependency's config is a **field** of the app's config record | records nest |

This is P6 at work: "config system vs. language" is a false choice. The
language already has places, records, rules and derives, so the library
only names how they fit together.

## 2. Declaring and loading

### 2.0 The face: a component declaration (decided; it exists today)

The schema IS a component declaration, and its body holds the sources.
Nothing new in the language: every line below type-checks and runs on
the gate's compiler (probes D1–D6, §13).

```avra
use @std.meta.{derive}
use @std.validate.{Decode, range}
use @std.config.{Configured, file, env, flags, stage, vault, Secret}

/// The shop's settings.
@derive(Decode)
component App {
    @range(1, 65535) port: int = 8080
    db: Db = Db {}                           // a dependency's config: a field
    api_key: Secret<string>                  // no default: required
    password: Secret<string>

    file "app.toml"                          // the sources, in precedence order
    env "SHOP"
    flags argv()
    stage prod {
        file "app.prod.toml"
        vault "kv/shop/prod"
    }
}

let app = App.load()?
```

| Part | Mechanism, as built |
|---|---|
| `component App { … }` is a type: `fn start(s: App)`, `App {}` | a component declaration is a record (D1, D4) |
| `name: Type = default`, required when no default | the declaration's field lines (D2, D4) |
| `@range` on a field; a secret as `Secret<T>` | marks on declared fields; `@derive(Decode)` reads them (D2). A `@secret` field holding text is refused (`config_secret_text`): its text rides every copy and `value()` |
| `App.decode(v)`, `App.fields()`, strict unknown keys | `@derive(Decode)` on a component declaration (D1: `prot is not a field here`) |
| the body: `file "…"`, `env "…"`, `stage prod { … }` | THE BODY LAW: `@std/config`'s `Configured` trait wears `@composes`, so its `derive` takes the body and wraps it in a library component holding `sources: List<dyn Source>` and `stages: List<stage>` (D6: `1 app.toml prod 2`) |

`avra expand` shows the lowering: the record, the `Decode` impl, and the
`impl Configured` that makes the source list (P7). A dependency may
still export a plain `@derive(Decode)` record with no body: it is a field,
and has no sources of its own.

**What is truly missing** (the ROADMAP's asks, renumbered):

| Ask | Today | Cost of living without it |
|---|---|---|
| **A1** — two bounds on one type parameter (`fn load<T: Decode + Configured>()`) | `parse.expected: expected (` at the `+` | the derive emits `static fn load()` per type, calling a `T: Decode` helper with the sources handed in |
| **A2** — two `@composes` traits in one file: the body is composed by NEITHER, and no refusal speaks | D6b: only `type.method: App has no method sourced`; the two-composers voice never fires | a config component lives in a file that imports no other composer (`@std/ui`'s `View`) |
| **A3** — the composer also derives `Decode`, so `@derive(Decode)` is not written beside it | the user writes `@derive(Decode)` | one annotation of ceremony |
| **A4** — `@std/io` `env_names()` (filed, parked) | no verb lists the environment | the env source reads the names the fields derive; a stray `SHOP__*` variable is not refused yet |
| **A5** — an upper-case text verb in `@std/text` | none | `@std/config` keeps a private ASCII one |

A `config` block word in place of `component` was the first ask. It is
dropped: `component` already reads as "declares a shape", and a second
word for the same declaration would be two spellings of one thing.

### 2.0a The rules

A dependency's config is a plain decoded record with no body; the app's
component names it as a field:

```avra
@derive(Decode)
export type Db = { url: string = "sqlite://app.db", @range(1, 512) pool: int = 10, password: Secret<string> }
```

| Rule | Decision |
|---|---|
| Schema | a component declaration (or, for a dependency, a record) wearing `@derive(Decode)`: a field's type is a scalar, a decoded record, a list of those, `Secret<T>`, or a type with its own `decoded` |
| Required | a field with no default. Missing means an issue, and **every** issue is reported before start (VALIDATE §10) |
| Rules | `@std/validate` annotations, unchanged. A literal default is checked at compile time |
| Unknown key | a file key or `PREFIX__*` env name that no field names is an **issue**, not a silent ignore. Typos are the #1 config bug |
| Answer | `T.load()` answers `T`, a plain value: a field read is a load, with no lookup. `T.loaded()` answers `Loaded<T> = { value: T, origins: Origins, generation: int }` |
| Library side | a library takes its config **as a parameter** (`connect(cfg: Db)`) or an `ambient` seat once that mark lands (SHARING_MODEL §3). **No global key lookup**: SHARING_MODEL §1.5 deleted type-keyed `provide`/`env`, and config does not bring it back |

### 2.1 Sources and precedence

```avra
let app = App.load(from: [
    defaults(),                    // the type's own defaults
    file("app.toml"),              // TOML or JSON by extension; a missing file is fine unless `required: true`
    stage_file("app.{stage}.toml"),// the stage overlay (§6)
    env(prefix: "SHOP"),           // SHOP__DB__POOL=20
    flags(args),                   // --db.pool=20
    vault("kv/shop"),              // a provider (§3.3)
])?
```

| Decision | Why |
|---|---|
| **Precedence is the list, read left to right, last wins.** `App.load()` with no list uses `[defaults, file("<pkg>.toml"), stage overlay, env, flags]` | the order is data you can see (P7), not a framework rule you have to remember (Spring has 17 levels) |
| Every source is a `dyn Source`, and the built-in ones too | one trait (P17), so a provider is not a special case |
| Merge is per **leaf**, deep: a lower layer's `db.url` survives a higher layer setting `db.pool` | whole-subtree replacement is a classic footgun (Helm values) |
| Lists replace and never append | appending makes order depend on layer count and cannot be explained |

### 2.2 Names: one derivation, collision-proof

| Source | Spelling of `db.pool` | Override |
|---|---|---|
| file | `[db] pool = 20` | — |
| env | `SHOP__DB__POOL` (`__` between path segments, `_` inside a name) | `@variable("DATABASE_URL") url: string` |
| flag | `--db.pool=20` | `@flag("pool", short: "p")` |
| provider | `<root>/db/pool` | `@key("…")` |

- `__` is the separator because of CLAUDE.md's law **"a flat
  concatenation of two sequences has a boundary that moves"**: under `_`,
  `db_host` and `db.host` are one name. The derive also refuses any two
  paths, overrides included, that derive one name (`config.name_clash`) at
  compile time.
- The prefix defaults to the root package's name. A dependency's fields
  sit under its field name, so two packages can never clash: the path is
  the namespace.

### 2.3 Provenance (P7: "where did this value come from")

```
$ avra config explain --stage prod
db.url       postgres://db.internal/shop   env      SHOP__DB__URL
db.pool      20                            file     deploy/app.prod.toml:4   (shadows app.toml:7 = 10)
db.password  <secret db.password v7>       vault    kv/shop/db#password v7, rotated 2026-11-20
port         8080                          default  src/app.av:3
```

- Each leaf has an `Origin { source, locator, version? }`. The locator is
  a file:line, an env name, a flag, or a provider path@version.
- **Shadowed** values are listed too, so you can see which layer lost.
- Issues carry the origin: `db.pool: 900 is out of range 1..512 — from
  SHOP__DB__POOL`.
- `explain` runs the same `T.loaded()` the program runs (one
  definition), with secret values never fetched, only their versions.

## 3. Secrets

### 3.1 `Secret<T>` is a handle, not a wrapper

```avra
type Secret<T> = { key: SecretKey, generation: int }   // @sealed; no bytes inside
```

| Property | How it holds |
|---|---|
| Never printable | the value holds no bytes, so printing a handle prints `<secret db.password v7>`. There is nothing to leak, whether the leak is a missed redaction, a debug dump, a crash report or a serialized struct |
| Never in text | interpolating a `Secret` is refused (`config.secret_text`: "a secret never becomes text; pass it to a seat that takes `Secret`"). §13 probe P1 shows why a plain record is not enough |
| Never logged | logs, issues, OTel attributes and `cmd"…"` projections render the handle (PROCESS research §6.3) |
| Use | **sinks take `Secret` directly**: `bearer(s)`, `Db.connect(password: s)`, `cmd"… ${s}"` (reaches the child, redacted in every projection). The sink reveals at the C boundary, inside the library |
| Escape hatch (P8) | `s.reveal { v -> … }`: block-scoped and greppable. `avra explain secrets` lists every reveal site (P7) |
| Compare | `s.matches(candidate)`: constant time |
| Memory | the runtime store keeps bytes in `mlock`ed, `MADV_DONTDUMP` pages, zeroed on replace and on exit |

**Why a handle (P6):** non-printability and rotation-without-restart look
like two features, but both follow from one choice. A handle has no bytes
to leak, and its `key` resolves to the **current** version at reveal
time, so rotation needs no code at the reader.

### 3.2 Rotation and versions

| Need | Design |
|---|---|
| Rotate without restart | the provider reports v8 → the store swaps the bytes → the next reveal sees v8. The old bytes are zeroed after the overlap window |
| Overlap (verify-side keys: JWT, webhooks) | `s.accepts(v)` checks the current and the previous version within `overlap:` (default 0) |
| Rebuild on rotate (pools, TLS contexts) | a typed `on rotated(s)` event (§5.2) |
| Pin / roll back | `@pin("v6")` in a stage file. `explain` shows the pin |
| Versioning | every provider value carries its version in `Origin`. A rollout (§5.3) records the versions it shipped |

### 3.3 Providers: one trait

```avra
export trait Source {
    fn read(want: List<Key>) -> Result<List<Entry>, SourceIssue>   // Entry = { key, value: Value, version: string? }
    fn watch(want: List<Key>, since: string?) -> Changes?          // null: this source never changes
    fn describe() -> SourceInfo                                    // for `explain` and least privilege
}
```

| Backend | Ships | Notes |
|---|---|---|
| defaults, TOML/JSON file, env, flags | **v1** | `watch` on files is v2 |
| `*_FILE` env convention, mounted dirs (k8s Secrets, Docker secrets) | **v1** | the zero-dependency path to real secrets |
| Vault / OpenBao | later | KV v2 versions map onto `version` |
| AWS Parameter Store, Secrets Manager, AppConfig | later | |
| GCP Secret Manager, Azure Key Vault | later | |
| 1Password, SOPS-in-repo | later | SOPS gives secrets in git, encrypted |

A provider is an ordinary package implementing `Source`. The core knows
none of them, so there is no framework (P14).

### 3.4 Least privilege, derived

- The compiler knows every `Secret` field reachable from the root type
  (P10). `avra build --manifest` emits **the binary's exact secret list**,
  and a provider package projects it to a Vault policy or an IAM policy
  (P12: one source, many projections).
- At run time the store refuses a key outside that list, so a binary
  cannot fetch what its types do not name.
- `config.secret_argv`: a `Secret` field is not settable from `flags`,
  because argv is world-readable in `ps`. In a non-dev stage, plain `env`
  is refused too unless the field allows it (`@from(env)`).

## 4. Composability

| Case | Answer |
|---|---|
| A package declares its config | it exports a `@derive(Decode)` record (`@std/db`'s `Db`) |
| The app composes dependencies | a field per dependency: `db: Db`. The path is the namespace, so a clash is impossible by construction |
| Explicit override | the parent field's default (`search: Search = Search { shards: 4 }`), or any layer at `search.shards` |
| Two packages want one value (region) | the parent passes it explicitly: `Db { region: app.region }` in code, or the same key in a file. **There is no implicit shared key** |
| A library is used twice (two databases) | two fields: `primary: Db`, `replica: Db` |
| Reusing a group of fields | field spread `..Common` (UI C1, landed) |
| Library defaults change on upgrade | `avra config explain --diff <old-lock>` shows each default that moved |

**Refused:** a global property bag (Spring's `Environment`) and
type-keyed lookup (`get<Db>()`). Each is an invisible dependency, the same
reason SHARING_MODEL §1.5 deleted `provide`/`env`.

## 5. Live config and distribution

### 5.1 Snapshots, never torn reads

```avra
state app: Live<App> = App.watch()?    // rides the place-wrapper ask (SHARING_MODEL §4.5)

fn handle(req: Request) -> Response {
    let c = app.now()                  // one generation for this whole request
    …
}
```

| Law | Meaning |
|---|---|
| **Whole-tree atomic swap** | a process sees generation N or N+1, never a mix of keys from both |
| **Validate, then swap** | a new generation decodes in full first. If it has issues, the old one stays, the issues are reported and the push is refused. A bad push never half-applies |
| **A turn pins a generation** | `app.now()` answers one immutable `App`. A request, a job or a loop turn reads it once |
| **Some fields need a restart** | a field marked `@restart` (a listen port, a pool size) changes status to "restart needed" instead of applying |
| Cost | a `now()` is one atomic pointer load. After that, every read is a field load |

### 5.2 Typed change events

```avra
on app.changed { c: Change<App> -> log("config ${c.from} -> ${c.to}: ${c.paths}") }
on app.db.pool.changed { n -> pool.resize(n) }
on rotated(app.now().db.password) { pool.reconnect() }
```

`Change<T> = { from: int, to: int, paths: List<Path>, origins: Origins }`.
A secret's change carries versions and never values.

### 5.3 Many processes and nodes

| Concern | Design |
|---|---|
| Identity | each root config has a **generation** (a counter plus a content hash) |
| Visibility | every process reports its generation and secret versions on its health endpoint. `avra config status` shows the fleet |
| Rollout | a config change is a deploy: canary → percent → all, gated on health, with automatic rollback (AWS AppConfig's model) |
| Mixed generations | requests between services carry `config-generation`, so a trace shows when one request crossed two generations |
| Barrier flags | `@barrier`: a flag flips only once every node reports a generation at least N (a schema migration's read path, for example) |
| Partition / provider down | keep the last good generation and report it as stale. **Never fall back to defaults** |

### 5.4 Feature flags are config

```avra
type Shopper = { id: string, country: string, plan: Plan }

@derive(Decode)
type App = { …, new_checkout: Flag<bool, Shopper> = off() }

if app.now().new_checkout.for(shopper) { … }
```

```toml
[new_checkout]
default = false
rules = [
  { when = { country = "NZ" }, then = true },
  { percent = 10, by = "id", then = true },
]
```

| Decision | Why |
|---|---|
| Rules are **data, decoded against `Cx`'s shape**: naming an attribute `Shopper` lacks is a load issue | typed targeting. LaunchDarkly's string attributes fail silently |
| Evaluated **locally**, with no network on the hot path | P4. Rules arrive like any live config |
| Percentages use a stable hash of (flag path, `by` value) | the same user always gets the same answer across nodes and restarts |
| Exposures (who saw what) are optional events | experiments are later |
| **A flag constant in a target folds** (§7), and its dead branch is removed | zero cost for shipped flags |
| `avra config stale` lists flags that have been constant everywhere for N days | flag debt is visible |

## 6. Environments, teams, agents

### 6.1 Stages are data

- `stage` is **one input**: `--stage`, `<PREFIX>_STAGE`, or the deploy that
  launched the process. It selects overlay files (`app.{stage}.toml`) and
  provider namespaces, and nothing else.
- The stages are the `deploy` declarations (TOUR §11: `deploy staging from
  production`), so the stage list is P13's one source.
- **Code never branches on the stage name.** `if stage == .Prod` is
  refused (`config.stage_branch`). What differs is a **field**, such as
  `emails: Mailer = .Log` in dev and `.Smtp` in prod. A licensed site
  (`// LICENSED I<n>`) is the escape hatch.

### 6.1a Real code does not need a stage branch

The owner asked whether it does. Each common case, as a VALUE that varies
per stage:

| Want | The branch people write | The value instead |
|---|---|---|
| emails only in prod | `if stage == .Prod { smtp.send(m) }` | `mailer: Mailer = .Log`; prod sets `.Smtp(host, user, password)` |
| debug endpoints | `if stage != .Prod { mount(debug) }` | `debug_routes: bool = false`; dev sets `true`. Fixed per target, so the prod binary carries no debug code (§7) |
| TLS | `if stage == .Prod { tls(cert) }` | `tls: Tls = .Off`; prod `.Files(cert, key)` or `.Acme(domain)` |
| trace sampling | `rate = stage == .Prod ? 0.01 : 1.0` | `trace_sample: float = 1.0`; prod `0.01` |
| log level | `if stage == .Dev { .Debug }` | `log: Level = .Info`; dev `.Debug` |
| payments sandbox | `if stage != .Prod { test_key }` | `stripe: Stripe` with its mode and `Secret` per stage |
| demo data | `if stage == .Dev { seed() }` | `seed_demo: bool = false` |

Why the value wins: a test sets the field and needs no fake stage; a new
stage (`preview`) needs no code edit; `explain` shows why; the compiler
folds it. READING the stage is allowed (a metric label, Sentry's
`environment`); only BRANCHING on it is refused.

**The true exception (P8):** `// LICENSED I<n>: <reason>` at the site, read
by `make idioms`, so every exception is listed and reviewed. None of the
cases above needs one.

### 6.2 Changes are receipts

| Need | Design |
|---|---|
| Who changed what | `avra config set db.pool 20 --stage prod --why "…"` writes through the provider and records a **receipt** (AUTHORITY_AND_RECEIPTS §6): actor (person or agent mandate), the diff (secrets as versions), generation, reason |
| Audit trail | an append-only change log. It lives in the provider's own history where it has one, else a `@std/db` relation |
| Review | a change to a `@guarded` path (prod secrets, barrier flags) needs a second approver, using the same safeguard model as `.destructive` actions |
| Drift | `avra config diff --stage staging prod` compares by path |

### 6.3 Per-agent scopes

- An agent's **mandate** lists path patterns it may read and write
  (`db.pool: write`, `flags.*: write`, `db.password: pass`).
- **`pass` versus `reveal`:** an agent can be given a `Secret` handle to
  hand to a sink (wire the API key into the HTTP client) **without ever
  being able to reveal it**. That is capability passing, and it falls out
  of §3.1: the handle has no bytes.
- An agent's writes are receipts like anyone's, so its config history is
  auditable.

## 7. Compile time versus run time

| The compiler checks | When |
|---|---|
| Field types, rules, literal defaults | always (existing `@std/validate` laws) |
| Env/flag/key name collisions (`config.name_clash`) | always |
| A secret reaching text or argv (`config.secret_text`, `config.secret_argv`) | always |
| A config field type with no `Config` (`config.not_config`) | always |
| **A missing required key** (`config.required_missing`) | when the deploy target is known: `avra build --target production` reads that deploy's sources. Files in the repo are read directly. Providers are asked for **key existence and version only** (`--offline` skips them and says so) |
| A file key no field names | at build for repo files, at load for the rest |
| Stage branching (`config.stage_branch`) | always |

| Zero cost | How |
|---|---|
| A field **fixed** for a target (the deploy pins it and no live source covers the path), or marked `@fixed` | settled as a `const`, laid out as static data (CLAUDE.md "a settled aggregate is static data") |
| A flag constant for a target | folded, and the dead branch removed |
| A loaded snapshot | a flat record: a read is a field load, never a map probe |
| A live read | one atomic load per `now()` |
| ZERO_COST row | **new row**: "config fold". Its detector is a `Config` field read whose path is fixed by every deploy |

## 8. What ships first, and what stays open

### 8.1 v1: four slices

| Slice | Contents | Depends on |
|---|---|---|
| **C1** | the `Configured` composer over a component declaration (§2.0, works today); `Source` trait; defaults, TOML/JSON, env, flags sources; all issues at once; unknown-key issues; `Origins`; `avra config explain` | a typed TOML decode (VALIDATE §11 basics) |
| **C2** | `Secret<T>` handle + the process secret store; redaction in print, issues, logs and `cmd`; `config.secret_text`, `config.secret_argv`; `*_FILE` and mounted-dir sources | C1 |
| **C3** | stages: `--stage` and overlay files; `config.stage_branch` | C1 |
| **C4** | the compiler adopts it (§9); `@std/cli` options read from config by path | C1 |

### 8.2 Doors v1 keeps open (shapes present on day one)

| Later feature | What v1 already carries so it never breaks |
|---|---|
| Rotation | `Secret` is a handle with a `generation` from day one, so readers never hold bytes |
| Remote providers | `Source.read` answers versioned `Entry`s. Env and files answer `version: null` |
| Live updates | `Source.watch` exists (built-ins answer `null`). `T.loaded()` answers a `generation` |
| Fleet consistency | the generation is a counter plus a content hash from day one |
| Audit | `Origin` carries actor and version fields (null in v1) |
| Flags | `Flag<T, Cx>` is a reserved name in `@std/config`. v1 refuses it with "flags arrive in L4" so nobody builds a lookalike |

### 8.3 Later

| # | Feature | Gate |
|---|---|---|
| L1 | `Live<T>` + change events — **OPEN ITEM O1, decided to wait** | TRIGGER: place-wrapper transparency lands (`state x: W<T>` reads as `T`, SHARING_MODEL §4.5, ask `avra-2y5c.20`). Until then v1 answers snapshots only, and no library `watch()` API is shipped to be replaced |
| L2 | Vault, AWS, GCP providers | `@std/https` client (built) |
| L3 | Rotation + `on rotated` | L1, L2 |

### 8.7 C4 as built: the compiler's settings, one declaration and its projections

The compiler does not import `@std/config`: doing so costs every check of the cli +1.1% of its asks (a fixed pull of `@std/validate` and `@std/config`, measured on a draft record of 16 switches). So the ONE declaration lives in the tree's instruments, and the compiler reads what it projects.

## 10. Against the prior decision

The legacy spec chose **(b): a first-class `secret("key")` literal with
pluggable provider backends** (`Secret<T>` not Display, `from_vault`,
`from_gcp_secret`, rotation, versioning). *(The legacy tree is not in
this container. This summary quotes the brief and the tree's citations,
PROCESS research §6.3 and the TOUR's `secret push_key`.)*

| (b) said | Here | Why |
|---|---|---|
| `Secret<T>`, not Display | **kept**, and made stronger: a handle with no bytes | redaction you have to remember fails open; a handle has nothing to leak |
| Pluggable providers | **kept** as one `Source` trait shared with every other layer | P17: a provider is not a special kind of thing |
| Rotation, versioning | **kept**, and they fall out of the handle | §3.2 |
| `secret("key")` **literal** anywhere in code | **dropped as the main spelling**: a secret is a typed field and its key is its path | a literal is a read from a global namespace at any call site: an invisible dependency, a stringly key spelled twice (P12), and no composition. The field form gives the binary's secret list from the types |
| `from_vault(…)` at the use site | **moved** to the source list, which is data and chosen per stage | the use site should not know which stage it runs in (P13) |
| `secret push_key` in a `deploy` block | **kept as a projection**: the deploy's secret lines are *derived* from the types, and a hand-written line that no field reads is a warning | P12 |

## 11. Prior art: what to take, what to refuse

| System | Take | Refuse |
|---|---|---|
| 12-factor | config lives outside the build; env works everywhere | env as the *only* store; flat untyped strings; secrets in env by default |
| Spring Boot | relaxed binding to typed `@ConfigurationProperties`; `/actuator/configprops` provenance | 17 precedence levels; the global `Environment` bag; profile `@Conditional` code branches |
| K8s ConfigMap/Secret | mounted files with atomic symlink swap (our `watch` on a dir); `*_FILE` | base64 called "secret"; env-injected secrets that never update |
| Vault | leases, versions, dynamic credentials, policies | the app knowing Vault paths at use sites |
| AWS AppConfig / Param Store | validated deploys, canary, auto-rollback | an untyped JSON blob |
| LaunchDarkly | local evaluation, stable bucketing, targeting rules | string-keyed flags and attributes that fail silently |
| CUE | types and values are one lattice; unification instead of override | a second language beside Avra |
| Dhall | typed and total; imports as values | a second language; no provenance |
| Nix | the whole system's config as one value; reproducibility | lazy, untyped attrsets |
| Pkl | schema, defaults and validation in one file; code generation into host types | a second language. Here the host language **is** the schema |

The pattern: CUE, Dhall, Nix and Pkl exist because host languages could
not express typed config. Avra can, so the schema is Avra and data files
stay dumb (TOML/JSON).
