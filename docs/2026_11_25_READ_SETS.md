# Read sets: the cells a fn reads, as a query — proposal

**Status:** a proposal for the UI lead's ruling (ticket avra-8sb5.109.16). Nothing here is built. The
probes ran on program d7cd84d9.

**The ask:** "the cells a fn reads, itself or through what it calls, as a lazy program-layer query", the
twin of `ctx_reads`. It is a static over-estimate. A `dyn` call reads what any impl reads. It is saved by
the fn's content, so a deep edit that does not change a read set reaches no caller. Its first use is a
component's `describe`: a paint hands back an instance's last nodes when its key, its props and the cells
it reads are unchanged (docs: the kept-row proposal, 2026-11-25). The same fact lets a pure fn that reads
state be cached, with no `derived` keyword.

**Short answer:** the query exists already, but it is too wide to help a real `describe`, and in two
shapes it is too narrow to be sound.

- `fn_reads` and `fn_reaches` (`compiler/item_places.av`) are lazy program-layer queries, keyed by fn.
  The rules they share live in `features/read_set.av`. Over the board's own fns they answer what the page
  wants: `admits` reads `filter`, `theme_label` reads `dark`, and the style fns read nothing.
- **Too wide.** Every method call answers `?` (assume any), and that includes the language's own verbs:
  `xs.map(…)`, `s.trim()`, `R.zero()`, `fetch.value()`. Almost every `describe` calls one, so today's
  answer for a real row is `?`.
- **Too narrow.** A cell reached through a parameter is not counted. A `state` seat (P8) and a record's
  `state` field read through a prop (P13) both answer `[]`. For a kept row that is unsound: `row.done` can
  be written without `row`'s box changing.
- **What it costs.** It is generalised by four changes, each small: a key for methods, method calls
  resolved where the receiver's type is known, cells reached through parameters marked, and `dyn` read as
  the union over impls. The cost is measured below. It is in the noise of a check.

## 1. Where reads are recorded today

**For a text, in the compiler.** An instance's `Sighted.reads` (`std-ui/tree/sites.av`) is a field of
the `Cells` role. The compiler fills it where an instance leaves it unset (`core/field_default.av`,
`field_left` → `placed_cells`).

- `placed_cells` (`core/frame_reads.av`) takes the closure the builder minted to say the text again, and
  asks `states_read` of its body.
- `states_read` (`compiler/item_places.av`) walks the body under `features/read_set.av`'s rules. It asks
  `fn_reaches` of every declared fn the body calls.
- A frame's *structural* cells (a cell whose write changes the tree's shape) come the same way, through
  `structural_cells`, with `structural: true`.

**At run time.** The web's exact path (`std-ui/realize/dom/exact.av`) observes each reading's cells with
`avra_box_observe`.

- An observed box is held, and flagged in its header.
- A write tests one byte (`avra_box_touch`, `runtime/avra_box.h`). The first write of a turn to an
  observed box stamps it and logs its address (`avra_box_changed`).
- The turn takes the log, and recomputes only the readings filed under the logged cells. A logged
  structural cell paints the frame whole.
- An unobserved box costs that one byte compare per write, and nothing more.

**The query itself.** `fn_reads(file, name, structural)` is a fn's own places plus the fns it calls.
`fn_reaches` is the union through every callee and any cycle (`reached_union`). Both are `@query`, in the
laws pass, keyed by the fn's file and name, and read off its elaborated body.

**Today they run rarely.** A build asks them only for the fns a text calls. Building the terminal board
(`tools/ui-board/term`) asks neither: none of its texts calls a state-reading fn.

## 3. The over-estimate's rules, as proposed

Each rule answers a set of places. `?` means "assume any": an instance whose set holds it is never kept.

1. **A module `state`** is its key: what today's query already says (P2, P3, P4, P14, P17).
2. **A fn's own `state` statement** is the fn's. It is a cell no caller names, so it is `?` to a caller
   (P9), as today.
3. **A call of a declared fn** folds in the callee's set, through any cycle. Recursion settles by
   `reached_union` asking until no fn reads more (P4), as today.
4. **A method call** where typing knows the receiver's type and the method is the type's own (an
   inherent `impl`, or a static fn by type) folds in that method's set. *New.* Today it is `?` (P6, P19).
   This needs a key for a method (type, name) beside the fn key: `describe` and a composition's body are
   methods.
5. **A language verb** (`map`, `filter`, `trim`, `length`, a `Cell`'s `get`, …) reads nothing of its
   own. It reads the cells of what it is handed, and the cells a lambda handed to it reads when it is
   applied. *New.* Today it is `?` (P15, P16, P20).
6. **A lambda** made in the body and applied there (handed to a verb, or called) is walked, its body as
   the fn's own. *New.* Today a closure is a leaf, which yields only its captures, and a module `state`
   is no capture (P12). A lambda the fn returns or stores, unapplied, reads nothing at the call (P12
   stands). Its reads belong to whoever applies it, and an applied fn value is rule 7.
7. **A fn value applied** that the fn did not make (a parameter, a field) is `?` (P5), as today. A
   handler is a fn value, but `describe` never applies one, so this rarely touches a view.
8. **A `dyn` call** reads the union of what each impl of that method in the program reads. *New.*
   Today it is `?` (P7). This is `ctx_reads`'s rule, narrowed there to the types the program boxes at
   that place. The union over the program's impls is the cheaper over-estimate: one read of the trait's
   impls, which `impls_with` already answers. A view's children are the exception (section 4).
9. **A cell reached through a parameter or the receiver** (a `state` seat P8, a record's `state` field
   P13, a `Cell` inside a param P11) is marked by the parameter it comes through (`param:row`). The
   identity of the parameter's box does not cover it. *New.* Today it is `[]` or `?`, and `[]` is the
   unsound one. Section 5 says what a caller does with the mark.
10. **An extern row, a host fn, a `Fetch` and an observation** read what they read at run time. They
    are `?`, unless the std-ui type declares the cell it reads. `Fetch<T>` keeps its answer in a cell
    (`tasks_ask: Fetch<…>` is a module `state`), so `fetch.value()` reads that cell and only that cell.
    The proposal: a std-meta mark on a method, saying it reads only its receiver's own cells.
    `Fetch.value`, `Fetch.loading` and their kin wear it, and rule 4 then answers `[tasks_ask]` for the
    board's `tasks` (P20's `c.get()` likewise answers `[c]`). Without the mark, rule 10 is `?`.

## 4. The first use: a component's `describe`

A composition's `describe` (derived in `std-ui/tree/view.av`) calls the component's body method
(`composed`). It then hands what that makes to `made_of`, which describes each child through `dyn View`.
Unchecked, rule 8 would make every view read what every view reads.

The rule for a view is the kept-row page's: **an instance's set is its body's set, and stops at its
children.** A child is an instance of its own, kept or described by its own set. So the set asked for an
instance is `reaches(T.composed)`, under rules 1–10, with calls of a `View`'s `describe` left out. A
primitive's is its props and its `Sighted.reads`.

## 5. "Does this fn read anything outside its params and its receiver's own state?"

One query, answered off `fn_reaches` by the same keys:

    reads_beyond(fn) -> Beyond
    enum Beyond { Nothing, Cells(List<Place>), Through(List<string>), Unknown }

- **`Nothing`** when the set is empty. The fn is a pure function of its arguments: it can be cached on
  their identities, and a row of it can be kept on its key and props.
- **`Cells`** when it names module cells only. A kept instance observes those cells.
- **`Through`** when it reads cells through named params (rule 9). A kept instance must observe the
  cells it reached through those params at its last paint. The runtime can name them: walk the prop to
  its `Cell`s once at the stand, and `avra_box_observe` each. Or the caller declines to keep it.
- **`Unknown`** when the set holds `?`.

Its cost to a caller is one saved answer read, of a list of keys. The answer is saved by the fn's
content, and moves only when a reached body's set moves (section 7).

A prop's type answers the other half statically. A prop whose type holds no `Cell` and no `state` field,
at any depth, carries no hidden cell, so its identity is its value. `declared_shapes` already walks a
type's fields for `compares_by_value`, and the same walk answers "holds a cell".

## 6. What a write does to reach the instances that read it

No new runtime mechanism. It is the exact path's, keyed by instance instead of by text.

1. At a stand, a kept instance observes each cell of its set (`avra_box_observe`, which holds the box).
   It files itself under each cell's key (`avra_box_key`), beside its key, its props' identities and the
   nodes it made.
2. A write is unchanged: one byte compare. The first write of a turn to an observed cell logs it.
3. The turn takes the log, looks up the instances filed under each logged key, and marks them stale.
4. The next paint describes a stale instance, and any instance whose key or props moved. Every other
   instance hands back its nodes.
5. An instance that leaves the tree unobserves its cells (`avra_box_unobserve`), as a reading does.

The cost: per cell read, nothing. Per first write of a turn to an observed cell, one log append. Per
logged cell, one table lookup.

## 7. Cold and warm cost

**Measured, cold.** The 11 board fns' read sets add no measurable time to a check. The board judged
alone took 138 s and 144 s across two runs; judged and then asked all 11 `fn_reaches`, 146 s and 149 s.
The difference is within run-to-run noise.

The walk reads each fn's elaborated body, which typing has already made. A fn's set is one pass over its
nodes, and `fn_reaches` unions keys. Generalising to every composition adds one `reaches` per view type,
which is 12 compositions on the board and std-ui's 25 primitives, over the fns they reach.

**Warm.** Today `fn_reads` and `fn_reaches` are `@query`. To meet the ask (a deep edit that does not
change a read set reaches no caller), both become `@cut_query`: a body edit re-asks that fn's
`fn_reads`, and an answer that comes out the same stops there. A signature edit that adds a read moves
the sets of exactly the fns that reach it.

**To measure when built:** the board's cold and warm `build --passes` ledger before and after, with the
census, held to the tape pass's bar (each row within +0.05% or falling, warm and cold).

## 8. When the estimate is too wide to help

An instance whose set is `Unknown` is described every paint, as today: never wrong, only slower. The
question is who hears about it.

- **Proposed: a warning, only where keeping matters.** Where an instance is a row of a windowed list
  (`rows`, `windowed`), a set of `Unknown` is said once, at the component, naming the first `?` and the
  chain it is reached through: "`task_row` is described every paint: it reaches `tasks`, which calls
  `tasks_ask.value()`, which the compiler cannot see into". This is `ctx_required`'s chain voice.
- **Not proposed: a refusal.** A view may read what the compiler cannot name, and its program is still
  right. A program that wants the guarantee asks for it, with a mark on the component that refuses
  `Unknown` and `Through` (ask 4).

## 9. Asks for a ruling

1. **Rules 4–6 and 8.** May the query resolve inherent methods and the language's verbs, walk applied
   lambdas, and read `dyn` as the union of the program's impls?
2. **Rule 9.** Is a cell reached through a param marked as `Through(param)`, and does a kept instance
   observe it at its stand? Or should an instance that reads through a prop simply not be kept?
3. **Rule 10.** A std-meta mark for a method that reads only its receiver's own cells, worn by
   `Fetch.value` and its kin?
4. **Too wide.** A warning only under a windowed list? And should a mark that refuses it come now or
   later?
5. **The view's set stops at its children** (section 4). Agreed?
6. **`@cut_query`** for `fn_reads` and `fn_reaches`, and their own pass in the ledger rather than laws?
