# S2c — THE IMPLEMENTATION DESIGN, for review before any code

The shape was chosen at `docs/2026_09_07_S2C_DYLIB.md`: a per-package
shared library, opened by the program's own dependency closure. That
paper measured three shapes and recommended one. THIS note is the
implementation — the seams, the decisions with their reasons, the
acceptance tests, and the two questions that are lane A's.

Nothing here is written until the lead and lane A have read it.

## 0. WHAT CHANGES, IN ONE PARAGRAPH

The tree derives one shared library per LINKING PACKAGE from the
objects that package's `[link]` row already names. `avra run` opens
the libraries of the program's own dependency closure and asks THOSE
handles for a symbol before falling back to the running image. A
program that does not depend on `@std/sqlite` cannot reach
`sqlite3_open` under the evaluator; a program that does, can, and
`corpus/net` and `corpus/sqlite` become differential instead of
native-only.

## 1. THE HAZARD THAT DECIDES THE WHOLE DESIGN

**THE LIBRARY IS OPENED `RTLD_LOCAL`, AND THIS IS NOT A DETAIL.**

`dlopen` with `RTLD_GLOBAL` puts a library's symbols into the
process's global namespace, where `dlsym(RTLD_DEFAULT, …)` finds them
— for every later lookup in that process, by anyone. And `./avra
corpus corpus` RUNS EVERY PROGRAM IN ONE PROCESS. So under
`RTLD_GLOBAL` the first corpus program that depends on `@std/sqlite`
would open sqlite's library and every LATER program in that run would
find `sqlite3_open` through the fallback, whether or not it declared
the dependency.

The failure mode is what makes it dangerous: the leak makes a program
PASS that should have been refused, and it depends on the ORDER the
corpus happens to walk its directories. A green run is what it looks
like. This is the guard-and-the-guarded law at a new boundary — the
guard is the dependency closure and the guarded thing is `dlsym`, and
`RTLD_GLOBAL` makes them read different namespaces.

`RTLD_LOCAL` (the default when neither flag is given, but written
EXPLICITLY because a reader must not have to know that) keeps every
opened library reachable only through its own handle. The narrowing is
then a property of the mechanism rather than of the order programs
run in.

**THE TEST THAT WOULD CATCH A REGRESSION** is ORDERED: a program that
opens sqlite, then a program that declares `sqlite3_open` and depends
on nothing, which must refuse. One process, both programs, and the
second one's refusal is the assertion.

**AND THE ORDER MUST BE STRUCTURALLY ORDERED, NEVER THE CORPUS WALK'S.**
The lead's point, and it is the difference between a test and a
coincidence: the corpus walks its directories in name order, so a pair
that happens to sort the right way asserts the property until someone
RENAMES a directory — and then it asserts nothing, silently, with the
run still green. The order becomes a property of the HARNESS: ONE row
that runs both programs in sequence in one process, the way
`tools/traps.sh` runs one, with the reason written at the row. What
would break it is a second harness that runs them separately, and the
row says so.

**AND IT IS NOT TRUSTED UNTIL IT HAS BEEN WITNESSED FAILING.** Lane
A's, and it is this tree's untested-instrument law aimed at the one
test the whole design rests on: build it, flip the open to
`RTLD_GLOBAL`, watch the SECOND program pass, flip it back, and say so
in the commit. A test whose failure nobody has seen guards nothing,
and this one guards a leak that looks exactly like success.

## 2. THE DERIVATION — a manifest never names the library

§2.3's law is that a manifest says what to LINK and never how to build
it, because a manifest path the toolchain WRITES is a write primitive
across a dependency boundary. A manifest path the toolchain OPENS is a
LOAD primitive and carries the same force: a dependency three levels
down must not be able to point the evaluator at a file on disk.

So the library's path is DERIVED and the manifest cannot influence it:

    build/lib<name>.dylib     name = the package's MANIFEST NAME,
                              `@` dropped and `/` → `-`
                              (`@std/sqlite` → `build/libstd-sqlite.dylib`)

The manifest NAME is data the compiler already reads and already
validates for uniqueness across a workspace; it is not a path and
cannot become one. Deriving from the package's DIRECTORY would work
today and is refused: a directory is a path, and the whole point is
that no path in a dependency reaches this decision.

**ONE LIBRARY PER PACKAGE, NOT PER OBJECT.** `@std/sqlite` names TWO
objects (`sqlite3.o` and `sqlite_sentinel.o`) and two flags (`-lm`,
`-lpthread`); its sentinel calls into the amalgamation. A library per
object would leave those references unresolved and force
`-undefined dynamic_lookup`, which is the flag that turns a link error
into a run-time crash. One library per package links exactly the
objects and flags the `[link]` row already promises, which is also the
only grouping that makes "the package owns its C" true of the artifact
as well as the source.

## 2b. WHAT STEP 1 TAUGHT THE DESIGN — two narrowings, both found by building

The note above was coherent and wrong in two places, and neither was
visible by reading it. A new consumer is the instrument.

**A PACKAGE THE COMPILER ALREADY CARRIES GETS NO LIBRARY.** Six
packages declare `[link]` objects; THREE of them are already inside
`build/avra` — @std/avrac, @std/io, @std/process — which is exactly
why S2a could host their externs at all. Building a library for one of
those adds no reach and adds a SECOND COPY of state meant to be
single. `ffi.o` is the sharpest instance: the frame would have one
staging area in the image and another in the library, with which one a
call used decided by lookup order. So the roster is the linking
packages MINUS the compiler's own image, and the test is `nm
build/avra` — the same instrument `tools/stems.sh` already reads, so
one truth answers both questions. Three libraries, not six:
`@std/net`, `@std/sqlite`, `width-witness`. A package SPLIT across
that seam is refused in words rather than folded into either answer.

**THE RUNTIME IS LEFT UNDEFINED ON PURPOSE, AND BOUND TO THE HOST.** A
package's C references some of the runtime's own symbols, and the
first link failed on exactly that. Linking the runtime INTO each
library is the obvious fix and it is wrong — but MY FIRST REASON FOR
SAYING SO WAS ALSO WRONG, and lane A's correction is the part to
keep.

I wrote that each library would get its own allocator and free lists,
so a box minted inside one and released by the evaluator would reach
the wrong allocator. IT WOULD NOT. Two copies of `g_free[CLASSES]`
PARTITION memory rather than corrupt it: a box freed into one list is
re-used from that list, on one shared malloc heap. No double free, no
wrong-list read. It costs FOOTPRINT — and a footprint argument is
precisely the one that loses to "but it links".

**THE DECISIVE REASON IS `g_once`.** `static OnceSlot
g_once[AVRA_ONCE_MAX]`, duplicated, means a `once fn` reachable from
both copies settles TWICE, with two different answers, where "one
value for the whole process" is the contract F2055 exists to protect.
And those answers are IMMORTAL, so it is two immortal answers where
the language promises one, neither ever dying. That is a SEMANTIC
BREAK, not a cost, and it is the argument that survives contact with
"but it links". `g_acc_live` is the second: `AVRA_MEM_STATS` would
report ONE copy's view and look complete, which is `acc_kind_of`'s
lesson again — an instrument miscounting its own data is worse than
no instrument.

**AND THE HONEST NARROWING, so nobody reads the measurement and
concludes the rule was over-cautious.** Today's libraries are pure C
from `[link]` rows: no Avra code, no `once`, no allocation — which is
exactly WHY only one open symbol was measured. The hazard is NOT LIVE
today. It is what makes "bind to the host" the RULE rather than a
lucky default, and it fires the first time a package's C calls back
into Avra.

Lane A also reads the first narrowing as this same law one layer out:
`ffi.o`'s staging area is state meant to be single, identical in kind
to `g_once`. MEASURED, the dependency is tiny and nameable — across all
three libraries exactly ONE runtime symbol is left open, `avra_trap`
from @std/net; @std/sqlite and `width-witness` leave none. Everything
else undefined is libc, which is the loader's business.

**AND THE FLAG THAT PERMITS IT IS BOUNDED BY A KEEPER.** Mach-O needs
`-undefined dynamic_lookup`, which also permits a TYPO — `avra_traap`
would link clean and fail at first call, which is the run-time crash
this note's §2 warned about in another context. `tools/stems.sh` now
holds every `avra_*` a library leaves undefined to what `build/avra`
exports, CONSUMING `tools/libs.py --undefined` rather than re-deriving
it. Witnessed failing before it was trusted: a bogus `avra_nosuch`
reference in @std/net's C made it say "libstd-net leaves avra_nosuch
for the host and build/avra does not export it", and it went green
again on revert.

## 2c. WHAT STEP 3 DELIVERED, AND WHY THE ORDERED PAIR DIED

**THE ORDERED PAIR IS NOT EXPRESSIBLE, and the reason is worth more
than the test would have been.** `avra corpus` runs many programs in
ONE process — the property this design needs — but it builds ONE
WORKSPACE over the directory, so every program in it shares ONE
dependency closure. "A program that does not depend on sqlite, running
after one that does" cannot be written there: the second program would
have the first's closure. No harness in the tree runs two closures in
one process, and inventing one would have been a compiler change made
to serve a test.

**SO THE MECHANISM IS TESTED DIRECTLY, IN ONE PROGRAM**, and it is
strictly better than the pair: there is no order to get wrong, no
directory-walk luck, and no rename that silently reverses it. A
program that DOES depend on @std/sqlite asks the frame's IMAGE-ONLY
lookup — `dlsym(RTLD_DEFAULT)` — for a symbol that lives in the
library its own closure opened. Under `RTLD_LOCAL` that answers 0.
`tools/libscope.sh` holds three rows: the library is REACHED by its
dependent, its symbols are NOT in the process, and a program that
declares the dependency nowhere is refused by name.

**WITNESSED FAILING BEFORE IT WAS TRUSTED**, as lane A required.
Flipping `RTLD_LOCAL` to `RTLD_GLOBAL` in `ffi.c` turns row 2 red —
the symbol becomes visible through the process and the row answers
`false` where it must answer `true`. Flipped back, three rows green.

**THE HOST TAKES ONE HANDLE, NOT A LIST, and this slice's own law
decided that.** `avra_ffi_symbol_in(handle, name)` asks about a single
library because an aggregate cannot cross an extern seat (F2056), so
a `List<int>` of handles could not be a seat at all. The loop lives in
the evaluator, which is where per-PROGRAM identity belongs — lane A's
answer arrived at the same place from the lifetime side, and the type
law arrived there from the seat side.

**WHAT IT DELIVERS, MEASURED.** `corpus/net` and `corpus/http-serve`
lose `native-only` and are differential now — the first package C the
evaluator has ever reached. `corpus/sqlite` and
`corpus/sqlite-refusals` do NOT, and the reason is no longer symbol
reach: they refuse with "`sqlite3_open_v2` has a `mut` seat — the
frame does not carry an inout yet". That is §5.6.8's recorded
refusal, and its recorded trigger was "the first in-image extern with
a `mut` seat, or S2c putting a package's own C in reach". S2C JUST
FIRED THAT TRIGGER, which is what a recorded trigger is for, and the
inout frame is the next slice rather than a surprise.

## 3. WHO BUILDS IT, AND WHAT `avra run` DOES WHEN IT IS ABSENT

**THE TREE BUILDS IT, NOT THE COMPILER.** `avra run` does not invoke a
linker. The Makefile gains a target under the same stem discipline as
`build/%.o`, and `make avra` is UNTOUCHED — the compiler links nothing
new, so the per-target split that keeps the amalgamation off every
cold build stays exactly as it is.

The grouping the rule needs (objects and flags PER PACKAGE) is not
something the current `sed` one-liner can express, so it moves to
`tools/libs.py`, which reads every `packages/*/avra.toml`, groups by
package, and emits one clang line each. That tool is also what
`tools/stems.sh` reads to check the libraries, so there is ONE
definition of "what a package's library is made of".

**AND WHEN THE LIBRARY IS NOT BUILT, `avra run` REFUSES BY NAME.** Not
a fallback, not a silent miss — the same shape as today's `no_symbol`:

    `sqlite3_open` is `@std/sqlite`'s and its library is not built —
    `make libs`, or build natively

A refusal a person can act on, naming the package that owns the
symbol and the two ways forward. The alternative — falling through to
the image — would answer differently depending on whether someone had
run `make` recently, which is the class of thing this campaign exists
to remove.

## 4. THE LOOKUP, AND AN HONEST CORRECTION TO THE PAPER

`avra_ffi_symbol` asks `dlsym(RTLD_DEFAULT, name)` today. It will ask
each opened handle in dependency order first, then the image.

**THE PAPER OVERSTATED WHAT THIS DELIVERS**, and the correction
belongs here rather than in a footnote later. §5 of the paper says
shape A makes "the evaluator reach exactly what the native build would
link". It does not, because the image fallback stays — and it must,
since S2a's entire delivery is the 125 in-image declarations, plus
every `avra_ffi_*` the frame itself calls. What shape A actually
delivers is narrower and still worth having: **A PACKAGE'S SYMBOL IS
REACHABLE ONLY WHEN THE PROGRAM DEPENDS ON THE PACKAGE.** libc and the
compiler's own image stay as reachable as they are today.

That is enough for the acceptance test the lead named, and the reason
is worth writing down: `sqlite3_open` is not in `build/avra` at all —
`nm build/avra | grep -c sqlite3_open` answers 0, because the
per-target object split kept the amalgamation out of the compiler.
The refusal for an undeclared dependency therefore comes from the
symbol being ABSENT, not from the lookup being scoped. **So the
acceptance test passes for a reason the design does not control**, and
that is exactly the shape of an unstated condition: the day anything
links sqlite into `build/avra`, that test goes green while the
property it names is gone. The test above in §1 — two programs, one
process, ordered — is the one that tests the SCOPE, and it is the one
that must exist.

## 5. WHAT IT COSTS, AND WHAT MUST BE MEASURED

Owed before this lands, each with its number in the commit:

- `make avra` wall time and `build/avra` size, before and after, ON
  ONE TREE, WITH THE COMMIT NAMED BESIDE EACH NUMBER. The first draft
  of this note wrote "2,263,008 bytes today" with no base: that is
  `lane/http`'s, and main's was 2,122,704 the same afternoon. A size
  quoted without its commit is not a measurement, and a before/after
  taken across two trees measures the trees. The claim is UNCHANGED
  and it is falsifiable once both numbers name one base.
- The one-time cost of building the libraries, per package.

**STEP 1's NUMBERS, ALL ON BASE `b2255fe`, ONE TREE.** `make avra` is
UNCHANGED: 12.45 s user / 2.08 s sys before, 12.22 s / 1.81 s after,
and `build/avra` is 2,263,728 bytes BOTH times — the same number, not
a similar one. Wall time is not quoted for the "before" run because it
was 503 s against 12 s, all of it waiting on a shared build lock: WALL
TIME ON THIS MACHINE MEASURES THE QUEUE, so the CPU figures are the
measurement and the wall figure is noise with a plausible face.
Linking all three libraries costs 0.52 s real, and they occupy
1.73 MB in `build/` and nothing in any user's binary
(`libstd-sqlite` 1,641,680, `libstd-net` 52,032, `libwidth-witness`
33,976).
- A net program's first `avra run`, which pays one `dlopen`.
- `./avra corpus corpus` wall time, since it gains two differential
  programs and some `dlopen`s.

**AND AN UNSTATED CONDITION, REGISTERED RATHER THAN TESTED.** Symbol
scoping does not scope STATE. Under the evaluator two corpus programs
that depend on `@std/sqlite` share the library's PROCESS-GLOBAL state
— its configuration, its initialised flag — where the native build
gives each program its own process. So a program that leaves the
library configured differently changes the next one's answers, and no
amount of per-handle lookup touches that. It is a DEADLINE, not a
case: it fires the day a corpus program calls a library's global
configuration verb, and on that day the fix is a process per program
under the evaluator, not a narrower `dlopen`.

## 6. WHAT THE STANDARD OWES AFTERWARDS — A LINE IN §2.3

**THE STEM LAW GUARANTEES ONE OBJECT PER STEM AND HAS NEVER GUARANTEED
ONE SYMBOL PER NAME.** Under a flat image, two packages exporting one
name collide at link time and someone notices. Under per-handle
lookup, they resolve per handle and nobody does. This is strictly
SAFER — a program reaches only what its own manifest named — but the
guarantee changes shape and §2.3 must say so IN ITS OWN LINE rather
than in a note beneath the stem law. Lane A's reason is the right one,
and it is why a note would not do: per-handle lookup being SAFER is
exactly why nobody will notice the guarantee moved.

## 7. THE TWO QUESTIONS, ANSWERED BY LANE A

1. **THE BUILD RULE: `tools/libs.py`.** Make cannot parse TOML, and a
   generated `.mk` adds a staleness hazard nothing reports. One tool
   that emits the clang lines is strictly better — AND IT ANSWERS AS
   DATA, which is lane A's condition and the better half of their
   answer: it says "what is this package's library made of" and
   `tools/stems.sh` CONSUMES that answer rather than re-deriving it.
   Two parsers of one truth is how `keeps` and `inert` both went
   wrong in one week.
2. **THE HOST: THE ARGUMENT FORM**, `avra_ffi_symbol_in(handles,
   name)`. Lane A's reasoning is §1's own, one layer up: handles held
   in frame state OUTLIVE the program that opened them, so a later
   program in the same process reaches a symbol it never declared —
   order-dependent, and green. That is `RTLD_GLOBAL` swapped for a
   stale field. AND "THE FRAME ALREADY HOLDS STATE" IS A FALSE
   CONSISTENCY, which is the part worth keeping: the staging area and
   the generation token are per-CALL scratch, while a handle set is
   per-PROGRAM identity. Same location, different LIFETIME, and
   lifetime is the whole question.

## 9. THE RED TEAM OVER THE S2C ARC

The derivation is spelled TWICE — once in `tools/libs.py` for the
build and once in the compiler's `library_stem` for the open — and §2
argued that was tolerable because a disagreement is LOUD. Attacking
the pair found that the argument was right and the SPELLING was not.

**THE TWO HALVES DISAGREED.** `libs.py` used `lstrip("@")`, which
strips EVERY leading `@`; the compiler used `.replace("@", "")`, which
strips an `@` ANYWHERE. So `@std/a@b` derived `std-a@b` on one side
and `std-ab` on the other, and `@@std/x` differed too. Both halves now
strip exactly ONE leading `@` and replace every `/` — a rule written
to be COPIED, which is the property a twice-spelled rule actually
needs. The disagreement was loud, as claimed; being right about the
failure mode is not the same as being right about the code.

**AND THE COLLISION THEY SHARED WAS NOT LOUD.** `@std/a-b` and
`@std/a/b` derive ONE stem in both halves — two packages, one library
path, the second build overwriting the first and the evaluator opening
whichever is on disk. §2's docstring claimed "two packages collide
only if their full names collide, which the workspace already
refuses"; that was false. The build side refuses a collision now,
naming both packages, rather than escaping the stem to buy
injectivity — an escape would rename every existing library for a
case nobody has hit. Witnessed: two manifests renamed to collide made
it say "@std/a-b and @std/a/b both derive `std-a-b` — one library path
for two packages, and the second build would overwrite the first".

**WHAT SURVIVED.** A bare file with no packages and no closure. A
package with no objects. A library that is not built (handle 0, the
image answers, and the refusal names the package only when the symbol
is found nowhere). A handle of 0 asked for a symbol. Both keeper bands
under attack. And the three `libscope` rows unchanged through all of
it.


## 10. THE LOOKUP IS ASKED ONCE PER CALLEE

Lane A's review of step 3 found what my own review round had waved
through with a FALSE reason. `symbol_of` is the first line of
`hosted_extern` and its answer is what the call is made with, so it
runs on EVERY extern call — not, as my leave-alone claimed, only on a
miss. Per call it allocated a list to find one element, `dlsym`'d
every handle rather than stopping at a hit, and recomputed an answer
that is FIXED for the life of the process.

The memo is a `Map<string, int>` on the machine keyed by callee.
ABSENCE IS REMEMBERED TOO: `0` is a real answer here and not a missing
one, so a callee nothing carries stays absent instead of re-walking
every handle to learn the same thing each time. Short-circuiting the
handle walk was not done and is not wanted — caching dominates it, and
the early-exit spelling would be the flag loop the idiom bar refuses.

**MEASURED**, 200,000 extern calls under `avra run` over a two-library
closure, medians of three, base `db688ac`:

| | before | after |
| --- | --- | --- |
| the program | 1.12 s | 0.58 s |
| the same loop with no extern call | 0.50 s | 0.49 s |
| the extern calls alone | 0.62 s | 0.09 s |

Per call, 3.1 µs to 0.45 µs. Bigger than the "invisible in the
compiler, real in a framer" the review expected, because the walk was
N `dlsym`s and a list allocation rather than one lookup. THE CONTROL
IS THE HALF THAT MAKES IT A MEASUREMENT: the same loop with the extern
removed is unchanged at 0.50 s against 0.49 s, so the difference is the
lookup and not the interpreter.

WHAT WAS NOT MEASURED, said rather than implied: the compiler's own
suite before and after. The memo landed on a base whose "before" was
never timed, and a clean answer costs four builds on a shared machine.
The effect is per-extern-call under the EVALUATOR, which the
compiler's native path does not take.
