# The PR check: a compiler in seconds, and a wall-clock budget

This is the design and the receipts for `.github/workflows/checks.yml`'s
pull-request path: a green PR should cost seconds of build and a few
minutes of wall time, with no human or agent watching it, and it should
REFUSE when it grows.

## What a PR runs

The merge queue is gone and the PR itself is the gate (PR #565): `prepare`
decides what the run owes, takes or builds the compiler once, and hands the
binary, the warm store and the C objects down; `gate` runs `fmt` on the
touched `.av` and `check` on the affected packages; `codecs` runs the codec
scan when the compiler's source moved; the keepers, the seed check and the
affected packages' suites run beside them; and `test` is the one required
check, judging both the aggregate (`tools/ci_verdict.py`, whose refusal names
what it counted) and the wall-clock budget. `merge_group` is still accepted
so a repo that re-enables a queue needs no edit.

## The compiler fetch

The compiler is keyed by its own source (`tools/compiler_paths.sh --key`),
and main publishes the binary under that key as a release
(`tools/compiler_release.py publish`, in `publish-compiler`). The release is
not ref-scoped, so every train and PR can read it.

`prepare` tries, in order:

1. the exact cache key for the tree (a hit is the tree's own compiler);
2. `compiler_release.py fetch <tree-key>` — the tree's own release, if one
   exists (a hit needs no build at all);
3. **main's own compiler** — `tools/fetch_compiler.sh <base>`, where the base
   is `origin/main` (main's own push: the commit before it). Only a push to
   main publishes, so a train's or a PR's own key can never have a release.
   Main's binary, beside the restored `.avra-cache`, is where the incremental
   build starts; the committed seed (`make bootstrap`) is the last resort, and
   NOTHING ELSE starts a build: the newest release may come from any tree
   main ever published — a batch landed then reverted is one — and may already
   know the features of the tree it would build. A prefix-restored binary is
   discarded for the same reason.

   A fallback HIT still owes a build — the binary is not the tree's — so
   `make avra` runs twice (one generation each, the second fixes the point).
   Only an exact hit sets `hit=true` and skips the build.

Both fetches smoke-run the binary; one built for another image falls
through. A miss is a `::warning::` carrying the fetcher's own reason, never
a silent 15-minute rebuild.

Read the evidence in the `compiler from release` step's log:

- `compiler-release: HIT — the tree's own key …` then `compiler … 0`
- `::warning::compiler release for avrac-… missed (…); starting the build
  from main's compiler (origin/main)`
- `::warning::compiler release for avrac-… missed (…) and main's compiler
  (origin/main) is not published or did not run; building from the committed seed`

## The warm store rides down

`prepare`'s `.avra-cache` is the tree compiler's analysis cache. It is
uploaded as the `avra-store` artifact (and appended to `avra-build.tar`),
then handed to `gate`, the keepers, the suites and the cache attacks, so a
`check` or a suite reads what `prepare`'s self-compile already analysed
instead of compiling every module cold. A cache cannot carry it (a train's
ref is throwaway), which is why it is an artifact, not a cache.

## The C objects are cached by the C that built them

`make objects libs` builds the runtime, the LLVM wrapper and every
package's C into `build/*.o` and `build/*.a`. Its cache key is
`hashFiles` of exactly those sources (`backend/**`, `runtime/**`,
`packages/**/src/c/**`, `packages/**/vendor/**`, `Makefile`), so a
`.av`-only change leaves the objects identical and the step is a no-op.
Saves ride `push`/`workflow_dispatch`, like the compiler cache.

## Timeouts

Every job carries `timeout-minutes`, and every heavy step carries a named
`timeout` bound sized from measured cost. A hung step dies with an
`::error::` naming it, never 15 minutes of silence.

| step | bound | behind the number |
| --- | --- | --- |
| `prepare` job | 65 min | backstop above the compiler (50) and objects (15) steps |
| `compiler from release` | 5 min job-step / 120 s client | two API calls and a 15 MB download |
| one `make avra` generation | 1500 s | cold self-compile measured ~517 s; raised from 900 s while the builder is slow (see the trigger in checks.yml) |
| `make bootstrap` | 1500 s | cold bootstrap ~17 min |
| `objects and libs` | 900 s | measured ~26 s cold |
| `gate` | 900 s | measured 6.5–8 min before the store rode down |
| `seed check` | 20 min | measured ~10 min |
| keepers-a / keepers-b | 30 min | measured ~15 min / ~3 min |
| `cache-attacks` / `code-hash-attacks` | 15 min | measured ~4 min / ~2 min |
| `suites` | 30 min | measured 3–15 min per shard |
| `test` / `wall budget` | 5 min / 4 min | seconds |

## The wall-clock budget

`tools/ci_wall.sh` reads a run's own job clocks from the GitHub jobs API
and writes one stream:

```
host ci-wall
wall prepare <ms>
wall gate <ms>
wall total <ms>
```

`total` is the SUM of the jobs' own clocks, so no queue between them
inflates it; a skipped job has no clock and is left out. It is a WORK
figure, not a makespan, and it grows with the gate's parallelism — which is
why the `ci-wall` ceilings are calibrated to the FULL GATE the PR now runs
(keepers, seed check and suites included), never to the fast floor the
budget was first written for. A PR that builds its own compiler costs ~16
min of `prepare` and ~70 min of summed job clock, so the first ceilings
refused every PR the day the queue was dropped; they are a human edit
calibrated from the completed runs that measured the gate.

`tools/speed_ratchet.py --wall` judges it
against the SAME `tools/speed.budget` the phase ratchet reads (one file,
one reader), in the `test` job of every PR run:

```
sh tools/ci_wall.sh collect > wall.metrics
python3 tools/speed_ratchet.py --wall --raw wall.metrics
```

The ceilings are HARD (no ratio, no slack), and **a ceiling may only
fall**. To lower them to a real run's times:

```
GH_TOKEN=… sh tools/ci_wall.sh --repo avra-lang/avra --run <id> collect > wall.metrics
make wall-accept WALL=wall.metrics
```

A host with no row is measured, printed and NOT gated:
`speed: NO WALL CEILING ROW for ci-wall — measured, not gated`. It is never
a silent pass. Raising a ceiling is a human edit of `tools/speed.budget`,
and that diff is the review.

## The warm-edit gate runs in CI

The DB 07 acceptance (avra-8sb5.57.176) is a warm `check packages/cli`:
<= 60 ms unchanged, <= 300 ms after one body edit. It lived in
`tools/warm_edit_bench.sh` from #552 but was never judged — the keeper
SKIPPED when no warm store stood, and no row keyed the runner, so CI was
green while the path was hundreds of times over.

Now the store `prepare` hands down (the `.avra-cache` inside
`avra-build.tar`, the same hand-down the `gate` and the suites read)
reaches `keepers-a`, and `prepare` leaves one standing even on an
exact-key release hit: if `.avra-cache` is empty it runs one
`check packages/cli` under the compiler it is about to hand down, so the
store is keyed to the binary the keeper will use.

`SPEED_HOST=ci-warm` in the keeper keys the numbers to one stable name —
never to whatever CPU the runner happens to draw. The ticket's GOAL is an
unchanged check <= 60 ms and one edit <= 300 ms (goal 150), but today's
path is hundreds of times over it, so the goal stands as a COMMENT in
`tools/speed.budget` and the ENFORCED rows are the MEASURED PRESENT — the
starting line. They are seeded from real runs (the CI runner measured two
same-commit runs 1.62x apart: 194 ms/14 824 ms and 314 ms/23 216 ms), and
the gate allows `WARM_RATIO` of a row for that variance, so ordinary
runner noise cannot make it flake. `--warm --accept` may only LOWER a row
to a faster real run, never raise one (`make warm-accept`), so the lane
that fixes the cost walks the ceiling down toward the goal.

A run that cannot judge is a FAILURE, by name, never a skip:

```
warm_edit_bench: no warm store at .avra-cache
warm_edit_bench: this is a FAILURE — the warm-edit gate cannot judge; set WARM_EDIT_SKIP=1 by hand only to skip
```

The ONLY skip is the `warm_skip` `workflow_dispatch` input, passed as
`WARM_EDIT_SKIP`; it says so loudly and the gate is not judged. The bench
and the ratchet (`--warm`) both refuse a skip stream without it
(`tools/witness_warm_edit.sh` proves both directions).

Cost: six `check packages/cli` rounds per run (`SPEED_ROUNDS`, default 3
unchanged + 3 edited), and once the path meets its target that is under a
second. On the tree as it stands it is minutes, which is the gate doing its
job, not a reason to skip it.

## What still needs a human

These are repository settings, not code, and the commands are exact.

1. **Up-to-date branches.** The owner's target assumes `main` requires
   branches to be up to date. Today the ruleset has
   `strict_required_status_checks_policy: false`:

   ```
   gh api repos/avra-lang/avra/rulesets/24277567 > /tmp/ruleset.json
   python3 - <<'EOF'
   import json
   p = json.load(open("/tmp/ruleset.json"))
   for r in p["rules"]:
       if r["type"] == "required_status_checks":
           r["parameters"]["strict_required_status_checks_policy"] = True
   json.dump(p, open("/tmp/ruleset.json", "w"))
   EOF
   gh api -X PUT repos/avra-lang/avra/rulesets/24277567 --input /tmp/ruleset.json
   ```

2. **The merge queue.** The ruleset still carries a `merge_queue` rule and
   the workflow still fires on `merge_group`. If the queue is dropped
   (a PR is in flight), the train jobs (`keepers-*`, `seed-check`,
   `cache-attacks`, `suites`) must move to `push` on `main` or they will
   never run before landing. The PR path above is unaffected either way.

3. **Release publishing** is automatic: `publish-compiler` runs on every
   push to `main` and publishes under main's key. The first run after this
   lands needs that push's release to exist; after that the fallback always
   has main's own compiler to read once main's run has proved it.

### What is still on the critical path (the target is NOT met for a
### compiler-touching PR)

The after `prepare` is 466 s, dominated by the `compiler` step's 424 s,
which is one `lower`-and-emit pass of the whole compiler. Two findings:

1. **The fallback's store did not match the fetched binary.** The price of
a cache means nothing if it is not the right one: the prefix restore gave
main's *older* compiler's `.avra-cache` (`avrac-e87b8abe…`) while `latest`
fetched the newest (`avrac-a02d70fb…`), so no module was reused and
`lower` re-ran for the full 424 s. The fix is to publish the store as a
second release asset beside the binary, so a fetch always gets a store keyed
to the binary it just took. (`tools/compiler_release.py` has the seam for
it: `publish`/`fetch` take an optional store path.)

2. **`lower` re-runs regardless.** Even with a matching store, the
self-compile's `lower` phase (~368 s cold) is one program and does not
partially reuse. Making a compiler-touching PR take seconds needs a
`lower`-level cache, a compiler change, not a CI one.

### Gap

The `gate` step's time WITH the store handed down is not measured: the
draft proof PR (#566) sat ~15 min in the GitHub runner queue without ever
starting a job (the repo was at 1 in-progress / 10 queued runs). The gate
ceiling is set from the before value (460 s) and will be ratcheted by
`make wall-accept` on the first run that measures it.
