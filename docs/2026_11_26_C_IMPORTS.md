# C imports: externs derived from their headers

Ticket avra-8sb5.125. At a bodiless `extern fn` naming a C function, the
compiler reads that function's real declaration from the headers its
package's `[link]` row names. It derives the seats the header can answer:
width, signedness, register file, pointer or value, variadic, void. A
written extern that disagrees with its header is an ordinary error at that
line, and its structured fix is the header's own spelling. The model is
Zig's `@cImport` and Swift's clang importer. The difference here: the Avra
declaration stays written, and the header holds it to account.

Measured at `42ed174` (program), Linux x86-64, clang 22.1.8. Every number
below is a warm page cache unless it is marked cold.

## 1. How the compiler reaches clang

**What is linked today: LLVM, not clang.** `packages/std-avrac/avra.toml`
links LLVM's static component libraries (`docs/2026_10_18_STATIC_LLVM.md`),
and `backend/llvm_wrapper.c` includes `llvm-c/*` only. No clang frontend
library is in `build/avra`. The manifest also says `dynamic_symbols = true`,
so the binary exports its LLVM symbols. Three ways in were measured:

| route | avra_runtime.h | sqlite3.h | a package `.c` | cost to the binary | verdict |
|---|---|---|---|---|---|
| **dlopen libclang** (C API) | 7.5 ms, +15 MB | 11 ms | 62 ms (runtime.c) | none | **refused**: it **double-frees at exit** |
| **spawn clang**, `-Xclang -ast-dump=json` + `@std/json` | ~20 ms + JSON 0.4 MB | ~30 ms + JSON 1 MB, parsed in 11–13 ms, 11 MB | 40–50 ms + 0.75–10 MB of JSON | none | **slice 1** |
| **static clang C++ libs**, in the same LLVM | 2.5 ms | 5.4 ms | 38 ms (runtime.c), 28 MB peak | ≤ +32 MB stripped (a standalone clang+LLVM test binary is 33 MB) | **the upgrade path** |

Why dlopen is refused: libclang.so brings a shared libLLVM into a process
that already holds a static LLVM and exports it. Measured by preloading a
libclang parse into `build/avra --version`: the parse succeeds, then exit
dies with `free(): double free detected in tcache 2`. `RTLD_DEEPBIND` stops
the crash, but it exists only in glibc, so it is a platform quirk, not a
design.

The route is the **spawned clang**, behind ONE verb,
`c_decls(unit: CUnit) -> CDecls`. Clang is already the toolchain's one
required tool (`packages/cli/avra.toml`'s `[process.tools] clang`, found by
`chosen`/`LLVM_PREFIXES`). `compiler/build.av` already spawns it to link,
and `@std/json` already reads JSON. It needs no new runtime row, so no
ladder, and it changes no link. Moving to in-process static clang later
changes the verb's body, not its callers. That move is worth its megabytes
only if the cold cost shows up in a measurement: the store (§5) makes the
warm cost one hash per file.

## 2. Which headers, per package

The headers belong to the manifest, beside the objects they describe:

```toml
[link]
objects = ["../../build/sqlite3.o", "../../build/sqlite_sentinel.o"]
headers = ["vendor/sqlite3.h"]          # what clang reads, package-relative
include = ["vendor"]                    # -I, package-relative; optional
# a system header is spelled as C spells it: headers = ["<math.h>"]
```

- **A package with a vendored header** (std-sqlite: 91 `sqlite3_*` externs
  over `vendor/sqlite3.h`) names that header. It is the first customer.
- **A package whose own C has no header** (std-io, std-net, std-process,
  std-time, std-hash, std-compress, width-witness: `avra_*` definitions in
  `src/c/*.c`) names the `.c` file itself, because a definition is a
  declaration. That costs 10 MB of JSON per file on the spawn route
  (std_io.c 9.6 MB, std_net.c 10.2 MB), about 120 ms cold. The better
  answer is a small header per package's C, which also makes the C
  compiler check the header against the body. Each package picks one when
  its slice lands.
- **libc** (`frexp`, `rand_r`): `headers = ["<math.h>", "<stdlib.h>"]`.
  These are the externs `tools/externs.py` calls *guessed*: it can read no
  body for them.
- **The runtime's rows** (`rt_sigs()`) are not in scope for the first
  slices (§6, step 6). Their C side is already held at C compile time by
  `runtime/avra_rt.h`, which is generated FROM the rows. Deriving the rows
  from the C would only make that loop circular.

A `[link]` with no `headers` derives nothing. Its externs are held exactly
as they are today, and the build says so once per package
(`extern: @std/x names no headers — N externs unread`). It never stays
silent.

## 3. What is derived, what is checked

The header's words are read through the **canonical** type (`typedef`s
resolved, as `clang -ast-dump` gives `qualType`/`desugaredQualType`).

DERIVED. The header owns the answer, and the written seat states the value:

- **The crossing width and signedness of an integer seat or answer.** A
  written `int` means "an Avra int crosses here", and the header picks
  `i32`/`u32`/`i64`/`u8`… for the crossing. This retires the "bare `int`
  is a 64-bit guess" class (`defaulted_walls`) wherever a header is named,
  and keeps A WIDTH IS A PROPERTY OF A SEAT, NOT OF A VALUE.
- **Variadic.** The header says `...`, so the fixed spelling is refused
  before it can read 12345 back as -298729216.
- **Void.** A C `void` answer read as a value is refused.

CHECKED. Written, and refused when it disagrees:

- **An explicit width word** (`i32`, `u32`, `i64`) against the canonical
  type: width and signedness.
- **The register file.** `float` against `double`, and a word against
  `double`.
- **Pointer against value**, both ways. The `ptr`/`string`/`Bytes` choice
  is the writer's, but it must sit over a C pointer. `string` must sit
  over `char*`, and a `Text` box must not sit over a `void*`
  (A POINTER SEAT NAMES ITS BOX).
- **Seat count.**
- **A struct or union passed by value** (one frame cannot carry it, the
  `unframeable` class).
- **`Bytes` earning its exemption:** a length must follow the pointer in
  the prototype.
- **Presence:** an extern whose name is in no named header is an error
  when the package names headers. A host fn, an extern with a body, is
  exempt: it DEFINES the symbol.

NOT the header's to answer, and still written: whether a pointer answer may
be null (`ptr?`; C says nothing unless it writes `_Nonnull`), which box a
`void*` reads (A POINTER SEAT NAMES ITS BOX), and ownership (`owns_result`,
`keeps`).

## 4. The cost

Measured, cold parse of `runtime/avra_runtime.h`. The cold figure is a
first touch of the files from disk; the warm figure is the steady state.

| route | cold | warm | memory |
|---|---|---|---|
| spawned clang | 490 ms | 20–30 ms | 82 MB peak, in the child |
| libclang (in-process, for reference) | 418 ms | 7.5 ms | +15 MB |
| static clang (in-process, for reference) | — | 2.4–2.8 ms | 28 MB whole-process peak, even on runtime.c |

Plus the Avra JSON read: 0.4 MB for this header, and sqlite3.h's 1 MB
parses in 11–13 ms at 11 MB peak. A warm compile pays one digest of each
file in the key and no clang (§5). avra_runtime.h's dependency closure is
41 headers; sqlite3.h's is 7.

## 5. The store key

`digest(clang identity, the unit's flags (-I/-D/-x), and the BYTES of
every file in the unit's dependency closure)`. The closure comes from the
same clang run (`-MD -MF`), so a changed `stdint.h` re-reads the header
just as a changed `sqlite3.h` does. The header's bytes alone are not
enough: a typedef three includes down changes the answer. The clang
identity is `clang --version`'s text plus the binary's size and mtime,
because an Apple clang and an LLVM clang can disagree on `long`.

The value is the extracted `CDecls`, not the JSON: name, canonical answer,
canonical seats, variadic. It is stored in the compiler's store beside the
other cross-compile facts (`.avra-cache`), keyed as above. Two derivations,
ONE value: the key's digest is also the entry's name (THE KEY A REMEMBERED
VALUE SETTLES ON AND THE NAME ITS RESULT IS STORED UNDER ARE ONE
DERIVATION).

THE EMPTY CASE FIRST: a header that declares no functions is a present,
empty `CDecls`. It is never an absent one. "Clang could not read it" is a
third answer with its own voice, never an empty table.

## 6. The voices

Each voice states the law, and each carries the header's line as a label
with the declaration text it read.

- `type.extern_header`: "a C header declares `sqlite3_changes` as
  `int (sqlite3 *)`, and this seat crosses it as `i64`". Remedy.Fix: the
  seat spelled from the header (`u32`, `ptr`…). One kind with the
  disagreement named (width, sign, file, pointer, count, variadic, void,
  by-value), not eight kinds.
- `type.extern_unheaded`: "`sqlite3_foo` is declared by none of this
  package's headers". Help: name the header, or give the extern a body.
- `manifest.header_unread`: clang refused the unit. It carries clang's
  first error and its location. It is spoken at the manifest row, never at
  each extern.
- `manifest.headers_without_clang`: no clang was found. The check does not
  run, and the build says so (consent on its own channel; it never reads as
  green).

## 7. The order of steps

Each step is a small branch, pre-flighted with the touched tests,
`make keepers-static` and `make try`.

1. **This doc.**
2. **The manifest row.** `headers`/`include` are read and validated
   (`manifest.*` voices for a missing file or an absolute path). No
   behaviour yet.
3. **The reader.** `c_decls`: spawn, JSON, then `CDecls`, under the store
   key. A fixture header pins every canonical shape: `int`, `unsigned`,
   `long`, `int64_t` through typedefs, `double`, `char*`, `const char*`,
   `void*`, `T**`, by-value struct, variadic, `void`, and empty. A
   projection, `avra explain header <path>`, prints what the compiler read
   (P7).
4. **The check** (§3 CHECKED) on std-sqlite. The lint law applies: measure
   the true-positive rate over every package before the kinds are errors.
5. **The derive** (§3 DERIVED). Lowering takes an integer seat's crossing
   width from the header, and `defaulted_walls` retires for packages that
   name headers.
6. **The other packages**, each with a header for its own C. libc rows go
   through `<…>` headers.
7. **Retire** what is covered from `tools/externs.py`. That change belongs
   to the keepers lane: I hand over the list, and I do not touch the
   keepers files.
8. **Open question for the lead:** the runtime's rows. Either rt_sigs keeps
   its C-side columns and `avra_rt.h` keeps holding them (today's loop), or
   the runtime gets a real header (`runtime/avra_rows.h`), the rows derive
   their widths from it, and `avra_rt.h` retires.

## 8. What `tools/externs.py` checks that this does NOT cover

A header is a prototype. Everything that reads a C BODY stays the keeper's:

- **Minting:** a body that returns a fresh box (`box_alloc`/`str_owned`)
  needs a row with `owns_result` (`leaking_externs`).
- **Keeping:** a body that retains a seat is `keeps` or `owns_result`
  (`unsaid_keeps`).
- **Terminators:** a body that ends text at a NUL is recorded in
  `tools/terminated.allow` (`terminating_bodies`).
- **`inert` rows** whose body resolves names (`resolving_inerts`).
- **A row's box column against its C** (`wrong_boxes`, `wrong_answers`)
  for `rt_sigs` rows. That is runtime-side (§7 step 8), and `List`/`Map`
  is not a C type in any case.
- **Pointer answers from bodies no tree C declares** (`unread_pointers`).
  Covered only where a header is named.
- **Host fns.** They define, so the typer holds them, not a header.
- **Externs in packages that name no headers**, until their step lands.

`clang -ast-dump` could read bodies too: calls inside a body are in the
AST. That would move the body checks into the compiler as well, but it is
a separate ticket, and the JSON cost grows with every body (runtime.c dumps
60 MB).
