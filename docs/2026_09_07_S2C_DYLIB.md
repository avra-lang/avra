# S2C — HOW `avra run` REACHES C THE COMPILER DOES NOT CARRY

> **Status:** a paper to decide from. No code. Written by the substrate
> lane under the HTTP lead; the decision is the owner's, and the part
> that needs deciding is a CAPABILITY question, not a technical one —
> the technical work is a one-line change to a lookup and a three-line
> build rule. Every number below was measured in this worktree at
> `db0b41e`.

## 0. THE QUESTION, AND WHY IT IS NARROW

The extern host lets `avra run` call a linked C function by name. It
reaches a symbol exactly when `build/avra`'s own image carries it, and
it says so when it does not:

    `avra_net_listen` is extern and this image does not carry it — build natively

That line is the whole of S2C. `@std/io` and `@std/process` gained a
second engine for free, because the compiler's own dependency closure
links their objects — the cli depends on both. `@std/net` and
`@std/sqlite` are in no dependency of the compiler, so `corpus/net`
and `corpus/sqlite` are `native-only` and the evaluator refuses.

**The two packages the differential is worth MOST for are the two it
does not cover.** A socket server and a database driver are exactly
the code where "the two engines agree" is worth having, and exactly
the code that has one engine.

## 1. WHAT IS TRUE TODAY, MEASURED

| | |

| `build/sqlite3.o` | 2.08 MB, 357 exported symbols |
| `build/std_net.o` | 0.01 MB, 15 exported symbols |
| `build/sqlite_sentinel.o` | under 0.01 MB, 1 symbol |
| a cold compile of the amalgamation | 13.61 s |
| the host's lookup | `dlsym(RTLD_DEFAULT, name)`, and `<dlfcn.h>` is already included |
| the keeper that reads the image | `nm -gU build/avra`, one place in `tools/stems.sh` |

Two of those decide most of what follows: **the amalgamation is as big
as the entire compiler**, and **the loader is already in the
trampoline** — S2C adds no new dependency, only a different question
asked of it.

## 2. SHAPE A — A PER-PACKAGE SHARED LIBRARY, OPENED BY DEPENDENCY

The tree derives `build/<stem>.dylib` from the object it already
builds; `avra run` opens the ones the program's own dependency closure
names and asks THOSE handles for a symbol, instead of asking the whole
process.

**COST.** A dylib per linking package, in `build/` and in no user's
binary. sqlite's is about 2 MB on disk and is built once. `make avra`
is untouched: the compiler links nothing new, so the per-target split
that keeps the amalgamation off every cold build stays intact. A net
program's first `avra run` pays one `dlopen` of a 10 KB library.

**THE SEAMS.** The host's symbol lookup, which is one line —
`dlsym(handle, name)` where it says `RTLD_DEFAULT` now. `link_inputs`
in the workspace, which already walks every package's `[link]` row and
would answer the same rows for a different purpose. The Makefile,
which gains a `%.dylib: %.o` rule under the same glob and the same
stem law. `tools/stems.sh` needs nothing: it asks `nm build/avra` what
the COMPILER carries, and under this shape the answer does not change.

**WHAT BREAKS, AND IT IS WORTH SAYING PLAINLY.** A dylib has its own
symbol namespace, so two packages exporting one name stop colliding at
link time and start resolving per handle. The stem law guarantees one
OBJECT per stem; it has never guaranteed one SYMBOL per name, and this
shape is the first place that distinction is observable. It is
strictly safer than the flat image — a program reaches only what its
own manifest named — but the guarantee changes shape and the standard
should say so.

**AND ONE CONSTRAINT THE DESIGN OWES, from §2.3's own law.** A
manifest says what to LINK and never how to build it, because a
manifest path the toolchain WRITES is a write primitive across a
dependency boundary. A manifest path the toolchain OPENS is a LOAD
primitive, and the same reasoning applies with the same force: the
dylib must be DERIVED by the tree from the object the manifest already
names, never named directly by the manifest. Otherwise a dependency
three levels down points the evaluator at any file on disk.

## 3. SHAPE B — LINK EVERY PACKAGE'S OBJECT INTO THE COMPILER

**COST, and it is the shape's answer.** `build/avra` is 2.1 MB and
`sqlite3.o` is 2.08 MB: the compiler nearly DOUBLES to carry one
package's vendored library. Every cold `make avra` pays the
amalgamation's 13.61 s — the cost the per-target split was landed to
remove, restored deliberately. And 357 sqlite symbols join the
compiler's own namespace.

**WHAT BREAKS IS NOT THE SIZE.** `dlsym(RTLD_DEFAULT)` searches the
WHOLE image, so under this shape any program declaring `sqlite3_open`
resolves it under `avra run` **whether or not it ever declared a
dependency on `@std/sqlite`**. A package's C becomes reachable to
programs that never named it, which is the containment the standard
exists to draw. Shape A tightens that boundary; shape B erases it.

This is §5.5's route (c), already refused on the grounds that the
compiler would carry SQLite. The measurement says the refusal was
right and understates it: the objection is not the megabytes, it is
that the image is a flat namespace and the host's lookup is
image-wide.

## 4. SHAPE C — THE STATUS QUO, AND SHAPE D, REFUSED

**C.** `corpus/net` and `corpus/sqlite` stay `native-only`, marked,
with the trigger recorded. Nothing breaks; the tree is honest about
what it proves. The cost is the one named in §0: the differential
misses the two packages it is worth most for, and every future FFI
package joins them.

**D, refused and recorded so it is not re-argued.** Re-link the
evaluator per package set — `avra run` links `build/avra.o` plus the
program's objects into `build/eval-<hash>` and re-execs it. It turns
`avra run` into `avra build`, which is the verb it exists to be faster
and safer than, and it needs the compiler as a relinkable object that
does not exist. Refused.

## 5. THE RECOMMENDATION, BY THE STANDARD'S OWN LAWS

**Shape A, with the derivation constraint of §2.**

The standard's roster asks one question of every substrate: does it
belong to the LANGUAGE or to a PACKAGE? Shape B answers "the language"
for every package's C at once, which is the answer the whole campaign
was written to refuse. Shape A answers "the package", and reaches it
the way the manifest already describes.

It is also the only shape that makes the host's reach MATCH the native
link. Today `dlsym(RTLD_DEFAULT)` is wider than a program's own
manifest — libc is in the image, so `avra run` can already call
`strlen` for a program that declared it and linked nothing. Under
shape A the evaluator reaches exactly what the native build would
link, which is the prior paper's own second law: both engines answer
the same or neither answers.

**WHAT THE OWNER IS ACTUALLY DECIDING.** Not the size, not the seams —
whether the toolchain may BUILD and OPEN a shared library derived from
a package's own C. The honest framing from §5.5a's fourth finding is
that `avra run` already reaches the host in full: it spawns children,
captures their streams, kills them by signal and writes files, through
hosted rows that have been there all along. Shape A adds no class of
power; it narrows an existing one, because a scoped `dlopen` reaches
LESS than today's image-wide `dlsym`.

**IF THE ANSWER IS NO**, shape C is the honest fallback and this
paper's §1 is the record of what it costs. The trigger to re-open is a
package whose corpus a lane wants on both engines and cannot have.
