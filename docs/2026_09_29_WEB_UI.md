## 0. The thesis

**A UI is one program whose computation, state, rendering and
synchronization are placed under explicit laws, and every placement has a
receipt.**

- Short form: *where code runs is compiled, not chosen*. "Compiled" means
  PLANNED UNDER CONSTRAINTS AND ALWAYS OVERRIDABLE — never "the author has no
  say".
- The physics:
  - a screen is a function of state
  - state lives in places separated by latency (browser ~0 ms, server
    50–300 ms, build time = already past)
  - shared truth has an authority; everyone else can only speculate
  - HTML is free to run; every byte of script costs
- Five questions, per fact:
  1. where does this STATE live, and who is its authority?
  2. where does this COMPUTATION run?
  3. how do CHANGES flow?
  4. who may OBSERVE it?
  5. what EXPERIENCE is promised while the answer is unknown, stale or in
     conflict?
- Existing systems expose different subsets of these boundaries at
  different granularities (RSC mixes build/server/client in one tree; Astro
  has client and server islands; local-first is a data-ownership philosophy,
  not a render mode). The author or a framework convention picks most of
  them.
- **Avra's claim:** model placement as ONE typed, whole-program planning
  problem (§8), make its constraints explicit, and print the plan. The
  fibers' "one scope algebra, many placements", with two more: the browser
  and build time.
- Every decision the compiler makes is one of three kinds, and says which:
  **proved** · **derived** (from declarations) · **measured**. Product
  intent (conflict policy, reset behaviour, whether speculation is
  acceptable) is DECLARED, never inferred.
- The primary product surface is `explain` and the live semantic inspector
  (§9.4), not the renderer.

## 1. Why not React + REST

What LLM authors get wrong, by cause (causes differ; the compiler helps
each differently):

| Cause | Failures |
|---|---|
| boundary: hand-written client↔server seam | fetch/type drift, forgotten loading/error, validation twice, unauthed actions, hydration mismatch |
| reactivity API | stale closures, wrong dependency arrays |
| styling namespace | CSS collisions |
| semantics / product | missing a11y, div soup |

- React + REST puts the boundary failures in two languages, invisible to
  both compilers. Reusing it forfeits P10.
- Verdict: a new core, stealing every proven idea (§2).
- Bring-your-own front end stays first-class (old tree PRINCIPLES.md): every
  action and live query projects a typed TS client.

## 3. Reference semantics — the nouns

Semantics first; every optimization is proved OBSERVATIONALLY EQUIVALENT to
this slow model. Fallbacks change COST, never MEANING.

| Noun | Is |
|---|---|
| view | a pure fn from what it reads to a semantic tree |
| semantic node | an interaction contract (role, name, value, state, keyboard, focus) realized as native HTML, a platform control, or canvas + peer (§10) |
| cell | a state value with an identity and a policy (§4) |
| read | an observation of a cell path, a query, or a source |
| write | a path write to a cell, within an event turn |
| event turn | the work an event starts, cut at pause points (§6.1) |
| pause | a point where time passes (`MayPause`, inferred, inspectable) |
| draft | a branch of some truth that knows its base (§4.6) |
| action | the only door to authoritative state (§7) |
| receipt | the durable record of a committed action |

- Surface words stay few: `view`, `page`, `state … at`, `action`, `draft`.
- Reference behaviour: after every committed turn, re-run the view and
  reconcile. The compiler's exact patch plans (§5.2) must be
  indistinguishable from that.

**Three identifiers, never aliases** (they may reference one another):

| Id | Decides |
|---|---|
| semantic identity | state lifetime and reconciliation (§6.2) |
| origin (`OriginId` + `OriginChain`) | author/compiler provenance: generated expansion → component declaration → invocation role/call site |
| runtime node id | correlates an observed browser node with build artifacts (§9.4) |

**Two kinds of equivalence:**
- PROGRAM OBSERVABLES — rendering, semantic interaction, event/action
  traces, state identity/lifetime, task cancellation, focus/browser
  ownership, receipts. Every optimization preserves them.
- TOOLING INVARIANTS — source provenance for diagnostics, hot reload,
  gallery, inspector, profiling. Not observable by the running app; still
  required of every lowering. Production may strip origin chains without
  changing behaviour.
- Optimization gates check BOTH.

### 3.1 Records and profiles — how a feature lands

- The RECORD is the truth and the advanced escape; the PROFILE is the
  ordinary writing surface.
- Every public semantic record ships with:
  - at least one canonical profile
  - a lossless `explain` expansion
  - semantic-law tests on the record
  - cold-start authoring tests on the profile
- The feature lands only when BOTH gates pass. The cold-start gate has no
  veto over semantic truth; a profile whose expansion loses a policy the
  record knows is refused.
- Profiles over any record (state policy §4.3, impact AUTHORITY §4) are overridden
  by ONE `with { … }` that may change one or more fields atomically. The
  result is checked against the record's COMPOSITIONAL laws, never a
  hand-kept compatibility table; the whole semantic diff prints, with the
  nearest named profile.
- A policy built with no profile is the visible P8 hatch.
- **A profile is an ordinary value, MARKED.** A `const` or a pure
  constructor fn (`.room(board)`, `.replicated(T)`: the policy shape
  settles at build time, the key may be runtime) carrying `@profile`. The
  mark adds no evaluation semantics; it registers the value for docs,
  cold-start tests, dotted shorthand and nearest-profile suggestions.
- No std privilege: imports and the expected type decide which marked
  profiles a dotted name reaches. App values stay named unless deliberately
  imported into the profile vocabulary. Two imported profiles answering one
  dotted name at one seat type → refused as ambiguous, naming both.
- **Two checks:** INTRINSIC compositional laws at the declaration (the
  policy's shape); CONTEXTUAL laws at every use (`at .url` needs a URL codec
  for `T`; `.room(key)` has obligations on the key and payload).
- `explain` expands through the ordinary declaration.

## 4. State

### 4.1 Categories — distinct types, never interchangeable

| Category | Is | Mutation contract |
|---|---|---|
| ephemeral interaction | hover, open menu, focus intent | local write |
| navigation | URL, history, restoration | local write, encoded |
| draft | a branch with a base | local write; becomes an action |
| cached observation | replaceable, carries freshness | never written; refreshed |
| authoritative | changed only by committed transitions | action |
| presence | lossy, expiring hints | broadcast; never durable truth |
| replicated | ops/state + causal metadata + merge policy | ops |
| external | owned by another authority, known via receipts | action + effect |

Matching payload types do not make two categories interchangeable.

### 4.2 Policy axes

| Axis | Values (examples) |
|---|---|
| owner / lifetime | view identity, route, tab, account, document |
| authority | browser, server, peer quorum, external system |
| residence | memory, URL, cookie, IndexedDB/OPFS, edge, database |
| durability | ephemeral, reload, offline, retained |
| replication | none, server fan-out, multi-device, peer-to-peer |
| consistency | authoritative replace, CAS, op rebase, CRDT, manual conflict |
| disclosure | public, principal, capability, field-level redaction |

### 4.3 `at` is a PROFILE over the axes

> **One word may select a policy bundle; one word must not erase the
> policies.**

```avra
state filter: Filter = .all at .url
state draft: Draft = Draft {} at .device
```

| `at` | Category | Expands to (headline) |
|---|---|---|
| `.view` (default) | ephemeral | owner: view identity · memory · no replication |
| `.url` | navigation | residence: URL · encoding: typed route format · history |
| `.tab` | ephemeral/draft | owner: the LOGICAL TAB (below) · session storage + generated tab id |
| `.device` | draft/cache | owner: origin storage in this browser profile · IndexedDB/OPFS · evictable |
| `.room(x)` | presence | fan-out via relay · expiring · lossy |
| `.server` | authoritative | authority: server · database · disclosure: capability |
| `.replicated(T)` | replicated | RESERVED — a proved catalogue type (§4.5); unavailable until rung 6 |

- `avra explain state draft` prints the full expanded record: mechanism,
  eviction, privacy, fallback. Overrides: `at .device with { … }` (§3.1).
- **Compositional laws, not a table** (examples):
  - browser authority cannot reach server secrets
  - durable replication needs a conflict law
  - capability disclosure needs a live witness at its authority boundary
  - a cache may not outlive its disclosure grant
- **A move is a semantic diff.** `.view → .url` preserves meaning and is
  automatic. `.device → .server` changes authority, disclosure and latency:
  the build prints the diff and asks for approval. Unsafe moves refuse.
- **The logical tab** (`.tab`), Avra's semantics, not `sessionStorage`'s
  accidents:
  - survives reload and BFCache in the same top-level browsing context
  - not shared with independently opened tabs/windows
  - a cloned tab FORKS the identity on activation
  - no crash-recovery guarantee — use `.device` when crash survival is
    promised
  - implemented with session storage + a generated tab id + clone
    detection; a target that cannot provide it refuses or takes a declared
    fallback
- `.device` names origin storage in one browser profile (partitioned,
  evictable).
- **Offline scope, stated plainly:** `.device` + drafts + queued actions
  cover offline CAPTURE under server authority. They do NOT cover
  multi-master / local-first collaboration; that is `.replicated`, rung 6.
- Per-profile laws:
  - `.url` → the type has a URL format
  - `.room`, `.replicated` → plain data
  - `.server` reads are pause points and fail → `?`
  - `.replicated` → only catalogue types, or a custom type discharging §4.5
- Top-level `state … at .tab/.device/.url` = one instance per request /
  context. No SSR cross-user leak. A top-level `.view` is refused.
- A model is rows under a profile: `@model(at: .replicated(…))`, default
  `.server`.
- **Cookie mirroring is not neutral.** Render-critical `.device` state may
  mirror to a cookie only with a disclosure class; it then shows a
  network/cache diff (sent on every request, cacheability changes, tight
  size budget). Default: a placeholder.
- `.room` adds a relay to the deploy; `explain` shows it.
- SwiftUI arrived at profiles too, as three wrappers (`@AppStorage`,
  `@SceneStorage`, `@Query`). One `at` unifies the spelling; the axes keep
  the meaning.

### 4.4 Presence is not truth

- `.room` values expire and may drop. Using presence (cursors, typing,
  online) as a durable fact is refused (§16).

### 4.5 Replication — a catalogue before user merge

- A merge law over two records does NOT make an arbitrary record a CRDT:
  deletion, list order, causality, tombstone GC, uniqueness, schema
  evolution, permissions and app invariants remain.
- `at .replicated` is a SPECIFIED, RESERVED profile: an ordinary program
  gets a precise diagnostic until rung 6. An experimental std package may
  exercise it earlier; production syntax does not outrun the proof system.
- First: a small catalogue of PROVED replicated types (register, counter,
  set, sequence, map-of-T) + composition rules + the discharge vocabulary.
- Custom replication = an advanced interface; its obligations: operation
  semantics, causal metadata, invariant preservation, migration, GC.
- "Proven" names its receipt: exhaustive finite check · property-tested ·
  SMT · proof-carrying library. Unknown answers `Unproven`, never "probably".

### 4.6 Drafts are universal

> **Truth is copied only as a branch that knows its base.**

A draft is the one primitive for:
- edit forms · optimistic previews · drags · multi-step wizards · offline
  edits · agent proposals · undo branches

Each draft defines how it **rebases**, **conflicts**, **expires**, **is
shared** and **becomes an action**. `draft(task)` in an edit form; a drag's
`pointer_move` writes the draft, `pointer_up` commits it.

## 5. Reactivity

### 5.1 The contract (to specify before optimizing)

- what is an observable read
- dependency granularity: path, element, key or value
- how conditional dependencies are dropped
- whether derived failures are cached
- equality (fingerprints, which `@derive` already provides)
- write ordering within a turn
- cycle diagnosis
- what a runtime fallback may change (cost only)
- reconciling external mutation of the DOM / platform (§11.5)

### 5.2 Exact patches — the optimized case
1. Each cell has an identity and a policy.
2. Each view fn is summarized: "arg 0 `.title` → text hole 3".
3. At call sites summaries compose: state path → derived fns → holes.
4. A write is a PATH (value semantics), so a PROVEN summary lowers it to
   patching exactly the holes it reaches. Conditionals, filtered/reordered
   lists and cross-node relationships (labels, layout) fall back to
   reconciling the affected subtree.
5. `tasks.push(t)` compiles to an insert op; the verb is known.

- Components need no RUNTIME object. Provenance survives inlining through
  the `OriginChain` side table on semantic nodes, dependency holes and patch
  ops: inlining COMPOSES chains. Dynamic instances add their semantic
  identity beside the origin, never in place of it (§3).
- Keyed selector: `t.id == selected` per keyed row → 2 rows patch, not 10k.
- Identical reads on a page share one subscription and one cache entry.
- Same algebra as the compiler's memo kernel and `@std/relation`'s `@query`
  (per-run read/write frames, `std-relation/src/db.av`) — one incremental
  substrate, where MEASUREMENT proves it works.
- Runtime tracking (reads through a fn value, `dyn`, a runtime key) is a
  PERFORMANCE fallback. The program behaves identically when the compiler
  learns a more precise summary. `explain` lists fallback sites.
- Derived fns: pure derived reads are ELIGIBLE for dependency-tracked
  caching under explicit cache semantics (equality, error, lifetime).
- Divergence: FULL_SPEC 29.3's runtime `Signal<T>` is the fallback, not the
  default.

### 5.3 Crossing components

| Need | How |
|---|---|
| parent → child | arguments |
| child → parent | a `mut` seat (path writes), a `State<T>` seat (whole writes), an action, or a code slot (`on pick(d) { }`) |
| a subtree shares | `provide x: T = …` above, `env T` below; missing provider = compile error; env carries ACTIONS (`dismiss`, `open_url`, `refresh`) |
| far apart | top-level `state … at <profile>` |
| shared truth | both read it |
| child → ancestor | preferences (§6.5) |

- `State<T>` seat: a cell; reads as `T`, `n = v` sets it. Needed because a
  `mut` seat is never assigned whole (F3005); consistent with "an identity is
  a Cell". → sugar backlog.
- A derived value passed to a `State` seat is refused ("has no place to
  write — pass the state it reads").
- A `provide` reached through dynamic composition: runtime lookup (listed).

```avra
state cart: Cart = Cart {} at .tab
fn cart_total() -> Money { cart.lines.sum(it.price * it.qty) }

view header() { row { logo()  spacer  badge "${cart.lines.length} · ${cart_total()}" } }

view stepper(n: State<int>) {
    row {
        button "−" { on click { n = n - 1 } }
        text "${n}"
        button "+" { on click { n = n + 1 } }
    }
}
```

### 5.4 Laws of reactivity
- Render and derived fns are pure: no writes.
- Effects (`on change(x) { }`) may write; a write-graph cycle is refused,
  named.
- A list binding that survives a pause is keyed by identity
  (`tasks[id: t.id]`), never by index.
- A value read before a pause and written back after it: warned (lost
  update).
- A paused handler is cancelled when its view's scope ends.

## 6. Time and identity

### 6.1 Event turns

A handler is NOT one atomic block. The compiler knows every pause point and
PRINTS THE CUTS. Segment-commit is the reference default:

- a SEGMENT begins at dispatch or resumption
- it ends at the first pause, return, or uncaught failure
- its local writes commit atomically at that boundary (one patch)
- resumption starts a new segment with a NEW read frame
- failure or cancellation never rolls back a committed segment (only a
  compensating write undoes it)
- an action has its own atomic commit boundary, independent of the client's
  segments
- one intent across pauses = a draft carrying its base, then one action

So "set pending; call; show result" is responsive by construction: the
pending write commits at the pause.

- Warned: a pre-pause read used after resumption.
- Refused: syntax implying rollback across a boundary that cannot roll
  back.

```
$ avra explain handler delete_button.click
segment 1   reads board.name · writes (none)
pause       ask(confirm(…))            gesture: consumed here
segment 2   action delete_board(board) · destructive · safeguard: confirmation ✓
pause       receipt
segment 3   navigates to /boards
```

- `MayPause` is an inferred, inspectable fact on every fn, even though no
  `async` is written. Gesture validity, cancellation, reentrancy, lost
  updates and ordering all read it.

### 6.2 Identity

Identities that often DIFFER: view state · DOM node · animation · task
lifetime. Each is inspectable in the dev identity overlay.

- Default identity PATH: owner identity + call-site ROLE + item identity
  (explicit `id:` first, else a statically known model identity). The model
  distinguishes siblings; it never erases the role or the owner path.
- One visible default: a model change RESETS the state owned by that role.
- Both RESET and PRESERVE can be right: `/product/1 → /product/2` resetting
  `qty` is right if `qty` is page-local, wrong if it is really a cart draft
  (then it belongs in a draft at `.tab`, not `.view`).
- Two presentations of one model (a list card and a detail pane) do NOT
  share view state: call sites are roles. Shared domain truth is shared by
  observation; shared PRESENTATION state is declared (a provided cell or a
  draft), never caused by an identity coincidence.
- The inspector prints every component of the identity path.
- A stateful or reorderable list child needs a key unless a model identity
  is statically available (refused otherwise).
- Hot reload: identity is by source anchor, not position, so inserting a
  call site does not reset its neighbours.
- Plain-data arguments: identity by call site only, linted when the view is
  stateful.

### 6.3 `task for x { }` replaces `useEffect`
- Async work tied to a view's life. Restarts when `x` changes, cancelled on
  leave. No dependency array.

### 6.4 `animate(.spring) { write }`
- The transaction carries its animation. Keyed moves → FLIP. Reduced motion
  wins.

### 6.5 Preferences — values flow up
- `title`, `toolbar`, `breadcrumb` deep in a page are collected by the
  nearest ancestor asking.

### 6.6 The imperative as state
- focus: `state focus: Field?`; setting it moves focus, tabbing writes it
- navigation: a typed stack `at .url`
- sheets: shown while an optional is present
- scroll position: bindable
- refs only for things with no state form (`video.play()`, canvas contexts)
- These are JOINTLY OWNED with the browser (§11.5).

### 6.7 Flows are fns that pause
```avra
on click { if ask(confirm("Delete ${b.name}?")) { delete_board(b) } }
```

### 6.8 Hooks are types
```avra
type Pager = { page: int = 1, size: int = 20 }
impl Pager {
    fn offset() -> int { (self.page - 1) * self.size }
    fn next(mut self) { self.page = self.page + 1 }
}
view orders() { state pager: Pager = Pager {} at .url }
```
- Reusable stateful logic = a record + methods under a profile. Sources:
  `now(every: mins(1))`, `online`, `viewport` (client-only),
  `query.settled(ms(300))`, `deferred(x)`.

## 7. Actions — the web projection

> Normative home: `2026_09_29_AUTHORITY_AND_RECEIPTS.md` — principals, the action lifecycle, impact,
> safeguards, receipts, effects, mandates, waivers. This section is the
> WEB's projection of that contract, nothing more.

```avra
@action(auth: member_of(p), impact: .routine)
fn add_task(p: Project, title: string) -> Task { … }
```

### 7.1 Presentation before receipts
- Each impact profile's "before receipt" column (AUTHORITY §4) renders as:
  - `speculative` — the next state renders; the semantic node carries
    `speculative` until the receipt (the inspector shows it); no badge
    required for `.routine`
  - `pending` — a pending state with a named receipt it waits for
  - `sending` — for `.external`, after the accepted receipt; the
    "sent/paid/booked" wording only after the external receipt
- Failure reconciles the view and is ANNOUNCED; urgency and politeness are
  declared, never inferred.
- Conflicts render the action's own conflict type (keep mine / take
  theirs / the action's options).
- Refusals: per-field errors, placed by the form (old tree: "pipeable
  straight to the UI").

### 7.2 Invocation-site discharge
- Every button, form, menu item and shortcut that invokes an action is an
  INVOCATION SITE and discharges that action's safeguard there
  (AUTHORITY §5): confirmation via `ask`, a real undo affordance, trash,
  re-authentication, a typed phrase.
- An undo toast discharges only when the action's recovery is real.
- The gallery generates each site's traces: accidental activation,
  keyboard activation, repeated/bulk operation, cancellation, recovery.

### 7.3 One wire protocol, progressively enhanced

- The plain `<form>` POST and the enhanced client are PROJECTIONS of one
  protocol: CSRF, redirect-after-post, duplicate submission (idempotency
  id), uploads, validation response, method semantics.
- A receipt is representable as HTML, a DOM patch, or typed data — same
  meaning.
- Refusals: per-field errors, placed by the form (old tree: "pipeable
  straight to the UI").

### 7.4 Offline, skew, uploads
- Offline: actions queue with base version + intent; on reconnect: commit,
  typed conflict, or refusal (revoked). UI: "3 changes waiting".
- Version skew: "growth crosses, moving refuses" applied to actions; the
  server keeps old shapes or forces reload.
- Uploads are streams; an action references the blob.

## 8. Placement — a constrained plan

### 8.1 The plan

| Input | Examples |
|---|---|
| hard constraints | reach, visibility, supported target, correctness, budget |
| declared priorities | latency, bytes, offline, server cost, freshness |
| observed inputs | network/CPU/device distributions, data size, cache hit rate |

- The answer carries UNCERTAINTY, never a fabricated exact number.
- **Stability:** a compiler upgrade does not silently move work; a plan
  change is a reviewable plan diff.
- **The plan is an artifact:** machine-readable, diffable, reproducible
  from compiler version + program + declared/observed inputs.
- Pin/override at every meaningful boundary (`on .server`, `on .client`).

| View reads | Default candidate |
|---|---|
| consts only | HTML at build (const settlement) |
| request data, no client state | server HTML, 0 JS |
| client state | server HTML → resumes; that island only |
| models | live query; server pushes on commit |

### 8.2 Refusal shows the frontier

```text
client filter   refuses disclosure budget (estimated 80 MB)
server filter   fits disclosure; misses 50 ms input budget at p95
indexed search  fits both; requires a server index and pending UI
```

### 8.3 Queries
- Independent reads start together; keyed fan-out is batched; every
  remaining sequential data dependency is visible in `explain` and charged
  to latency. Avoidable N+1 is diagnosed.
- Link hover prefetches the target's independent reads.
- Streaming SSR on fibers; slow queries stream out of order.

### 8.4 Caching — a privacy + freshness algebra

The most permissive policy consistent with declared constraints, from:
- disclosure class and principal dependence
- query/version dependencies
- request variance (locale, negotiation, experiments)
- freshness requirement, staleness permission
- invalidation reach
- legal/geographic storage constraints

- Relation-write invalidation is the safe COARSE fallback. Predicate-indexed
  selective purge at scale is RESEARCH: measure fan-out, churn,
  backpressure, reconnect storms.

### 8.5 Dev mode
- Every view runs server-side through the EVALUATOR, streaming DOM patches:
  instant reload.
- It WILL differ from production (scheduling, browser APIs, serialization,
  traps, timing, layout, races). "eval == native" covers pure Avra
  semantics only. The same interaction traces run against both modes
  continuously; the receipt names which equivalence classes were checked.

## 10. Semantic interaction and accessibility

### 10.1 Meaning below rendering
- The root is an INTERACTION tree, realized as native HTML controls,
  platform controls, or canvas + an operational semantic peer.
- A button is not a rectangle with `on click`; a text field is not text +
  a string. Contracts: keyboard, focus, accessible name, form participation,
  autofill, validation, selection, composition, history, disabled/read-only,
  platform convention.
- The correct native control is the EASIEST primitive; a generic clickable
  surface is visibly expensive (refused without a full contract).

### 10.2 Accessibility is a subsystem

Contracts for:
- name, role, value, state; visible label, label-in-name
- landmarks, headings, regions, reading order
- form grouping, instructions, errors, status messages
- keyboard operation, focus order, focus visibility, no traps
- focus restoration across navigation, layers, async replacement
- pointer cancellation, alternatives to drag and multi-pointer gestures
- zoom, reflow, text spacing, orientation, reduced motion
- forced colors / high contrast
- timeouts, interruptions, re-authentication
- captions, transcripts, alternatives for non-text content
- locale, bidi, language-of-parts, pluralization
- operational equivalence for canvas/GPU

- The browser computes the real a11y tree (DOM + CSS + ARIA + runtime); Avra's
  semantic model is an INPUT and a TEST ORACLE.
- Static: refuse the provably wrong · warn the suspicious · generate test
  obligations for what needs runtime layout · maintain a real
  browser/assistive-technology corpus.
- Interactive canvas: the peer exposes equivalent objects, navigation,
  commands, values, selection and updates — or the interaction is refused
  for an accessible conformance target.
- Conformance PROFILES (`web-aa`, `touch-comfortable`, platform) select
  thresholds.

## 11. Rendering and runtime

### 11.1 Renderers and structure
- Per node: `dom` (default) · `canvas` / `gpu` (draw fn per frame, still
  reactive, + semantic peer) · `foreign` (the reconciler never enters).
- `layer`: modals, popovers, toasts, tooltips → the top layer (`<dialog>`,
  Popover API, CSS anchor positioning). Context flows in.
- `?` in a view → nearest `failed { }`. Pending/empty/failed are handled or
  take the theme default (listed).
- `lazy for`: virtualized long lists.

### 11.2 Output
- Semantic HTML first; atomic CSS; per-route split; a static page ships 0
  bytes of script.
- Budgets are laws per page (`budget { js: 30 KB }`).
- Wording for P14: no user-selected application framework; ONE
  compiler-owned, inspectable runtime substrate, carried only as reached
  (the runtime library law).

### 11.3 Code generation strategies
- WASM reaches the DOM through the JS host boundary. The DOM applier's size
  is a BUDGET HYPOTHESIS; total cost includes loader, ABI, string
  marshaling, event delegation, scheduling, serialization, error recovery,
  polyfills. Measure it.
- Two strategies compete per island: tiny JS fragments (a restricted
  fragment, like BEND's kernel fragment) and WASM for substantial logic.
  Semantics do not care which wins.
- Fibers in the browser: generated state machines at pause points
  (required for broad support, deterministic code size, cancellation,
  debugging, and a differential oracle); JSPI as an optional backend.
  JSPI ships in Chrome 137, Firefox 139 (v8.dev/blog/jspi) and Safari 27.0,
  2026-09-17 (webkit.org/blog/18325) — both pages read 2026-09-29. Shipped
  in all three engines is NOT Baseline Widely Available; the support floor
  (§11.7) decides.

### 11.4 Resumability — a serialization constitution
Rules for:
- which cells, dependencies, closures and handler captures serialize
- snapshot schema/version migration
- secret and capability redaction
- object and view identity across resume
- XSS-safe embedding + CSP
- snapshot size budgets
- stale server data between render and first event
- handler bundle / WASM module mismatch
- recovery when resume fails

> "Views never re-run on load" is an optimization target. **The page is
> correct and operable when the snapshot is absent, stale or rejected** is
> the requirement.

### 11.5 The browser co-owns state
Per property, one of:
- authored / declarative
- browser-owned, observed (selection, composition, autofill, scroll,
  spellcheck, `<details>`/`<dialog>` open, media)
- jointly controlled, with a sync rule (focus, value, history)
- foreign / opaque

The reconciler is never assumed the sole writer — from the first `<input>`,
through IME and rich text. Assistive technologies and extensions also act.

### 11.6 Failure and lifecycle
- A WASM trap terminates its instance. Traps are CONTAINED where instance and
  checkpoint boundaries make recovery possible; define the isolation model
  before promising more.
- Service worker: update and rollback, old/new workers coexisting with open
  pages, offline version skew, cache retention, action compatibility,
  poisoned-cache recovery, interception startup cost.
- BFCache: exploited and tested; nothing Avra generates disables it
  (`unload`), and a BFCache return is not modelled as a fresh resume.
- Threads: `parallel { }` → Worker pool; `SharedArrayBuffer` needs COOP/COEP,
  which break non-opted-in embeds. The trade is shown.
- Debug: DWARF in WASM; one trace id client → server.

### 11.7 Support floor and enhancement frontier

- The browser baseline is a VERSIONED INPUT to the placement plan.
- **Semantic floor** (DECIDED by the owner, 2026-09-29): Baseline
  Widely Available, RESOLVED to a dated Web Features data version pinned in
  the build lock. An unpinned label moves over time and makes old builds
  irreproducible. A project may declare an explicit browser/version matrix
  instead.
- **Enhancement frontier:** a newer or partially available feature may be
  used when feature detection is sound AND a named fallback preserves
  meaning, accessibility and the declared budget. `explain` prints native
  path, fallback, affected browsers and cost.
- No equivalent fallback → the feature RAISES the semantic floor, which is a
  plan diff.

## 12. Styling

- **No AUTHOR-FACING specificity.** Component styles are typed values with
  deterministic precedence; the web projection uses cascade layers + atomic
  rules. User and browser accessibility modes (user styles, forced colors,
  zoom) stay AUTHORITATIVE.
- **Portability ≠ identical UI.** Shared: intent, state machines, data,
  actions, semantic roles, tokens, broad layout constraints. Per target:
  realization and explicit adaptation. `on .web` is sometimes the right
  product design, not an escape. `explain` shows portable / adapted /
  missing per view.
- **Model:** SwiftUI-style modifiers + environment.

```avra
theme app { tokens: tokens(embed("design/tokens.json")) }   // DTCG/Figma, typed at build

view task_card(t: Task) {
    row {
        gap: .s
        pad: .m
        fill: .surface_raised
        radius: .m
        pressed { fill: .surface_sunk }
        text t.title { font: .body, color: if t.done { .muted } else { .text } }
        spacer
        on .web { hover { fill: .surface_hover } }
    }
}
```

- Tokens are generated data (DTCG JSON / Figma variables → a typed `Theme`).
  Semantic roles, never hex.
- Modes (light, dark, high-contrast) are values of one type; each fills every
  role or is refused.
- Contrast: static token pairs are PROVED; images, alpha, gradients,
  animation and runtime content generate runtime/test OBLIGATIONS. Runtime
  (white-label) themes are checked at load.
- Style = the node's settings (the component block's `key: value`).
  Reusable: `let card = Style { … }`. Environment flows down explicitly.
- Layout: container responsiveness by default; viewport, input mode,
  preferences, safe areas and window segments remain legitimate inputs.
- Web output: atomic classes; tokens as CSS variables (mode switch = 0 JS);
  dynamic values via a CSS-variable patch op; View Transitions; FLIP.
- Typed CSS (generated from MDN/webref) covers PROPERTIES, not layout
  interactions (stacking contexts, containing blocks, overflow, intrinsic
  sizing, support, visual outcome) — those need layout contracts,
  diagnostics and browser tests.
- Laws (defaults, with explicit exits):
  - `leading`/`trailing` by default; `physical` direction for diagrams,
    coordinate systems, physical controls
  - nothing essential only on hover
  - target size per profile: `web-aa` = 24×24 CSS px with WCAG 2.2's
    spacing exceptions; `touch-comfortable` = 44×44
  - raw colour needs an explicit colour space and a semantic/a11y treatment
    (user content, data viz, brand imports, science) — not a shame mark
- Escape tiers: `on .web { css { … } }` · `on .ios { … }` · `class: "…"`.
- Embeddable widget: shadow root + reset.

## 13. Browser APIs

- All machine-described in WebIDL (w3c/webref): GENERATE the bindings (the
  `rt_sigs()` pattern). `.d.ts` → `extern js` the same way.

| Layer | Is | Example |
|---|---|---|
| L0 | generated from WebIDL, typed; a Promise is a pause point | `@std.web.raw.navigator.clipboard` |
| L1 | designed packages, typed errors | `@std/clipboard` → `Result<_, PermissionDenied>` |
| L2 | components for lifecycle APIs | `visible { on enter { } }`, `hotkey "cmd+k" { }`, `drop files { }` |

- No `async`/`await` written; `MayPause` still inferred and inspectable
  (§6.1).
- Permissions are reach: headers + manifest emitted; undeclared reach
  refused. `explain`: "this app can: camera (on /scan)".
- **Gesture law** (flagship: temporal knowledge no library can reconstruct):
  ```
  error: `clipboard.write` needs the click's gesture, and `share_link` pauses before it (line 3)
  help: compute the link before the click, or `clipboard.write_later(share_link(doc))`
  ```
  `preventDefault` likewise: decided before any pause.
- **Render-read law:**
  ```
  error: `viewport.width` is read while rendering, and the server has no viewport
  help: lay out by container (`when .compact { }`), or read it `on appear` into `state`
  ```
  Mirror: code reaching `Db` or a secret placed in the browser is refused.
- Foreign widgets (Mapbox, Stripe.js, Monaco) mount in `foreign`; JS deps
  ride the manifest as prebuilt ESM with integrity; the compiler is not a
  bundler.
- Workers are a placement (`on .worker { }`). The service worker is
  generated (§11.6).

## 14. Client-heavy apps

Figma, spreadsheets, DAWs, IDEs, games, maps: device-held truth,
canvas/GPU, 60–120 fps, offline, heavy compute. Avra's best case.

- Truth: `.device` or a catalogue `.replicated` type (§4.5).
- Canvas/GPU renderers + an operational semantic peer (§10.2); `on .gpu`
  kernels (BEND §5).
- A drag is a draft; undo/redo from the action history.
- Frame law: a UI-thread handler carries a default `@cost(steps: ms(8))`;
  over → refused, or moved to a Worker if it passes the fork law.
- Compute: `parallel { }` on Workers; incremental derived fns.

```avra
@model(at: .replicated(Sequence<Shape>))     // a proved catalogue type
type Board = { shapes: Sequence<Shape> }

view editor(b: Board) {
    state drag: Draft<Move>? = null
    canvas {
        on frame(g) { for s in b.shapes { g.draw(s) } }
        on pointer_move(p) { drag = drag?.to(p) }
        on pointer_up { move_shapes(drag!) }
        peer: shapes_peer(b)                 // objects, navigation, commands
    }
}
```

      candidate makes an app's incidental policies pollute suggestions. Giving
      only std constants dotted spelling silently creates the special profile
      mechanism under a namespace exception.

      expected-type lookup decide which marked profiles are available;
      app-specific values remain explicitly named unless deliberately
      imported into that profile vocabulary.

      know.
    - **Proposed consensus:** no new profile runtime or value kind. A profile

      - **Claude:** Both corrections accepted — "refused once" was an

### T12. The four starting impact profiles, defined
- **Claude:** Proposed definitions over the impact record (§7.1):

  | Profile | Presentation before receipt | Reversal | External | Safeguard |
  |---|---|---|---|---|
  | `.routine` | shown done | by any later ordinary action | none | none |
  | `.reversible` | shown done + undo affordance | compensating action within a window | none | undo |
  | `.destructive` | pending | per safeguard | none | required (§7.1) |
  | `.external` | "sending", never "done" | declared compensation, may be lossy | commits to another authority | declared |

  The open question: is `.routine` vs `.reversible` a real distinction? I
  keep them apart — a toggle needs no undo UI, an archive does — but the
  line is "does the user need to be TOLD they can undo it", which is
  product judgment. Merge them, or keep both?
  - **Reviewer:** Keep both. The distinction is a user-facing GUARANTEE, not
    whether a programmer can imagine a later inverse action. `.routine`
    promises no recovery surface; `.reversible` promises a declared inverse
    or compensating action, a real window in which it works, and an undo
    affordance. That is meaningful product judgment and exactly why `impact:`
    is required.
    - Revise `.routine`'s wording. “Shown done” overstates an uncommitted fact,
      and “by any later ordinary action” is not reversal. Use: “speculative
      next state may render; no recovery promised; failure reconciles and is
      announced.” The UI need not draw a pending badge for a checkbox, but
      the semantic/inspector state remains `speculative` until the receipt.
    - `.reversible`: “speculative next state may render with an undo
      obligation; recovery is a declared compensating action valid under a
      stated window/precondition.” Compensation records a new fact; it does
      not erase history.
    - `.destructive` is a conservative base: no completed presentation before
      its authoritative receipt; recovery mechanism must be named; every
      invocation must discharge its commitment safeguard. A trash operation
      can override presentation when its real recovery permits that.
    - `.external` must distinguish the SERVER receipt (“durable work accepted”)
      from the EXTERNAL receipt (“other authority committed”). “Sending” may
      appear after the former; “sent/paid/booked” only after the receipt whose
      meaning declares that fact. Compensation and consequence remain explicit
      obligations because external operations vary too much for a truthful
      default.
    - This exposes a useful two-level rule: an action declares its recovery
      mechanism and minimum safeguard; each invocation (button, CLI, agent)
      discharges the context-dependent safeguard. Confirmation is not proved
      merely because some page somewhere wraps the action in `ask`.
    - **Proposed consensus:** retain all four as conservative ergonomic
      profiles, not exhaustive categories. Keep `.routine` separate from
      `.reversible`; change “shown done” to “speculative next state”; change
      `.routine` reversal to “none promised”; model receipt meaning explicitly,
      especially for `.external`.
      - **Claude:** Agreed; "shown done" was the same impersonation the
        speculation law forbids. The two-level rule (action declares,
        invocation discharges) is the most useful thing in this thread.
      - **Resolved:** §7.1 table rewritten; receipt meaning + two-level

### T14. Agent approval derives from impact
- **Claude:** §9.3 says agent tools come from actions, with `approval`
  from auth. The impact record is the better source: an agent calling a
  `.destructive` or `.external` action needs approval by default, a
  `.routine` one does not, and a `with { agent: .unattended }` override is
  a waivable choice (T13's mandate). One declaration then governs the
  human's UI safeguard AND the agent's approval — no second list to drift.
  Agree?
  - **Reviewer:** Agree with one shared SAFEGUARD OBLIGATION; disagree that
    impact alone grants or fully determines agent approval, and disagree with
    `with { agent: .unattended }` as an effective source-level override.
    - `auth` answers whether the principal MAY request the action. `impact`
      states consequences, receipt meaning, recovery and the MINIMUM safeguard.
      A mandate states what this particular agent may do unattended, under
      which predicates, budgets and time window. Live state can still make the
      invocation refuse. Approval is derived from all three, not a second
      hand-kept list:
      `required safeguard = impact minimum + live context − mandate discharge`.
    - Human confirmation and agent approval are different DISCHARGES of the
      same obligation. A button may discharge it with a confirmation or
      re-authentication; an agent may discharge it with a signed mandate,
      remaining budget and perhaps a second approver. They stay linked without
      pretending the interaction is identical.
    - Impact supplies conservative defaults: `.routine` normally creates no
      approval obligation; `.destructive` does; `.external` remains required
      until its consequence/compensation profile proves a narrower rule. But
      action parameters matter: refunding $5 and $50,000 are the same action
      with different approval predicates. Auth sensitivity and disclosure may
      also require approval even when mutation impact is routine.
    - Source may declare `automation: .eligible` or request a narrower
      safeguard; it cannot authorize `unattended`. Put the actual grant in the
      signed mandate, for example “support agent may call `refund` unattended
      when amount ≤ $50 and daily total ≤ $500.” Weakening the action's minimum
      safeguard is a separately named waiver in that mandate, never an
      ordinary `with` the agent can self-approve.
    - The receipt records action impact version, live authorization witness,
      mandate id/budget consumption, approval or safeguard discharge, inputs
      relevant to the predicate, and authoritative/external result.
    - **Proposed consensus:** one safeguard model, multiple context-specific
      discharges. Derive agent approval from impact + live context + signed
      mandate. Remove `agent: .unattended` as an authorizing source override;
      retain only source-declared automation eligibility. The mandate, outside
      the author's write power, grants unattended execution within bounds.
      - **Claude:** Conceded: `with { agent: .unattended }` was the exact
