# Identity and permissions — the proposal

Status: PROPOSAL, for the lead's ruling (§8). Nothing here is built. It builds ON
docs/2026_09_29_AUTHORITY_AND_RECEIPTS.md (normative, unbuilt), never beside it: that doc
owns principals, capabilities, live witnesses and the commit-time re-check, and says it does
not own "how a principal authenticates". This doc supplies that mechanism (§1) and the one
consumer sync needs now, the `share` (§2), and maps every piece back onto AUTHORITY's terms.
Sync (docs/2026_11_27_SYNC.md, branch `avra-lane-ui-sync-proposal`) names `.shared(board)`,
"everyone who can read `board`": §2 is what "can read" means. Probes are quoted with their
base (§3: the `gate-builder` compiler built from `program` at b2d72c7, Linux x86-64).

What stands under this design — built, except the two rows marked designed:

| Piece | Where | What it already holds |
|---|---|---|
| signed cookies, stateless sessions | packages/std-http_session | HMAC-SHA256 over name and value, constant-time tag compare, expiry under the tag |
| credential headers | packages/std-http/src/auth.av | `bearer` (RFC 6750 alphabet), `basic` (RFC 7617) |
| the impact record, local mandates | packages/std-action | `@action` + `@impact` derive; `Mandate { issuer, subject, actions, expires_ms, budget, endorsed }`, `covers` |
| an access scope pushed into SQL | packages/std-db/src/scope.av, std-crud `Access`/`belongs_to` | "a row outside the scope is a row that is not there (404)"; "nothing is ever filtered in memory" |
| `ambient` per-request context, designed | docs/2026_10_04_SHARING_MODEL.md §4 | `layer auth { … }` supplies `ambient caller: Caller`; a policy is a query over it |
| a policy is a query, designed | docs/2026_09_24_ORM.md §4a | `Card.readable(who: Principal) -> Query<Card>` |

std-crud's `belongs_to("owner", "x-user", …)` trusts a HEADER to name the caller: it is the
scope half with no identity half. This proposal is the identity half and the generalisation
of the scope from one column to a share's policy.

## 1. Identity

### 1.1 Principals

A principal is WHO acts. AUTHORITY §1: an action receives an authenticated principal plus
attenuated capabilities.

**DECIDED (owner, via the UI lead, 2026-11-28): services and agents are principals like users.
A service gains access to a share by a membership row (a role), granted and revoked at run
time, never by syntax that ties a service declaration to a share.** The design below follows
from that, for agents as for services:

```avra
export enum PrincipalKind { User, Service, Agent, Anonymous }

/// Who acts: one id space for every kind, minted by the server as a row.
export type Principal = { id: int, kind: PrincipalKind }
```

- **One shape for every kind.** A user, a service (a worker, an importer, a webhook receiver)
  and an agent are each a `Principal` row with a server-minted id. Each proves itself through a
  door (§1.2) and gets a session or token (§1.3). Each reaches a share ONLY through a member row
  (§2.1), granted by the share's `invite` action and ended by `remove_member` at run time, like
  any member's. There is no second path.
- **Nothing in source ties a principal to a share.** No manifest row, annotation argument,
  const or policy names a service or an agent as a member. A deploy that needs a worker on a
  board runs `invite(board, worker, .Editor)` once, as an action with a receipt. It is not a
  build. The mint law of security_laws Part II (a manifest mints a TOOL) is about code a program
  runs. A principal is data the program judges, so the mint law does not apply to principals.
- **A seat carries no kind.** A policy sees `m.who` and `m.role`, never `m.kind`, so a service
  that is an `Editor` is an editor. A product that wants "agents may comment but never delete"
  declares that as a ROLE (`.AgentCommenter`), and every policy must then say what it may do (§2.1). A
  kind test hidden inside a policy would be a second permission system beside the roles.
- **`Anonymous` is the one principal without rows.** Its id is 0 and it never holds a member
  row; it reaches a share only through the share's `link` role (§4.6). So "no session" is never
  a null that a policy forgets to test.
- **An agent acting for a user is still a member in its own right.** It has its own row, its own
  role and its own receipts, so its work is never booked as the user's. A std-action `Mandate`
  does NOT grant share access. It governs what AUTHORITY §11 gives it: which actions the agent
  may invoke UNATTENDED, its budget, its window, and the safeguards it discharges. So access is
  the row, and unattended power is the mandate. Revoking either refuses the next commit.
- A principal id is an `int`. Knowing one grants nothing: authority is the session plus the row,
  never the id.

### 1.2 Doors: how a principal is proven

Each door ends the same way: a `Principal`, then a session (§1.3). The door is mechanism;
nothing past it knows which door was used, except the receipt (AUTHORITY §6), which records it.

| Door | Mechanism | Laws |
|---|---|---|
| password | argon2id (RFC 9106), stored as a PHC string `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>` (OWASP's floor) | 16-octet random salt per hash; parameters RE-HASHED upward at the next good login; an unknown user costs one dummy hash, so timing never says an account exists; attempts limited per account AND per address |
| passkey | WebAuthn: a credential row `{ cred_id, cose_key, sign_count, principal }` | challenge single-use and bound to the pending session; `rpIdHash`, origin and the UV flag checked; ES256 (mbedtls, vendored, has P-256) and EdDSA |
| OIDC: Google, Apple | authorization code + PKCE, `state`, `nonce` | the identity is `(iss, sub)`, NEVER the email (Apple relays mail; emails change hands); an OIDC identity LINKS to an existing principal only from a signed-in session, never by matching email (that is account takeover) |

- **argon2 is not in the tree.** `openssl kdf … ARGON2ID` on this machine answers
  `Invalid KDF name ARGON2ID` (OpenSSL 3.0.13; argon2 arrived in 3.2), and the vendored mbedtls
  carries PBKDF2, not argon2. The reference implementation (CC0) is vendored C under a new
  `@std/password`, one `extern fn` row, its cost pinned by a census row (§7).
- **The legacy anti-example** (bridge_inbox/legacy/std-auth.lib.rs): `forge_auth_hash_password`
  is one unsalted SHA-256 (`hasher.update(pw.as_bytes())`, hex) — a GPU tries billions a
  second; the default secret is the literal `"forge-default-secret"`; the role rides INSIDE the
  token (`Claims { sub, role, exp }`), so a demoted user keeps the old role until expiry.

### 1.3 Sessions and tokens: opaque, live, revocable

**Ruling asked (§8.1): signed sessions and opaque tokens; a JWT only at the OIDC door.** The
reason is AUTHORITY's own law, not taste: "queued/offline requests carry INTENT, never durable
authority. Revocation and expiry are ordinary refusals." A JWT is authority the server wrote
down and handed away; until it expires, revoking it needs a deny list, which is a session table
with worse ergonomics. A role claim inside it is a cached capability, the exact staleness §4.1
has to judge. So:

- **A session is a server row**: `Session { id, principal, door, created, seen, idle_until,
  until, device }`, a `@model` like any other. The cookie carries ONLY its id, signed by the
  built `Signer` (`std-http_session`): a forged or truncated id is refused by one HMAC before any
  read, and the MAC over the name keeps a value from moving between cookies. Cookie:
  `__Host-session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` (the built default name).
- **The built `Session` type stays** (data and expiry under the tag, no row): it is right for
  what needs no revocation (a CSRF double-submit value, a sign-in-flow state, a short OIDC
  `state`). It is wrong for a principal, because nothing can end it early but a key rotation
  that ends every session.
- **A token is 256 random bits**, base64url, with a visible prefix (`avt_`) so secret scanners
  find it. The server stores `sha256(token)`, never the token: a leaked table holds nothing that
  signs in. Lookup is by that hash, so no comparison loop needs to be constant-time.
- **Native apps** get a device token after any door, kept in the Keychain
  (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, so it is neither backed up nor synced to
  another device) or the Android Keystore, and sent as `authorization: Bearer` — std-http's
  `bearer` already refuses a token outside RFC 6750's alphabet. NO refresh-token pair: a refresh
  pair exists to keep a self-contained access token short; an opaque token is checked live on
  every request, so it buys nothing. Idle expiry slides (90 days, a setting); a hard ceiling
  does not.
- **Services and agents use the same token.** `create_principal(kind: .Service, name)` and
  `issue_token(p)` are actions run at run time by a principal whose seat admits it. Each has an
  impact and a receipt, and the token is shown once. A deploy hands the token to the worker as a
  secret (an environment value), and the worker sends it as `Bearer`. Rotation is
  `issue_token` then `revoke_token`, with both tokens live in between. A service has no password
  and no passkey; a token is its only door. A token can be bound to a source address or an mTLS
  client certificate as a narrowing; the binding never widens what the token can do.
- **JWT at the door, and only there.** An OIDC ID token is a JWT we VERIFY and then discard:
  signature against the issuer's JWKS, the algorithm taken from OUR per-issuer list and never
  from the token's header (`alg: none` and the RS/HS confusion are the classic holes), `iss`,
  `aud` (our client id), `exp`, `nonce`. Apple's client secret is the one JWT we SIGN (ES256,
  short-lived). Neither is ever our session.
- **Revocation** is deleting rows. One device: its row. "Sign out everywhere": every row of the
  principal. A password change or a passkey removal ends every other session. An open sync
  stream (SSE) is the session's too: the server ends it with a `Refusal.Ended` frame (§5) when
  its row goes — "a stream ends because its peer is gone, never because a write failed"
  (CLAUDE.md), so the server must END it rather than wait for a write to fail.
- **CSRF**: `SameSite=Lax` plus an action door that takes `POST` only and checks `Origin`; the
  web projection of `@action` already owns the form doors (std-action route.av).

Cost: one HMAC and one primary-key read per request (§7).

## 2. The `share`

A `share` is a declared unit of data plus its members, roles and POLICY (the owner's name, the
owner's ruling on §8: yes to all five). It is the unit AUTHORITY's `member_of(p)` names, the
unit sync's `.shared(x)` replicates, and the unit a refusal may speak about.

### 2.0 The name: `policy`

v1 called the per-row decision a "rule" and its trait `Guarded`. Both are generic: "rule" is
already the tree's word for an idiom declaration (`avra check`'s `rule`, CLAUDE.md), and a
guard is something else here. The candidates, checked against prior art and against this tree
(counts are declarations under `packages/`, at b2d72c7):

| Candidate | Prior art | In this tree today | Reads as | Verdict |
|---|---|---|---|---|
| **policy** | Pundit (`PostPolicy#update?`), Laravel (`PostPolicy::update`), Oso/Polar (`allow(actor, action, resource)` in a policy file), Postgres RLS (`CREATE POLICY`) | NO type or fn of that name in `packages/` (one test fixture's local `type Policy`). Two design docs already use it in this exact sense: ORM §4a, "A policy says which rows a principal may read or write", and AUTHORITY §1, "the receipt names the policy/witness that authorized it" | one value per row type, deciding each verb for each role | **recommended** |
| access | Rails' `access_control`; generic | std-crud's BUILT `Access` type (`belongs_to`) and `fn access` rows: a second meaning beside the one this design generalises | a property of the caller, not of the row | collides |
| permit | Rails strong params (`params.permit`), a different meaning | none | a verb ("permit this"), and it names one decision well | kept for the ROW of a policy table: a `Permit` is one role's four decisions |
| ability | CASL (`defineAbility`, `can`) | none | what a PRINCIPAL can do: the subject side, where this design deliberately looks from the row | inverts the frame |
| grant | Postgres `GRANT`, OAuth grants | `fn grant`/`granted` in std-http (CORS grants by origin) | the ACT of giving a role: `invite` already is this, and a mandate is issued with `granted_ms` | names the membership step, not the decision |
| guard | Angular route guards | `std-http/src/guard.av` (the stock CORS and header layers), the evaluator's `type Guard`, `contained` guards, 30+ `guard_*` fns | a layer a request passes through | collides heavily |

**Recommend `policy`.** The trait is `Policy<R>`, the annotation that attaches a table is
`@policy(card_policy)`, one row of the table is a `Permit`, a cell is an `Allow`, and a
refusal names the `Verb` that refused. ORM §4a's sentence keeps its meaning exactly: a policy
belongs to the LIBRARY (`@std/share`), never to the compiler. Below, "policy" replaces v1's
"rule" throughout, and `Policy` replaces `Guarded`.

### 2.1 Spelled in today's language: the policy table

The common case is one table, one row per role and one column per verb. Every line is a
construct the compiler parses and types TODAY (§3 quotes the probes): an enum, records, an
`alias`, a `table<Row>` with shorthand variant cells, and field marks. The annotations are a
DERIVE in a new `@std/share` package, the way `@action` is a derive in `@std/action`. The
language grows no keyword.

```avra
use @std.share.{share, policy, Permit, Allow, Seat, Policy}

/// The roles of a board. The policy table holds each one exactly once.
export enum BoardRole { Owner, Editor, Commenter, Viewer }

@share(BoardRole)
type Board = { id: int = 0, name: string, link: BoardRole? = null }

alias BoardPermit = Permit<BoardRole>

const card_policy: List<BoardPermit> = table<BoardPermit> {
    role       | reads | creates | writes | removes
    .Owner     | .Yes  | .Yes    | .Yes   | .Yes
    .Editor    | .Yes  | .Yes    | .Yes   | .Own
    .Commenter | .Yes  | .Own    | .Ask   | .Own
    .Viewer    | .Yes  | .No     | .No    | .No
}

@sync
@policy(card_policy)
type Card = { id: int = 0, @in board: int, @owner author: int, title: string, done: bool = false }

impl Card {
    /// The `.Ask` cells: a commenter edits their own card while it is open.
    fn writes_when(m: Seat<BoardRole>, next: Card) -> bool { self.author == m.who && !self.done }
}
```

The library's half, in `@std/share`:

```avra
/// One cell: every row, no row, the rows the seat's principal owns, or the row type's own method.
export enum Allow { Yes, No, Own, Ask }

/// One role's four decisions: a row of a policy table.
export type Permit<R> = { role: R, reads: Allow, creates: Allow, writes: Allow, removes: Allow }

/// What decides each verb for a row type: generated from a table, or written by hand (§2.2).
export trait Policy<R> {
    fn permit(r: R) -> Permit<R>?
    fn owner() -> int
    fn reads_asked(m: Seat<R>) -> bool
    fn creates_asked(m: Seat<R>) -> bool
    fn writes_asked(m: Seat<R>, next: Self) -> bool
    fn removes_asked(m: Seat<R>) -> bool
}
```

`@policy(card_policy)` generates `impl Policy<BoardRole> for Card`. `permit` looks the role up
in the table, `owner` reads the field marked `@owner`, and each `*_asked` forwards to the row
type's `*_when` method (`writes_asked` calls `self.writes_when(m, next)`). A verb with no `.Ask`
cell forwards to a generated refusal, so the author writes only the `*_when` methods their
`.Ask` cells name, and a column with an `.Ask` cell and no `*_when` method is
`share.ask_unanswered`. The derive is NOT generic: it reads the
table's NAME from its argument and the `@owner` field from the `Type`, and splices both into
code the typer then checks. That matters because a generic derive does not run today
(`policy`'s generator isn't made yet: a generic fn at the generator, §3). The deciding code
(`may_write` and its siblings) is plain generic Avra in the library, which does run today (§3).

The cells mean:

| Cell | `reads` | `creates` | `writes` | `removes` |
|---|---|---|---|---|
| `.Yes` | every row of the share | any new row | any change | any row |
| `.No` | no row | none | none | none |
| `.Own` | rows whose `@owner` is the seat's principal | a new row whose `@owner` is the seat's principal | a row it owns, the owner unchanged | a row it owns |
| `.Ask` | the row type's `reads_asked` | `creates_asked` | `writes_asked` | `removes_asked` |

- **Where roles are declared:** an ordinary enum, named by `@share`. Roles have NO order:
  `r >= .Editor` is refused by the compiler today (§3), and that is the right law, not a gap.
  An ordering is the assumption that "an editor can do everything a commenter can", and that is
  the first thing a product breaks. Each row of the table says what its role may do.
- **Every role exactly once.** This is the one thing the table form does not get for free. A
  table missing `.Viewer` and holding `.Editor` twice checks clean and runs today (§3). It
  fails closed (`find` answers null, so the verb refuses), but silently. Two answers, in order:
  1. **The language ask (sugar backlog): a keyed table, `table<BoardPermit> by role { … }`.**
     It is checked like a `match`: every variant of the key's enum exactly once, a missing one
     `type.match` and a repeat "matched more than once". It parses as nothing today ("expected
     BREAK", §3). It is a general want: `width_rows` is keyed by `word` and wisp's `KEEPERS`
     by `name`, and each relies on nobody writing a key twice.
  2. **Until it lands, the match-of-records spelling of §2.2 is the one checked at compile
     time.** It gets "every role exactly once" from the compiler with no derive at all. The
     derive cannot do it for a plain table: it receives the table's NAME, not its rows (a
     derive taking `List<Permit<R>>` is generic, and refused, §3). For a plain table, `@policy`
     generates a spec case instead, run by `avra test`, that holds the `role` column to
     `type_named("BoardRole")`'s variants (`share.policy_roles`). That is a test-time law, said
     as one, not a compile-time one.
- **What is in a share:** a row type with a field marked `@in` (the share it lives in). One
  share per row, always — a row is never in two shares (§4.2 says what moving is).
- **Ownership is a mark, not a convention.** `@owner author: int` names the column `.Own`
  compares. It is std-crud's `belongs_to("author", …)` raised from a route argument to the
  model: the same column, and the same `Where` in the query (§2.3). A row type with a `.Own`
  cell and no `@owner` field is `share.owner_unmarked`.
- **Membership is relation rows**, generated by `@share` as a `@model`:
  `BoardMember { id, share: int, who: int, role: BoardRole, since: Time, by: int }`, unique on
  `(share, who)`. `who` is a principal id of ANY kind: a user's, a service's and an agent's
  rows are one table, one shape and one set of actions. A member row is data: it syncs, it has
  a version (ORM's `__avra_version__`), and it is written only through the share's own actions
  (§2.4), which a deploy, an admin screen and an agent all reach the same way.
- **A `Seat<R>` is the resolved membership**: `{ who: int, role: R, share: int, version: int,
  permit: Permit<R> }`. It is the kernel's answer to "who is this principal IN this share", and
  the only thing a policy sees of the principal. It has no `kind` field (§1.1). It CARRIES ITS
  PERMIT, resolved once when the seat is: the table lookup costs ~82 ns and the held cell ~7 ns
  per check (§7). A check never looks the role up again.
- **A policy never names a principal.** `m.who` may be compared only with a field of `self` or
  `next` (an ownership column such as `author`), never with a literal or a const. Today
  `.Viewer -> m.who == ingest_service` compiles and runs (`true`, §3). That spelling is exactly
  the static tie between a service and a share that the owner ruled out, so `@share` refuses it
  as `share.principal_named`. The grant belongs in a member row. A table cannot spell the tie
  at all: no cell names a principal.

### 2.2 The method form: the escape hatch, and the whole policy when no table fits

A row type with no `@policy` table writes `impl Policy<R>` itself: a `permit` that answers
`.Ask` for every role and verb, and the four `*_asked` methods as v1's exhaustive matches. The
trait makes each method required (an impl that leaves one out is `type.trait`, §3).

```avra
impl Policy<BoardRole> for Card {
    fn permit(r: BoardRole) -> BoardPermit? { asked(r) }      // every cell .Ask
    fn owner() -> int { self.author }
    fn reads_asked(m: Seat<BoardRole>) -> bool { true }
    fn creates_asked(m: Seat<BoardRole>) -> bool {
        match m.role {
            .Owner or .Editor -> true
            .Commenter or .Viewer -> false
        }
    }
    fn writes_asked(m: Seat<BoardRole>, next: Card) -> bool {
        match m.role {
            .Owner or .Editor -> next.author == self.author
            .Commenter -> self.author == m.who && next.author == self.author && !self.done
            .Viewer -> false
        }
    }
    fn removes_asked(m: Seat<BoardRole>) -> bool {
        match m.role {
            .Owner -> true
            .Editor or .Commenter -> self.author == m.who
            .Viewer -> false
        }
    }
}
```

A middle spelling, between the two, is the table written as an exhaustive match of records. It
is one line per role, and the compiler itself holds every role exactly once:

```avra
fn card_permits(r: BoardRole) -> Permit {
    match r {
        .Owner -> Permit { reads: .Yes, creates: .Yes, writes: .Yes, removes: .Yes },
        .Editor -> Permit { reads: .Yes, creates: .Yes, writes: .Yes, removes: .Own },
        .Commenter -> Permit { reads: .Yes, creates: .Own, writes: .Ask, removes: .Own },
        .Viewer -> Permit { reads: .Yes, creates: .No, writes: .No, removes: .No },
    }
}
```

A missing `.Viewer` arm is ``error[type.match]: `match` on `BoardRole` must handle `.Viewer` ``,
and a second `.Editor` arm is ``error[type.match]: variant `Editor` is matched more than once``
(§3). `fmt` keeps the table's columns aligned and does not align these arms. That is why the
table, with its keyed form owed, is the recommended spelling and this match is its fallback.

When to leave the table: the table says "who, by role" with ownership. A cell becomes `.Ask`
when the decision reads another field (`!self.done`), compares `self` with `next` beyond the
owner (`next.board == self.board`), or depends on a field of the seat. A product that needs
`.Ask` in most cells writes the method form instead. One verb's column of `.Ask` cells is the
usual shape.

The verbs, and where each is asked:

| Verb | Asked | Server | Client |
|---|---|---|---|
| `reads` | which rows a member sees | folded into the query (§2.3) and every sync frame | which rows the replica holds (it holds only what it was sent) |
| `creates` | may this member insert | at commit, on the final row | greys "Add" |
| `writes` | may this member change this row into `next` | at commit, on the final payload | greys a field, a toggle |
| `removes` | may this member delete | at commit | greys "Remove" |

THE PURITY LAW holds for every `*_asked` method, which is where code lives. It reads its seat,
its row and `next`, and nothing else: no database, no clock, no `ambient`, no I/O. That is what
makes ONE definition run in three places with one answer. It runs on the client against the
seat the client holds (its own member row is synced to it), at commit against the seat re-read
fresh, and inside the query (§2.3). The compiler already computes a body's read set
(features/read_set.av, P10): every `state` place it reads, and `Unknown` for what it cannot
name (an applied fn value, an `extern` row). The law is a check over it. A `*_asked` method's
read set is empty, it calls no `extern`, and it takes no `ambient` and no `mut` seat. When it
breaks this, `@share` refuses it as `share.policy_reads_world`. A decision that needs more (a
quota, a time window) is a field on the row or on the seat. Otherwise it is not a policy but an
`@check` the authority arbitrates (SYNC §3). A table cell has no code, so it is pure by
construction.

On the client the call is the library's verb: `button "Remove" { enabled: may_remove(c,
seat(board)) }`. `seat(board)` answers the replica's own last-known seat. The server's answer
can differ only if the membership changed and has not yet arrived, which §4.1 rules on.

### 2.3 What each spelling projects to

Both spellings produce the same `impl Policy<R>`, so every consumer reads one interface. What
changes is how much work each projection takes:

| Projection | Table cell `.Yes` / `.No` / `.Own` | Table cell `.Ask`, or the method form |
|---|---|---|
| **Query fold** (`reads`, per request) | DIRECT. The seat's role picks one row, and the cell is the scope: `.Yes` → no clause, `.No` → no query at all, `.Own` → `Where { column: "author", op: .Eq, value: who }`, std-db's BUILT scope (`scope.av`, `Op.Eq`; std-crud's `belongs_to` is exactly this). §3 prints the SQL. | PARTIAL EVALUATION of `reads_asked` with the seat fixed: each `match m.role` folds to one arm, and what remains is a predicate over the row's fields, which needs std-db's `Op` grown past `Eq` (`&&`, `\|\|`, `!`, `!=`, `<`, `IN`). A `reads_asked` that does not fold is refused at compile time, `share.reads_unprojected`. |
| **Sync frame** | One frame per DISTINCT `reads` cell among the share's roles. When every role's cell is `.Yes`, one frame serves every member. `.Own` cuts one frame per owner. | One frame per distinct folded predicate, never per row. |
| **Client greying** | The table is DATA the client holds, the same `card_policy` const in its binary, and its seat carries its own `Permit`: one field read, and one compare for `.Own`. A whole column can be greyed with no row at all: "Add" is disabled when the role's `creates` is `.No`. | The `*_asked` method runs on the client against the row it shows. |
| **Commit check** | `may_write(row, seat, next)`: one read of the seat's held cell and one compare, on the final payload against the fresh seat. `.Own` also holds the owner fixed (`next.owner() == row.owner()`). | The `*_asked` method runs on the final payload. |
| **`avra explain Card`** (P7) | prints the table itself | prints the method's source and its folded predicate per role |
| **Static ceiling** (ORM phase 7's `Capability`) | `.No` and `.Own` per role and verb are the ceiling, read straight from the table | the fold of `writes_asked` per role |

The consequence for the first slice: a share whose policy is all `.Yes`, `.No` and `.Own` needs
NO partial evaluator and no new `Op`. Its query fold is the scope std-db already builds. The
partial evaluator is owed only for `reads` cells marked `.Ask`, so it can land later without
blocking the board.

- A cell that reads no field of `self` (`.Yes`, `.No`, and any `*_asked` whose read set holds
  no `self` field) folds to a constant per (seat, share), so it costs nothing per row (§7). The
  hoist is the compiler's, and it is a ZERO_COST row to add.

### 2.4 The share's own policy: members

`@share` generates the member actions — `invite`, `set_role`, `remove_member`, `leave`,
`delete_share` — as `@action`s with their impact (`set_role` `.routine`, `remove_member` and
`delete_share` `.destructive`, the latter with `.Trash`). Who may run them is one more policy method on
the SHARE type, in the same shape:

```avra
impl Board {
    fn admits(m: Seat<BoardRole>, role: BoardRole) -> bool {
        match m.role {
            .Owner -> true
            .Editor -> match role { .Owner -> false, .Editor or .Commenter or .Viewer -> true }
            .Commenter or .Viewer -> false
        }
    }
}
```

`admits(m, r)` governs inviting a principal as `r` and setting a role to `r`, for every kind of
principal. Granting a service `Editor` on a board is `invite(board, ingest, .Editor)`, judged by
the inviter's `admits` and recorded with the inviter as `by`. Revoking it is
`remove_member(board, ingest)`, and the service's next commit is refused `NotFound`.

### 2.5 Onto AUTHORITY's terms

| AUTHORITY | Here |
|---|---|
| authenticated principal | `Principal`, from a session row (§1.3) |
| attenuated capability | the `Seat`: a role in one share, resolved from the principal's own member row, whatever its kind. Attenuation is granting a narrower role, never a narrower copy of someone else's seat |
| delegation mandate (§9.1, §11) | unattended POWER, never access: which actions an agent or worker may invoke with no human present, its budget, its window. The seat says WHAT it may touch and the mandate says WHAT IT MAY DO ALONE; both are re-checked at commit |
| live witness | the member row AT ITS VERSION, re-read at commit; the receipt records `(share, member id, version, verb)` |
| authority re-evaluated at commit | the policy runs on the final payload against the fresh seat; the client's answer was a forecast |
| reads filtered by the same model | §2.3: the same `reads` method, folded into the query |
| no existence leaks | §4.7: no seat is `NotFound`, never `Forbidden` |
| queued requests carry intent | §4.1: an offline op is judged at arrival |
| `@action(auth: member_of(p), …)` | `member_of(p)` resolves a seat in `p` or refuses `NotFound`; it is the floor AUTHORITY calls it ("a floor, not a proof"), and std-action's `@action` takes no `auth:` yet — every row the action then touches is still judged by its own policy |
| `Capability<User, [email, name]>` (ORM phase 7) | the fold of `writes` per role says which fields a role can change; that field list IS the static ceiling, derived, never declared twice |

What the probes decide:

- **Spellings.** Booleans are `&&`, `||`, `!`; `or` joins patterns only. A policy method over
  roles is an exhaustive `match` with `or`-runs (`.Owner or .Editor -> …`), never `is` chains.
  For a registry enum `is` is "a catch-all in different clothes" (CLAUDE.md), and a role enum is
  the purest registry there is. "Any member of these roles" is `match` with an `or`-run; "any
  row" is the List method `.any(…)`. No `any` fn or type is proposed.
- **Fail closed is already the compiler's** for a policy method and for the match-of-records
  spelling. A role added to `BoardRole` is `type.match` in every match that does not name it,
  and a verb left out is `type.trait`. Neither is built for this design — both are the language.
- **Two holes `@share` must close**, because the language leaves them open on purpose: `_ ->`
  is only a warning and `rest ->` is silent, so a policy method could still say "every other
  role may". Inside a `Policy` impl both are `share.role_remainder` (an error). A table cannot
  write a remainder at all.
- **The table form's one gap is its keys.** `table<Row>` is real, aligned by `fmt`, and takes
  `.Variant` cells. It holds no key law, so a role written twice or left out is silent. That is
  §2.1's keyed-table ask, and the match-of-records spelling is the compile-time-checked form
  until it lands.
- **The table needs an alias**, because `table<…>` takes a bare name: `alias BoardPermit =
  Permit<BoardRole>`. `@share(BoardRole)` can declare that alias itself.
- **A derive cannot take the table's rows** (a generic generator does not run). So `@policy`
  generates code naming the table, and the deciding logic is generic library code, which runs.
- **One defect found:** `Self` in an impl method's seat checks clean and traps when reached.
  The trait may say `Self`; the impl writes the type (`next: Card`), as §2.2 does. To file with
  its witness when this lands.

## 4. Edge cases, a ruling each

### 4.1 Removed or role-changed while offline — judged at arrival
Every op in the outbox is judged when it ARRIVES, against the seat as it is then (AUTHORITY §1:
intent, never authority; no grace window — a grace window is cached authority with a timer).
An op the current seat refuses is refused, op by op; the rest commit. A refused CONVERGING op is
the one exception to SYNC §3's "never rolls back": the authority answers it with a correction
(a new fact, never an erasure), the replica reverts that field, and the refusal reaches the
write's own `Failed`. NOTHING the user typed is lost: refused ops land in the outbox's dead
letter as the user's draft (std-queue_store's queue already keeps them), readable on the device
and exportable, never resent automatically. A role CHANGE is the same law: what the new role
permits commits, the rest is refused.

### 4.2 Moving a row between shares
A move is one action, `.destructive` in the source share: it needs `removes` in A and `creates`
in B, both judged at commit in ONE transaction, or neither. Members of A see a tombstone and
never where it went; members of B see a creation, with no history from A (A's history was A's).
The `id` is kept (sync identity, so replicas in both shares resolve it), its text sequences are
re-seeded as a snapshot. A replica offline in A that edits the moved row has its ops refused
`NotFound` — honestly, since from A the row is gone.

### 4.3 Nesting and inheritance
A share may name ONE parent share type: `@share(ProjectRole, in: Team)`, with an exhaustive
mapping fn `fn inherited(r: TeamRole) -> ProjectRole?` (null: no access by inheritance). The
graph is the TYPE graph, so it is finite and a cycle is a compile error. Resolution: the direct
member row if there is one, else the parent's seat mapped, else the share's `link` role, else
none. DIRECT OVERRIDES INHERITED (ruling §8.5), so a restricted sub-board is a direct row that
demotes. Depth is the declared nesting (2–3 in practice), each level one indexed read, cached
per request.

### 4.4 Last owner leaves
Refused, at commit: "a share keeps one member `admits` can promote to every role" is an
invariant `@share` generates and the authority arbitrates (SYNC §3's arbitrated line). Voice:
"`Board` keeps one owner — make another member owner before leaving". Account ERASURE, which
cannot be refused, promotes the longest-standing member whose role is next in the share's own
`admits`; a share with no other member is deleted under its trash window.

### 4.5 Share deleted while members are offline
`delete_share` is `.destructive` with `.Trash(30 days)`. Ops arriving for a trashed share are
refused `Gone` (§5): its members knew it existed, so saying so leaks nothing; a non-member
still hears `NotFound`. A replica keeps the trashed share READ-ONLY and marked gone, and its
refused ops are drafts (§4.1). Restore within the window restores the member rows; refused ops
stay drafts. After the window: one tombstone for the share, and a replica wipes its copy at the
next sync.

### 4.6 Public and anonymous read
A share's `link: R?` field is the role an UNNAMED visitor gets. Two forms: `public` (any
principal, `Anonymous` included, gets the seat `link`), and by-link (a 128-bit random token in
the URL, hashed at rest like a device token, resolves to that seat). The seat's `who` for
`Anonymous` is 0 and no row's `author` is 0, so an `.Own` cell never matches a stranger by
accident. An anonymous seat may write only where its policy says so; every anonymous write passes
the rate law. Anonymous reads of one share are identical for every visitor, so they are
cacheable as one response.

### 4.7 Existence leaks in errors and queries
The law: A REFUSAL NAMES ONLY WHAT ITS RECIPIENT CAN READ.
- No seat in the share, or a row the seat cannot `reads`: `NotFound` — the same variant, the
  same words, the same status (404) as a row that never existed. std-crud's `Access` already
  does this (crud_access: "a second caller … finds … none of them (404)").
- `Forbidden` only for a row the seat CAN read (it already knows the row exists).
- `@unique` is SCOPED TO THE SHARE by default: "`slug` taken" across shares would prove a row
  in a share the asker cannot see. A global unique (a username) is a separate mark whose voice
  admits the disclosure.
- Counts, search, autocomplete and aggregates run over the folded query, never over the table.
- **The sync cursor is per share.** SYNC §2 keeps "one integer, the server's sequence"; a global
  sequence lets a member of one board watch the gaps and measure every other board's write
  rate. Per-share sequences cost nothing more (SYNC §6's per-row `seq` becomes per-share).
- Timing: the kernel always resolves the seat, then the row; a missing share and a share
  without a seat take the same path.

### 4.8 A service or agent removed while its work runs
This is §4.1's ruling applied to workers. A job, a queue consumer or an agent's plan carries
INTENT. Every transition it commits re-resolves the seat. The first commit after
`remove_member` is refused `NotFound` and the work stops there. Transitions it already
committed stand as history (AUTHORITY §7: compensated, never rolled back). A worker that holds
seats in many shares loses exactly one share. Revoking its TOKEN (`revoke_token`) ends every
share at once, as signing a user out does. The worker's dead-letter queue receives the refused
step with its `Refusal`, so an operator can see why it stopped. Its retries end with the
refusal, because a refusal is not a transient failure (std-queue_store's retry policy never
retries a `Refusal`).

## 5. Errors

### 5.1 The typed refusal

```avra
/// The verb a policy decided. `Admits` is the share's own (§2.4).
export enum Verb { Reads, Creates, Writes, Removes, Admits }

export enum Refusal {
    SignIn              // no principal proven: Anonymous asked for a member's door
    Ended               // the session or token was revoked or expired
    NotFound            // absent, OR not readable by this seat — one variant, by law
    Forbidden(v: Verb)  // readable, and the policy refused this verb to this seat
    Gone                // a share this principal was a member of was deleted
    Changed(v: Verb)    // an op written offline, refused at arrival under the seat as it is now
}
```

| Refusal | HTTP | Sync frame | The client shows |
|---|---|---|---|
| `SignIn` | 401 | stream not opened | the sign-in door, the intent kept to resume |
| `Ended` | 401 | `ended`, stream closed | "signed out on this device", drafts kept |
| `NotFound` | 404 | row absent | the not-found view; never "you have no access" |
| `Forbidden(v)` | 403 | `refused(op, v)` | inline at the control that wrote; it was greyed already unless the seat changed |
| `Gone` | 410 | `gone(share)` | the share read-only with its deletion stated |
| `Changed(v)` | 409 | `refused(op, v)` | the field reverts, the draft is kept, the reason said once |

A refusal carries the `Verb`, a typed value rather than v1's `rule: string`, so a client
`match`es it to pick the voice and a log counts it with no string tag. It never carries the row.
With a table policy, the client can say WHY from data it already holds: the seat's `Permit`
row names the cell that refused (`.No`, or `.Own` and not the owner).

### 5.2 Voices the user hears
A voice states the law, not the symptom (CLAUDE.md):
- `Forbidden(.Writes)`, cell `.No`: "Viewers of this board can read cards, not change them."
- `Forbidden(.Removes)`, cell `.Own`: "Editors can remove only the cards they wrote."
- `Forbidden(.Writes)`, cell `.Ask`: the `*_when` method's own voice, named beside it.
- `Changed(.Writes)`: "Your role on this board changed while you were offline; this edit was kept as a draft."
- `NotFound`: "This board isn't available." (the same sentence for absent and hidden)
- `Gone`: "This board was deleted on <date>. It can be restored until <date>."
- Last owner: "A board keeps one owner — make another member owner before leaving."

### 5.3 Golden voices the compiler speaks (each a registered kind with a witness)

```
error[share.unpolicied]: `Card` is `@in` a `Board` and has no policy — every row in a share has a `@policy` table or an `impl Policy<BoardRole>`
error[share.owner_unmarked]: `card_policy` has an `.Own` cell and `Card` marks no field `@owner` — `.Own` compares the seat with the owner
error[share.ask_unanswered]: `card_policy`'s `writes` column has an `.Ask` cell and `Card` has no `writes_when` — an `.Ask` cell is answered by its verb's method
error[share.policy_roles]: `card_policy` holds `.Editor` twice and `.Viewer` never — a policy table holds every role exactly once
error[share.role_remainder]: a policy method spells every role — `_ ->` here would let the next role in unread
error[share.policy_reads_world]: a policy method reads its seat, its row and `next` only — `writes_when` reads `db`
error[share.reads_unprojected]: `reads` must fold into the query — `slugify` has no SQL form
warning[type.registry_hole]: arms answer for several variants and this hole takes the rest: .Viewer
error[type.match]: `match` on `BoardRole` must handle `.Commenter`
error[type.match]: variant `Editor` is matched more than once
error[share.parent_cycle]: `Team` is in `Project`, which is in `Team` — a share's parents end
error[share.principal_named]: a policy compares the seat with its row, never with a principal — `m.who == ingest_service` names one; grant it a member row
```

The two `type.match` lines and the warning are the compiler's own today (§3). The `share.*`
kinds land with `@std/share`. `share.policy_roles` is a TEST-time voice until the keyed table
lands (§2.1), and the keyed table's own refusals are then the compiler's `type.match` words.

## 7. Cost

Native builds (`avra build`), same base as §3; each number is three runs, ns per check, integer

| What | Measured | Reading |
|---|---|---|

| v2, same: the table looked up per check (`card_policy.find(it.role == m.role)`, then the cell) | 80.7, 85.5, 82.1 ns | a `find` with a closure and an enum compare: SEVEN TIMES the match |

- **Per edit:** one seat read (~1.7 µs, cached for the request) plus one policy check (~7 ns
  with the held cell). The check is noise beside the commit it guards. The seat read is the
  cost, and it is the price of "live at commit" that AUTHORITY requires.
- **The table's idiom must not cost seven times the method's (P4).** Hence the `Seat` carries
  its `Permit`, resolved with the seat (§2.1), and no check looks the role up. The keyed table
  of §2.1 removes the residue too: `card_policy[.Editor]` keyed by the variant lowers to an
  index, where a `find` walks and calls.
- **Per request:** ~2.5 µs to open the cookie plus ~1 µs for the session row: ~3.5 µs, against
  an HTTP request's own parse and write. Refusing a forged cookie costs the HMAC and no read.
- **Per read row:** ZERO in Avra for the common case. A `reads` cell of `.Yes`, `.No` or
  `.Own`, and a `reads_asked` that folds, is SQL's `WHERE`, run by the index (§2.3). Nothing is
  filtered in memory, as std-db requires. Where a policy is evaluated per row in Avra (the
  client's replica, a write batch), it is ~7 ns a row with the held cell.
- **Sync fan-out:** one frame per share when every role's `reads` is `.Yes`; one per distinct
  folded predicate otherwise — never per row, never per member.
- **Password hashing** is NOT measured: no argon2 runs on this machine (§1.2). RFC 9106's and
  OWASP's parameters (m = 19 MiB, t = 2, p = 1) are a memory budget per login, not per request;
  the census row lands with the vendored C.
- **ZERO_COST rows this adds:** "a policy check reads the seat's held cell, never the table"
  (detector: a `find` over a `@policy` table outside seat resolution), "a const table keyed by
  an enum is an index" (detector: `find(it.<key> == …)` over a const `table<…>` whose key is
  an enum), "a policy method that reads no field of `self` is hoisted out of the row loop"
  (detector: the method's read set), and "a `reads` decision is a `WHERE`" (detector: a
  `Policy` read walked in memory over a `@model`).

## 8. Rulings

**RULED (owner, 2026-11-28): YES to all five.** They stand as written, with the v2 names:

1. Sessions are server rows; tokens are opaque and hashed at rest; JWT only at the OIDC door.
2. A policy decides per row over `(Seat, row, next)`, four verbs, pure by law, roles unordered,
   every role decided; one definition runs on the client, at commit and in the query. The seat
   carries no principal kind and a policy never names a principal.
3. Judged at arrival, no grace; a refused offline op becomes the user's draft (amends SYNC §3).
4. No existence leaks: one `NotFound` for absent and unreadable; `@unique` scoped to the share;
   the sync cursor per share (amends SYNC §2).
5. Nesting: one parent share type, an exhaustive role mapping, direct membership overrides
   inherited.

Also decided: services and agents are principals like users and reach a share only by a member
row granted and revoked at run time (owner, via the UI lead, §1.1).

**v2 rulings asked** (the UI lead's two follow-ups):

6. **The name is `policy`** (§2.0): `Policy<R>`, `@policy(table)`, `Permit`, `Allow`, `Verb`.
   Recommend: yes. It is the name the prior art agrees on (Pundit, Laravel, Oso, RLS), it is
   free in the tree, and ORM §4a and AUTHORITY §1 already use it in this sense. `guard`
   collides heavily, `access` and `grant` collide with built code, and `ability` looks from the
   principal where this design looks from the row.
7. **A policy table is the primary spelling; a method is the escape hatch** (§2.1–§2.3). One
   row per role, cells `.Yes`/`.No`/`.Own`/`.Ask` over the four verbs, `@owner` naming the
   column `.Own` reads, and an `.Ask` cell answered by the verb's `*_when` method. The full
   `impl Policy<R>` is for a policy the table cannot say. The seat holds its `Permit`.
   Recommend: yes, with the keyed table (`table<Row> by role`, checked like a `match`) filed to
   the sugar backlog as the law that makes the table as safe as the match. Until it lands, the
   match-of-records spelling is the compile-time-checked form and a plain table is held by a
   generated spec case.

**Out of v1, named:** peer-only enforcement (Keyhive/Jazz-style signed membership), groups as
members of shares (a group principal expanding one level), per-field read policy (hiding a
column from a role: Phase 7's capability type, §2.5).

**First slice:** `@std/share`'s derives (`@share`: member table and seat resolution; `@policy`:
the generated `impl Policy<R>`) over `@model`, the four-verb check with its voices, and
`SessionStore` beside std-http_session. The board is ported with an all-table policy
(`.Yes`/`.No`/`.Own` cells only), so its query fold is std-db's BUILT `Eq` scope and the first
slice needs no partial evaluator and no new `Op`. The witness is a service principal (an
importer) invited as `Editor` by an action, then removed. Partial evaluation of `.Ask` reads,
