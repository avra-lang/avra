## 0. The one idea

The schema is a type. There is no second artifact describing it — no schema
YAML, no prompt fed to an agent, no hand-maintained migration alongside the
real one. Every later thing in this doc (a query, a migration, an
authorization capability, a cross-company contract) is a **projection** of
that one type (P12), generated and checked by the same compiler that checks
everything else. This is the thing every ORM surveyed gets wrong somewhere:
Prisma's client drifts from the schema by design, ODCS's YAML drifts from the
code by convention, text-to-SQL's prompt drifts from the live database by
construction. Avra's `@derive` already sees a declaration's real shape at
compile time and type-checks its output with the program — the mechanism to
not have a second artifact already exists; this campaign is mostly new
*consumers* of it, not new machinery.

## 1. Sequencing: most unlocking first, frontier last

Every phase below ships something real and gated on its own. None of them is
a prototype for the next one to throw away — each is a projection of the
model type that the next phase projects further. Phase 1 alone, shipped and
nothing else, is already a working ORM for real programs.

| Phase | Ships | Depends on | New infra needed |
|---|---|---|---|
| **1 — the floor** | CRUD models over SQLite | derive contract (done), `@std/sqlite` (done) | fix 2 known compiler bugs (§3); `decimal` |
| **2 — relations** | typed joins, N+1 killed structurally | Phase 1; COLLECTIONS' `collect` (landing) | none — the derive already sees the whole model graph |
| **3 — migrations** | schema evolution, no hand SQL | Phase 1 | a schema-snapshot format (parallels `seed.ll`/`seed.sources`) |
| **4 — contracts** | `@unique`/`@soft_delete`/`@computed`/`@polymorphic` enforced, not remembered | Phase 1, derive contract | new annotation fns only — zero new mechanism |
| **5 — dialect fidelity** | Postgres/MySQL, real power not lowest-common-denominator | Phase 1 | `@std/postgres`/`@std/mysql` packages — **its own campaign**, see §7 |
| **6 — typed SQL & pipelines** | raw-power escape hatch, composable queries | Phase 2 | a new sublanguage grammar (the machinery already exists) |
| **7 — capability as a type** | compiler-enforced authorization | Phase 4, supertraits (filed) | generalize `SeatMark` to a query-scoped mark |
| **8 — DB as a versioned value** | agent self-undo, audit-grade history | Phase 3 | an append-only storage model (SQLite: derive-generated shadow tables) |
| **9 — cross-org negotiation** | typed contracts between businesses | Phase 5, 7 | reuse the compiler's own fingerprinting; a signed log format |

Phases 1–4 are the practical ORM — competitive with Drizzle/Ecto/Diesel on
day one, SQLite-only. Phases 5–6 make the "every good database, without
flattening" claim real. Phases 7–9 are the part nobody else has built: state
designed for an autonomous agent (or a fleet representing a business) as the
primary reader/writer, not a human.

Nothing in Phases 7–9 gets built ahead of a real consumer needing it —
CLAUDE.md's own law: machinery built ahead of a decision biases the decision
toward the shape it serves. §11's placeholder is deliberately thin.

## 2. What a user writes, growing phase by phase

```avra
// Phase 1
use @std.db.{model, Db}

@model
type User = {
    @unique email: string
    name: string
    balance: decimal
}

let db = Db.open("app.sqlite")
let u = db.insert(User { email: "a@b.com", name: "Ada", balance: decimal("0.00") })
let found: User? = db.find(User, u.id)

// transactions are real today — @model calls and hand-written SQL commit/
// roll back together, consistently (confirmed by red-teaming, not aspirational)
db.begin()?
let ada = db.insert(User { email: "ada@b.com", name: "Ada", balance: decimal("0.00") })?
db.rollback()?   // ada's insert is undone; a later db.find(User, ada.id) answers null
```

```avra
// Phase 2 — relations, typed joins
@model
type Post = {
    title: string
    author: User            // a model-typed field IS the relation
}

let posts: List<Post> = db.query(Post).with(.author).all()   // one planned query, never N+1
```

```avra
// Phase 3 — a schema change becomes a migration, never hand SQL
@model
type User = {                      // the SAME User from Phase 1, evolving
    @unique email: string
    name: string
    balance: decimal
    plan: string = "free"          // NEW field, with a default -> additive migration
}
// `avra db migrate` diffs this against the committed snapshot and writes
// migrations/003_user_add_plan.sql for you. A RENAMED or NARROWED field
// instead refuses to auto-generate and asks for an explicit typed migration
// statement naming the exact field — the same "growth crosses, moving
// refuses" law the compiler already enforces on its own generations (§5).
```

```avra
// Phase 4 — contracts the derive enforces
@model
@soft_delete
type Account = {
    @unique email: string
    balance: decimal
    deleted_at: Time? @auto
}
// every generated query filters deleted_at by default; .including_deleted() opts out, visibly
```

```avra
// Phase 5 — dialect fidelity: real per-backend power, typed against the connection
let pg: Db<Postgres> = Db.open_postgres("postgres://...")

@model
type Event = {
    payload: Jsonb          // a real Postgres type, not a lowest-common-denominator string
}

let sq: Db<Sqlite> = Db.open("app.sqlite")
// sq.query(Event).all()
// compile-time error: `Jsonb` needs a Postgres connection, this is `Db<Sqlite>` —
// the missing capability is named, never a runtime exception or silent flattening
```

```avra
// Phase 6 — the escape hatch, typed against the models
let big_spenders = sql {
    SELECT name, balance FROM User WHERE balance > ${threshold} ORDER BY balance DESC
}   // `balance`/`name` resolved against User's real fields at compile time, no live DB needed
```

```avra
// Phase 7 — capability as a type (frontier)
let cap: Capability<User, [email, name]> = grant(principal, User)
let rows = db.query(User, cap).all()   // .balance on this seat refuses to parse
```

```avra
// Phase 8 — the database as a versioned value (frontier)
let past: Db = db.as_of(yesterday)
let mistaken = db.writes_since(yesterday).by(agent_42)
db.replay(from: past, excluding: mistaken)
```

Method names above are mostly illustrative, not committed, with one
exception: `insert`/`find`/`update`/`delete`/`Db.open`/`table_name`/
`@unique` and `begin`/`begin_read`/`commit`/`rollback`/`in_transaction` are
no longer a naming proposal — they're the real, shipped vocabulary in
`packages/std-db`/`@std/sqlite`, confirmed against the source for this edit.
Everything past Phase 1 (`with`/`query`/`@via`/`HasMany`/`db.migrate`/
`Db<Postgres>`/`Jsonb`/`sql { }`) is still a doc-time name, not a commitment.

## 2a. The error story: not "compliant," the best one that exists anywhere

Non-negotiable, per the owner: every diagnostic and every runtime error this
campaign produces follows `docs/2026_09_24_DIAGNOSTICS_ARCHITECTURE.md`
exactly (coordinated directly with ERRORS, who owns that design). But
compliance is the floor, not the target. The ORM has one thing no
general-purpose diagnostics mechanism has: **the compiler already knows the
schema.** A raw database error is a string; a model-aware one names the
field, the file, and the annotation that made the rule. Two channels, kept
separate on purpose:

**SUPERSEDED 2026-09-25 (the owner rejected the stacked-annotation shape
outright): `@model`'s own structural refusals speak through `@model`
itself, from one fn, via a new `@std/meta` answer shape.** The 2026-09-25
resolution below this line stood for about a day: a second annotation,
`@model_shape` (a Validates-effect fn, `static fn derive(t: Type) ->
List<Diagnostic>`), stacked beside `@model` on every declaration. The owner
called this "a heinous idiom" against P3/P6 the moment it shipped and asked
directly why one annotation couldn't do both — a fair question the original
resolution never actually asked, since it took the existing four-effect
system as fixed rather than as something CLAUDE.md's own P6 (paradox
collapse) says to widen. **The actual fix: `@std/meta` gained `Declared {
made: List<Directive>, problems: List<Diagnostic> = [] }` as an ALTERNATE
answer shape for the Declares effect** (not a fifth effect, not touching
`Derived`/`@derive`'s own multi-trait machinery) — `check_annotation` and
`expand.av`'s dispatch both recognize it by name (`meta_type(ret,
"Declared")`) alongside the plain `List<Directive>` shape, and `problems` is
spoken exactly where a Validates annotation's own diagnostics are. `@model`
now answers `Declared { made: Model.derive(t), problems: shape_problems(t)
}` — one word on the declaration, one fn, both effects, from the SAME
generator that already had to know the shape to build the `impl` in the
first place. `@model_shape` is deleted; every reference to it below this
line is historical.

**Compile time — `@model`'s own contract violations.** Every annotation
(`@model`, `@unique`, `@soft_delete`, `@computed`, `@polymorphic`, and every
later one) raises through `@std/meta`'s `Diagnostic`/`refuse_as`/`refuse_as_at`,
never a hand-rolled message path. **Kind strings are BARE WORDS, never
dotted** — `core/modules.av`'s `is_kind_word` refuses a `.` in one, because
the PACKAGE is already the namespace: `refuse_as("no_id_field", ...)` from
`@std/db` renders as `@std/db:no_id_field`, so a self-chosen `model.` prefix
would only duplicate what the package name already says (confirmed
building Phase 1 — the doc-time guess above this line was wrong about the
wire format, right about wanting one consistent namespace per package;
`no_id_field`, `too_many_fields`, `enum_not_supported` are Phase 1's three,
shipped). Every later phase's kind names the same way: `duplicate_unique`,
`unknown_relation`, `narrowing_migration`
in Phase 3, `capability_unknown_field` in Phase 7. A message states
the law broken, in the law's own words (CLAUDE.md's "a builder's words are
its claim") — never a generic "`@model` failed:" prefix flattening five
different mistakes into one sentence. A typo'd relation or field name gets a
"did you mean" suggestion the same way the compiler already offers one for
an unresolved name elsewhere — shown, not auto-applied, unless proven.

**Run time — a constraint failure resolved back through the schema.** This
is the actual push past every ORM surveyed. SQLite reports `UNIQUE
constraint failed`; every ORM in the research either passes that string
through untouched or wraps it in a generic "conflict" exception. `@model`'s
derive knows, at compile time, every `@unique` field and which table/column
it became — so the generated insert/update path can resolve a
`Cause.Constraint(.Unique)` back to the exact field, and say so:

```text
error: `email` must be unique — declared @unique on `User.email` at
       models/user.av:3
caused by: sqlite.constraint.unique (UNIQUE constraint failed: users.email)
```

Two honest cases, never one dishonest answer: **one** `@unique` field on the
table — attribute with full confidence, no ambiguity possible. **More than
one** — SQLite's error message names the exact `table.column` for the index
that failed (a documented, stable part of its error text, not a guess);
match it against the derive's own known mapping and attribute exactly when
it parses as expected. If it ever doesn't (a future SQLite version changes
the format, or a hand-written constraint the derive didn't generate fires),
fall back to naming every `@unique` field on the table as "one of these" —
never a confident wrong attribution manufactured from a string that stopped
matching. The underlying `SqlError` stays reachable as `.cause()`
regardless (ERRORS' `ClientError.cause()` shape, copied exactly) — a caller
who wants the raw SQLite text always has it; the model-aware sentence is a
richer *addition*, never a replacement that can lose information.

This is P10 (the compiler holds semantic knowledge no other tool has) paid
at the one boundary where a runtime failure and a compile-time declaration
are, underneath, facts about the same field. No prior art in the research
closes this loop — it's a real, buildable, near-term differentiator, not a
frontier promise, and it lands in Phase 1 alongside the derive itself.

## 3. Phase 1 — the floor: `@model` over `@std/sqlite`

This is the S6b task named in the kickoff. `@model` bundles derives through
the existing contract machinery — `static fn derive(t: Type) -> List<Directive>`,
held to its contract at declaration (F2134) and at each use (F2072, F2066),
an unclaimed mark refused (F2092). Nothing here needs a new derive engine.

**Must fix first — both filed 2026-09-24, both fixed on main, both block writing a single model until they land:**

1. **F2033**: an annotation fn cannot call `Model.derive(t)` — a trait's
   static fn is taken as generic over `Self` even when neither its signature
   nor its body names `Self`. This is a typer fix: a static fn that never
   mentions `Self` should not be treated as generic over it. Grep the highest
   F-code on main before landing this (moves hourly).
2. `@model` over a multi-line record with a field mark fails to parse
   (F0100 at `type User = {`). Diagnose with a minimal probe first — the
   kickoff itself flags "it may be the probe," i.e. confirm this is a real
   grammar defect before assuming one.

**What `@model` generates:** table DDL, typed insert/find/update/delete,
typed column accessors. Table creation vs. migration-tracked creation is a
Phase 3 question — Phase 1 can create-if-missing and defer the diff machinery.

**Reserve a version column now, unconditionally.** SHIPPED —
`"__avra_version__" INTEGER NOT NULL DEFAULT 1` on every generated table,
bumped in every `UPDATE`'s own `SET` clause, confirmed atomic (a rolled-
back write leaves it unbumped, red-teamed against both a unique-constraint
failure and a real `SQLITE_BUSY` contention failure). Every generated table
gets a hidden monotonic version (bumped on every write), whether or not
Phase 1 exposes a compare-and-set API for it. Optimistic-concurrency
authority (Phase 7's real subject) needs this column on every existing row;
adding it later means migrating every model already in the wild. Reserving
it now costs one hidden column and pays for itself the day Phase 7 lands.
This is `AUTONOMOUS_SYSTEMS_AND_STATE.md` decision #6 (idempotency,
causality, and provenance are structural, not columns remembered later) —
pulled forward because it's free today and expensive to retrofit.

**Plain fields are authoritative truth by default.** A `@model` field holds
current institutional state, not an attributed claim — that distinction
(fact vs. assertion vs. intention) only matters once agent-derived data
enters the picture, which Phase 1 doesn't need. No mechanism to build now;
naming the default here means an `Assertion<T>` wrapper, if it ever lands,
arrives as an opt-in exception rather than a retrofit onto every field.

**Boundary discipline (CLAUDE.md, already paid once for `@std/sqlite`, must
hold for *generated* code too):** the NUL guard at every C-crossing string,
the empty-path temp-database trap, the `file:`-URI split, variadic/out-param
hazards. A hand-written call can be reviewed; a derive-generated call must be
**structurally incapable** of hitting one of these — the derive templates
that build SQL text and bind parameters are the one place to get this right,
not every call site.

**`decimal`** (avra-8sb5.9.9) belongs in this phase, not later — a `balance`
field typed `float` is exactly the silent-money-corruption hazard the
owner's ruling exists to prevent, and Phase 1's own example above wants it on
day one. `core/types.av` already carries the anchoring note for where
`Type.Decimal` lands (grep "A money column wants" to find it) — this is a
core-language slice that can run in parallel with the sqlite-integration
work, not a blocker on the critical path.

**Landing test:** SHIPPED (`packages/std-db/src/tests/landing/`) — one real
program, insert, find by unique field, update, close, reopen the SAME file
path on a fresh connection, find again (the load-bearing assertion: reads
back the value the UPDATE wrote before the close, so it only passes if the
write actually persisted), delete, confirm absence — `eval == native ==
expected`, gated. Proved it has teeth by deliberately pointing the reopen
at `:memory:` instead and watching it fail correctly, before reverting.

**Transactions are real today, not a later phase** — `db.begin()`/
`db.begin_read()`/`db.commit()`/`db.rollback()`/`db.in_transaction()` already
exist on `Db` (`@std/sqlite`'s `tx.av`) and are confirmed (round 3
red-teaming) to compose correctly with `@model` calls: rollback undoes an
`@model` insert/update/delete exactly like hand-written SQL, and mixing an
`@model` call with hand-written SQL in one transaction commits/rolls back
them together, consistently. Nothing to build here — worth stating in the
doc's own example set (§2) rather than leaving a real, already-solid
capability implicit.

## 3a. Phase 1, as actually built — what changed and what every later phase must respect

Built in `packages/std-db` against a real SQLite database, red-teamed across
seven rounds (74+ tests, five separate bug classes found and fixed). This
section is the receipt Phase 2–4's design below is built on — not
speculation about what Phase 1 *would* need, but what it actually needed.
Two of the five bug classes are worth naming here because they're the kind
Phase 2's own error-attribution and relation-loading work will reach for
the same shape of fix: a bad `@model` shape used to generate a broken
`impl` that mistyped 5-6 different ways instead of generating nothing (the
`Declared`-answering `@model` now checks the same shape predicate its own
`problems` half does, and answers an empty `impl` rather than a half-built
one); and the unique-constraint field-attribution's own
substring match could confidently name the WRONG field when one `@unique`
field's name prefixed another's on the same model, or a model's name was a
suffix of an unrelated table's — fixed by requiring an identifier boundary
on both sides of the match, the same class of bug Phase 2's join-column
resolution should assume it's exposed to wherever it matches a name
against SQL text rather than against a typed value.

- **Convention, load-bearing:** every model's first field is `id: int = 0`.
  Phase 2's relation fields and Phase 3's migration keys both assume this —
  neither should invent a second identity convention.
- **Every generated identifier is double-quoted, unconditionally**, in every
  piece of generated SQL — table names, column names — because a field or
  type named after a SQL keyword (`order`, `group`, `table`) produced broken
  SQL otherwise. `table_name()`'s own PUBLIC return value stays unquoted
  (introspection shouldn't leak SQL syntax into a caller comparing strings);
  quoting happens only at the point generated SQL text is assembled. Any new
  generated SQL in Phase 2–4 (join clauses, migration DDL, contract-enforcing
  `WHERE` fragments) inherits this rule — it is not Phase 1-specific.
- **A table-name collision is real and was silent before the fix.** Two
  unrelated `@model` types in different modules sharing a bare type name (and
  a compatible field shape) wrote into the SAME physical table with zero
  error — the kind of collision two developers independently naming `User`/
  `Order`/`Item` hit in any real codebase. Fixed with a claim registry
  (`__avra_models__(table_name TEXT PRIMARY KEY, declared_at TEXT)`, keyed by
  the declaring type's own file via `Loc`, since `@std/meta`'s `Type` carries
  no module/package field): `create_table()` claims its name there first, and
  a second, different model claiming an already-claimed name refuses loudly,
  naming the file that claimed it first, before touching the real table.
  **Phase 2 must extend this registry, not bypass it** — a relation is a
  foreign-key column pointing at another model's table, and the join planner
  needs the SAME claimed-name mapping to resolve which physical table a
  `User` field actually means; a second, independent name-resolution path for
  relations would silently reopen the exact hole this fix closed.
- **The zero-non-id-field edge case is real, not academic** (a model that is
  pure identity, or a join/junction table before Phase 2 adds cross-references
  natively): an empty column list breaks `INSERT`, an empty `SET` clause
  breaks `UPDATE`. Fixed with `INSERT ... DEFAULT VALUES` and a
  self-referential `id = id` update. Phase 2's join-table representation (if
  `has_many`-through ever needs one — see the open question below) will hit
  this immediately and should reuse the fix rather than rediscover it.
- **Unsupported field kinds correctly REFUSE to compile** rather than
  silently misbehaving: `List`, `Opt`/nullable, a nested struct, and (still,
  as of this edit) `decimal` and any model-typed field (the relation itself)
  are today an honest compile-time refusal, not a runtime surprise. Phase 2
  is exactly "teach the derive to recognize a model-typed field instead of
  refusing it" — the refusal path already existing and being loud is the
  right foundation to extend, not a gap to route around.
- **Performance has an explicit floor, and it is not "faster than before" —
  it is C-equivalent, per the owner's own standard** ("the floor is the
  goal, nothing more"). Closed in stages, each one measured, not assumed: a
  real `Db`-level statement cache (avra-8sb5.44.5, benefits every
  `@std/sqlite` consumer) closed the 4.2x naive-reprepare gap; `Stmt.names()`
  caching column names once per statement instead of once per row closed a
  further ~20%; the biggest win was architectural, not tactical — `find()`
  reads columns straight off the live `Stmt` (`int_at`/`text_at`) instead of
  building a `Row`/`List<SqlValue>` the caller then unwraps a second time,
  cutting `find()` roughly in half on its own. Two compiler-level fixes
  (`Result<bool, E>`/`Result<float, E>` riding registers instead of a heap
  pair, and `defer` over a method call/managed capture/non-void answer
  getting the same no-closure fast path a free-fn `defer` already had — both
  filed as this campaign found them, both landed on main) closed the rest
  for free, no `@model`-side code change needed. Net: `find()` went from a
  first-cut ~1100-1300ns/call to a steady ~650-700ns/call against a fair
  hand-measured C floor (real `malloc`+`memcpy` for the text columns, not a
  borrowed-pointer read) of ~350-450ns/call — under 2x, not the ~3x this
  entry originally reported, and `insert()` was at/under the C floor from
  the start. **Phase 2–4 must not add a second per-call allocation on the
  hot insert/find/update path** without being held to the same bar —
  measure against the raw `Stmt` API each time, per CLAUDE.md's "measure,
  then change," not against Phase 1's own already-improved baseline.
- **`decimal` (avra-8sb5.9.9) is the one Phase 1 item from the original plan
  still not built.** Every `balance`-shaped field in this doc's examples
  still can't be written for real yet — it is not blocking the ORM mechanism
  itself (float/int/bool/string all round-trip correctly, including the
  false-vs-absence and NUL-byte edge cases probed in round 2 of red-teaming),
  but it blocks the money-safety claim the doc leads with. Track it as a
  standing Phase 1 loose end, not folded into Phase 2's scope.
- **Cross-package derive struct-literal construction (avra-8sb5.44.3) was a
  real, general compiler bug, now fixed on main** — a template-constructed
  struct literal of an annotated type, built from a DIFFERENT package than
  the one declaring it, asked the wrong file's namespace to resolve the
  literal's head. This was not ORM-specific (any cross-package `@derive`
  building a full literal of its own annotated type hit it) and its fix
  benefits every future `@derive` consumer, not just `@model`. Worth noting
  here only because it was the reason `find()`/`all()` — needing to
  construct a fresh instance from a row with no `self` to `with{}` from —
  were the LAST Phase 1 pieces landed, not the first.

## 4. Phase 2 — relations & typed queries, N+1 killed structurally

**A `belongs_to` field, concretely.** `author: User` on `Post` generates an
`author_id INTEGER NOT NULL REFERENCES "user"("id")` column (quoted per
§3a's rule, and `"user"` resolved through the SAME `__avra_models__` claim
registry Phase 1 built — never a second, independent name-resolution path).
`author: User?` generates the same column `NULL`-able, no `REFERENCES`
enforcement dropped. The field's own accessor (`post.author`) is a *loaded*
read (see `.with()` below) — reading it before loading is Phase 2's own
refusal (`relation_not_loaded`), never a silent lazy-query-per-access (that
reintroduces the N+1 hole this whole phase exists to close, just moved to
the read side). **Correction from the original text:** this is a RUNTIME
check at an arbitrary read site, not a `@model`/`Declared` compile-time
`problems` entry — the derive cannot know at compile time whether a given
call site ran `.with()` first. It belongs with the generated accessor's own
body (trap or `Result`-typed read, a call decided when the accessor is
built), not in either channel §2a describes.

- A field typed as another `@model` is a `belongs_to`; the derive can see
  this because it sees the *whole* model graph in one compile, not
  per-file. "Every model in the closure" is COLLECTIONS' `collect models =
  model in closure` (avra-8sb5.28) — COMPONENTS already flagged this exact
  need (2026-09-24 comment on that epic). If COLLECTIONS hasn't landed by
  the time this phase starts, build the narrowest possible table-of-models
  helper rather than block on it, and delete it the day `collect` lands.
- `has_many` needs the inverse direction spelled somewhere. **Recommendation
  (was an open question, narrowing it here — still needs the owner's actual
  sign-off, not decided by this edit):** EXPLICIT declaration on the parent
  (`posts: HasMany<Post> @via(.author)`), not implicit inference. Reasons,
  from what Phase 1 actually surfaced: (1) `avra explain User` printing an
  inferred relation is still a SECOND thing a reader has to go run — a
  declared field is inspectable by just reading the type, zero tooling
  required, which is the stronger form of P7; (2) the child model's own file
  may not even be visible to the parent's package the way Phase 1's
  table-name registry had to learn to handle (`Loc`, not module identity,
  is what the compiler actually has) — inferring the inverse requires a
  whole-graph pass at the parent's declaration site that the explicit form
  makes unnecessary; (3) it matches the field-mark idiom `@unique`/
  `@soft_delete` already established in Phase 1 rather than inventing a
  second "the compiler figures it out" mechanism this early. If implicit
  inference is wanted later, it is additive sugar over the explicit form,
  never the other way around.
- `.with(.author)` compiles to **one** planned join or **one** batched `IN`
  query, chosen by the derive at compile time from the model graph's shape —
  never a runtime dataloader cache reacting per request. Landing test:
  `.with()` over 1000 rows executes exactly 1 (or 2) SQL statements, not
  1001 — assert the statement count, not just the result. Concretely, reuse
  the connection-level statement cache Phase 1 built (avra-8sb5.44.5) for
  the join/batch query itself — a relation load is exactly the kind of
  repeated, shape-stable query that cache exists for, and Phase 2 gets its
  own performance floor for free by routing through it rather than a
  parallel query path.
- **Cascade behavior is a per-relation, explicit choice, never an implicit
  default** — `@via(.author, on_delete: .cascade | .restrict | .set_null)`.
  SQLite enforces `ON DELETE` at the DDL level when foreign keys are turned
  on; the derive emits the clause the annotation names. An un-annotated
  relation defaults to `.restrict` (refuse the delete, the SQL-standard-safe
  choice) — silent cascading deletes are the relational-data equivalent of
  the un-filtered-soft-delete anti-pattern Phase 4's `@soft_delete` closes,
  and this phase should not open a new instance of the same shape of bug.
- Escape hatch (P8): a join the derive can't plan is Phase 6's `sql { }`
  block, typed against the models it names — never a silent fallback to an
  untyped string inside this phase's own API.
- **Open, unresolved by this edit:** `has_many`-through a join table (a
  many-to-many) needs the join table itself to be a real `@model` (so it
  gets the same collision-registry protection and id convention) or a
  compiler-synthesized one the user never writes by hand — decide which
  before building this, since it changes whether §3a's zero-field-model fix
  is reused as-is or needs a variant for a table with no natural non-key
  columns at all (a pure join table IS that zero-non-id-field case, id
  aside — worth testing against the existing fix directly rather than
  assuming it generalizes).

## 4a. Queries compose in `impl`, and a policy is a query

THE COMPOSITION MECHANISM IS `impl` + `Query`, and there is no second one.
A named query is a method on the model's own `impl` answering a query value;
what a model adds to its derived doors is more of the same kind:

```avra
impl Card {
    static fn open() -> Query<Card> { Card.all().where(done: false) }
    static fn readable(who: Principal) -> Query<Card> {
        Card.all().where(owner: who.id)
    }
}

fn board(b: Board, who: Principal) -> List<Card> {
    Card.readable(who).where(board: b.id).order(.newest).all(db)
}
```

(`Query` and the builder's verbs are Phase 2's spelling; §2 records which
names past Phase 1 are illustrative.) Why `impl` and not a query block or a
second DSL: a query is a VALUE, and a type already carries the place to name
values of its own type. Methods compose — `Card.readable(who)` is a query
another `where` narrows — they are inspectable by the same `avra explain`
the builder answers, and a named query is testable without a database. None
of that is free from a keyword-shaped query surface.

A POLICY IS A QUERY OVER THE SAME VALUES, and it belongs to the LIBRARY,
never to the compiler. A policy says which rows a principal may read or
write; it is written in the builder's own vocabulary (a `where`, a join, a
subquery) and it is a value the program holds:

```avra
// a policy is a query, not a language feature
fn readable(cards: Query<Card>, who: Principal) -> Query<Card> {
    cards.where(owner: who.id)
}
```

The reason is the split the compiler actually holds: it bounds what code may
EVER ask for (Phase 7's `Capability<Model, Fields>`, a compile-time ceiling),
and the library decides who may ask, per request, in the same vocabulary a
read is written in. The compiler knows no application's authority model; a
policy encoded in the language would be an unopenable list of application
laws inside it, and every application the list did not fit would become an
escape hatch. A policy that is a value is inspectable, testable by the path
the read takes, and narrowable by code — which is the whole point.

## 4b. Input shapes wait for projections

`Patch<T>` (every field optional) and `New<T>` (no `id`, no server-owned
field) are the shapes every write wants, and neither is built by hand. They
are instances of ONE language feature — a type-level projection over a
record's fields, `Partial`/`Pick`/`Omit` — which is deferred to
`avra-8sb5.59.44.21`, not refused. Until it lands, spell the shape out (one
named record per use); do not mint a generated name per derive
(`CardPatch`, `UserPatch`, …), which would be a second naming scheme for one
concept and the exact parallel mechanism the projection replaces.

The same deferral covers `@std/validate`'s PATCH rule
(`2026_09_30_STD_VALIDATE.md` §9 decision 13): a field's rule applies only
when the field is present, which is `Patch<T>`'s first consumer, not its
definition.

## 5. Phase 3 — migrations as a projection, not a second truth

**The six migration decisions (a–f) are accepted as one package.** They are
the shape this mechanism is built to, and the list below is that package;
the down-migration question they do not settle is named at its end.

- **(a) One source of truth.** The `@model` type's declared shape is it; a
  migration file is a **generated, reviewable, committed projection** of
  the diff between today's shape and the last-recorded one (P12), never a
  second place a schema is written by hand.
- **(b) A committed snapshot, diffed at build time.** A schema snapshot sits
  beside the migration files and is diffed against the live `@model`
  declarations — the same shape as `seed.ll`/`seed.sources` recording what
  the compiler itself looked like at a generation boundary. Reuse that
  pattern rather than inventing a second one.
- **(c) The snapshot is keyed by DECLARATION, never by column shape.** A
  model's mutation surface may one day move behind a `@transition`/invariant
  declaration (see §9's forward pointer) without changing what the model
  *means*, so the diffed snapshot is keyed by declaration rather than
  hardcoded to "table plus columns" — else that day becomes a format
  migration instead of an additive one.
- **(d) Growth is automatic; movement is explicit.** The boundary check that
  already makes a moved shape unmovable in one generation ("growth is not a
  moved shape," CLAUDE.md) applies unchanged here: a model growing a field
  (with a default) generates an additive migration automatically, and a
  renamed or narrowed field refuses to auto-generate and demands an explicit
  typed migration statement naming the exact field. This is the *same*
  mechanism `@std/meta` crossing already uses for the compiler's own
  generations, pointed at a table's shape instead.
- **(e) The claim registry is the tracking table.** `__avra_models__` (§3a)
  is not just a collision guard — Phase 1 built it to answer "who claimed
  this table name", and Phase 3 needs "what shape did this table have last
  time we ran", which is the same table with one more column
  (`schema_fingerprint`, or the snapshot's own key) rather than a second
  bookkeeping table. Extend it, don't duplicate it: a second registry
  answering an adjacent question about the same rows is the "third copy
  names the concept" smell CLAUDE.md's style rules refuse.
- **(f) Create-if-missing retires the day this lands, and never coexists
  with it.** Two code paths that can both create a table — one from the
  derive's own `create_table()`, one from a migration runner — is a race the
  moment two processes start a fresh database at once, and a silent
  divergence the moment someone edits the model without running a migration.
  Phase 3's landing test includes this exact regression: import a
  Phase-1-authored program unchanged, confirm it now refuses to auto-create
  and asks for a migration instead of quietly succeeding the old way.
- Reserved-word identifiers (§3a's quoting fix) are exactly what makes a
  hand-inspectable migration file honest: the generated DDL a developer
  reviews before committing must show the SAME quoted form the derive
  actually executes, or a reviewed migration and the real behavior diverge
  on the first `order`/`group`-named column — a specific instance of the
  general "a guard and the thing it guards must read the same bytes" law.
- **Open, and not one of a–f:** down-migrations generated (mechanical,
  usually correct) or hand-required (safer, consistent with the language's
  honesty about what the compiler can and can't infer)?

## 6. Phase 4 — schema contracts: forgetting them becomes impossible

Every contract below is an annotation fn in the *same* derive-contract
machinery `@model` itself uses — zero new mechanism, just more consumers of
F2134/F2072/F2066/F2092.

- **`@unique` already shipped, inside Phase 1, not held for this phase** —
  worth correcting the doc's own original sequencing here rather than
  leaving it to read as still-pending. It generates a real `UNIQUE`
  constraint, is enforced on insert AND update, supports multiple
  independent `@unique` fields on one model, and its violation is the
  worked example in §2a (a `Cause.Constraint(.Unique)` resolved back to the
  exact declared field). Nothing left to build for it; it stays listed here
  only because it's the pattern the rest of Phase 4 follows.
- **`@soft_delete`** — every derived query method filters `deleted_at IS
  NULL` by default; `.including_deleted()` opts out, visibly, at the call
  site. This closes the single most-documented anti-pattern in the ORM
  research: a silently un-filtered soft delete is a real production
  incident class (double-selling seats), everywhere else a code-review
  discipline rather than a compiler guarantee. Concretely, against what
  Phase 1 actually built: `delete()`'s generated body changes from a real
  `DELETE FROM ...` to an `UPDATE ... SET "deleted_at" = ?` (quoted per
  §3a), which means a `@soft_delete` model's `delete()` and `update()`
  share more generated-SQL shape than they did before this annotation —
  worth generating both from one shared template rather than two, so a
  future fix to the quoting/parameter-binding rule can't silently apply to
  one and not the other. `Time? @auto` (the kickoff's own example) needs
  Phase 1's "unsupported field kind" refusal (§3a) to specifically carve out
  `Time?`/`@auto` as a recognized pair before this annotation can compile at
  all — check that gap is closed before starting this, not assumed closed.
- **`@polymorphic`** — generates real per-type foreign keys via a
  discriminated union of tables, not a typeless `type_id` + loose `id`
  column. Closes the referential-integrity hole every surveyed ORM leaves
  as an app-level convention. This is Phase 2's `belongs_to` machinery
  generating N foreign-key columns (one per possible target type, all but
  one `NULL` on any given row) instead of one — reuse Phase 2's relation
  codegen as a library call with a cardinality argument, don't fork a
  second relation-generation path for the polymorphic case.
- **`@computed`** — a schema-declared expression, evaluated lazily on
  read (EdgeDB's move). The field's type is inferred from the expression —
  ordinary Avra typing, no new mechanism. A computed field is exactly the
  shape §2a's structural-refusal channel anticipates needing more of: an
  expression naming an unknown field, or one whose inferred type can't
  round-trip through SQLite's affinity rules, is `@model`'s own `problems`
  domain (a real `computed_type_unsupported` Diagnostic, from `Declared`),
  never `@model` generating code that then fails at the backend with a
  compiler-internal message.
- Ent's other idea, privacy-as-schema, is **not** built here — it folds
  into Phase 7's capability type. Building a parallel authorization
  mechanism now that Phase 7 has to migrate away from would be exactly the
  premature machinery CLAUDE.md warns against.
- **Named but not built:** idempotency keys and causal links (`caused_by`)
  on a mutation are the other columns `AUTONOMOUS_SYSTEMS_AND_STATE.md`
  wants structural rather than app-remembered. Naming them here means a
  future `@idempotent`/causal contract has an obvious home in this same
  machinery instead of being invented ad hoc under schedule pressure later.

## 7. Phase 5 — dialect fidelity: Postgres, MySQL, and the rest

**Honest dependency, stated up front:** this phase needs `@std/postgres`
and/or `@std/mysql` to exist first. They don't today — only `@std/sqlite`
does. A wire-protocol driver is a different shape of work than an embedded
library (its own boundary-law audit, its own campaign). This must not block
Phases 1–4 shipping real value on SQLite alone — see §9's open question.

- Architect Phase 1's derive so a second backend is a **new per-dialect
  derive module**, never a rewrite of the first. Drizzle's steal: separate
  `pg-core`/`mysql-core`/`sqlite-core` builders, never one struct with
  optional per-backend fields.
- jOOQ's steal: a per-feature support matrix, stated in the type system.
  A Postgres-only column type (`Jsonb`, arrays, a real `enum`) used against
  a `Db<Sqlite>` connection is a **compile-time type error naming the
  missing capability** — never a runtime exception, never silent
  flattening to the lowest common denominator.
- **Needs a probe before committing** (idiom bar: probe first): is the
  generated model type itself parameterized by backend (`Model<B:
  Backend>`), or does one `@model` type generate backend-specific derive
  output selected by the `Db` value's own type? Try both against a small
  scratch model before writing the design's final shape.
- **Two Phase 1 mechanics are already dialect-shaped landmines, worth
  flagging before this phase starts rather than after:** identifier quoting
  (§3a) is `"double quotes"` in SQLite/Postgres (ANSI-standard) but
  backtick-quoted by default in MySQL — the quoting rule needs a dialect
  parameter from day one of a second backend, not a global constant
  discovered wrong later. And the `__avra_models__` collision registry's own
  DDL (`TEXT PRIMARY KEY`) is SQLite's affinity-typed dialect of "a string
  primary key" — confirm the same schema is legal, and the same claim-then-
  create sequencing is still race-free, under Postgres/MySQL's stricter
  typing before assuming the registry itself is backend-agnostic.

## 8. Phase 6 — typed SQL sublanguage & composability

- `sql { }` as a block-word sublanguage — Avra already has grammar/quote
  sublanguages, so this is a new consumer, not new grammar machinery.
  Parses real SQL, resolves column/table references against `@model`
  declarations at compile time. No live DB connection needed to
  typecheck — this closes sqlx's actual gap (a string verified against
  today's DB has no relational reasoning) by checking against the *type*
  instead.
- A PRQL-style pipeline (`from(User) |> filter(...) |> join(...)`) as
  sugar desugaring to the same checked query nodes underneath Phase 2's
  builder — gets composability without EdgeDB's cost (a whole new database
  with no path to "keep your Postgres").
- This sits above Phase 2's ordinary `.query(Model).with(...)` surface as
  the power-user escape hatch (P8); most code never needs it.
- **Scope this now, before an agent-facing surface gets built on top of
  it:** `sql { }` is for trusted implementation code. It must not silently
  become the tool handed to an autonomous planner — that surface is a
  closed, named vocabulary (Phase 7's typed transitions, or Phase 2's
  query builder), never open-ended SQL a model assembles itself. This is
  the same reason dbt/Malloy's semantic layers outperform text-to-SQL:
  accuracy comes from shrinking the agent's task to *selection*, not from
  a bigger escape hatch.
- A `sql { SELECT ... FROM User ... }` block's table/column resolution must
  go through the SAME `__avra_models__`-registered name Phase 1 built (§3a)
  and honor the same identifier-quoting rule — a hand-written block that
  resolves `User` differently than `db.query(User)` does would silently
  reintroduce the exact table-identity ambiguity the collision registry
  exists to close, just through a second door.

## 9. Phase 7 — capability as a type (frontier, biggest structural win)

**Overclaim flagged by `AUTONOMOUS_SYSTEMS_AND_STATE.md` §4.5/§6.2, fixed
here:** `Capability<Model, Fields>` is a compile-time data-minimization
ceiling — it bounds what code could ever *ask for*. It is not authorization.
Real authority is dynamic (expires, is revoked, has a budget, depends on
who currently owns the resource), so it needs a second, runtime half this
doc did not previously separate out:

```text
static capability  = the maximum this code can express (built here)
live mandate       = what this principal may do right now (Phase 7 of
                      AUTONOMOUS_SYSTEMS_AND_STATE.md's sequence, not this doc)
commit check       = the mandate re-checked fresh, at the final payload,
                      not when the plan began (closes a TOCTOU hole)
```

This phase still builds only the static half below — the live-mandate
kernel is real, separate, later work. The fix here is scoping the claim,
not adding the kernel.

- `Capability<Model, Fields>` parameterizes the query builder the same
  way a fn type's `SeatMark` list already parameterizes a fn's own
  promises (`mutable`/`settled`, interned and normalized onto the type
  key). **Reuse that exact mechanism** rather than inventing a second
  "marks on a type" concept — a capability's field list rides the same
  kind of channel a fn's mutability mark already does.
- A query naming a field outside the capability's field list is F-code,
  at the call site, before the query runs once — not a runtime 403.
- Attenuation (narrowing a capability for a spawned sub-agent) is a pure
  function over the type parameter — free at runtime, exactly like
  narrowing a fn's marks costs nothing extra today.
- Depends on supertraits (avra-8sb5.43, already filed) if `Capability`
  is meant to compose with the derive-contract trait hierarchy —
  coordinate with that task rather than duplicating its design.
- Phase 4's `@computed`/future `@private` field marks name the capability
  that may see them; the capability's field list is checked against those
  marks the same way F2092 already checks an unclaimed derive mark.

## 10. Phase 8 — the database as a versioned value (frontier)

**Unsafe wording fixed, per `AUTONOMOUS_SYSTEMS_AND_STATE.md` §4.6/§6.3.**
The original framing here treated `as_of`/`replay` as a cheap copy-and-undo,
the same law that governs an ordinary Avra value (`mut q = p` is a copy).
That law is right for a value nobody else has observed. A committed
transition is not that — once another party (an agent, a customer, an
external system) has seen or acted on it, "copy an earlier version and
write from it" quietly discards their observation. The corrected shape:

- `let snap: Snapshot<Db> = db.as_of(t)` is a **read-only view**, not a
  writable copy — writing from it is refused, or requires an explicit
  `Branch<Db>` (a named, private hypothetical, merged only as new commands
  revalidated against *current* state — never a pointer-swap over reality).
- `db.replay(excluding: ...)` is **not a production undo promise**. Its
  replacement is `db.counterfactual(excluding: writes_since(t).by(agent))`
  — an analysis tool, explicitly not authoritative — plus, for real
  correction: causal descendants (what did this bad write influence?) and
  an explicit corrective transition or compensation, per §2's "correction
  is a new fact, not an erasure."
- Bitemporal tracking (separating "when true" from "when recorded" as two
  independently queryable axes) is real storage-engine work — append
  rather than overwrite, index both axes. This is the single biggest
  engineering lift in this document.
- **Load-bearing open question:** does this live entirely inside
  `@std/sqlite` (derive-generated append-only shadow tables per model —
  SQLite has no native temporal support) or does it want a dedicated
  storage engine? `AUTONOMOUS_SYSTEMS_AND_STATE.md` §6.6 warns against
  letting shadow tables *be* the language-level abstraction — the surface
  Avra exposes should be a transaction/event/evidence history, with SQLite
  shadow tables as one possible storage projection of it, not the concept
  itself. Needs its own design pass and must not block Phases 1–7.

## 11. Phase 9 — cross-organization negotiation (frontier, genuinely far out)

**Scope correction, per `AUTONOMOUS_SYSTEMS_AND_STATE.md` §4.7:** a content
hash of a model's shape proves structural equality; it says nothing about
field meaning, units, jurisdiction, which party has authority for which
transition, deadlines, compensation, or dispute rules. A real
cross-organization agreement is a typed *protocol*, not a shared model —
the fingerprinting idea below still holds, it just has to cover the whole
protocol declaration (transitions, authority, wire semantics), not only
record shape. This phase stays a placeholder either way (§7 below).

- The contract is the type; a published OpenAPI/YAML description is a
  generated projection, never hand-authored truth — the same P12 law as
  Phase 3's migrations, a different pair of artifacts.
- Two parties' compilers agree on a shared model shape via a
  **content-addressed hash of the model's declaration** — not new
  invention: the compiler already has fingerprinting (`settled_symbol`,
  the fold that gives consts and derives their cache identity). This
  phase is a new *consumer* of that fold, pointed at a `@model` type
  instead of a const expression.
- The existing crossing law applies unchanged: a counterpart's model
  growing a field crosses clean; renaming or narrowing one refuses,
  naming the exact divergent field, before a cross-org query runs once.
- Disputes ("your agent wrote this, not mine") settled by a
  Certificate-Transparency-shaped append-only signed log — inclusion
  proofs between named, known parties. No consensus, no mining; nobody
  here is anonymous the way a blockchain assumes.
- **Deliberately no prototype yet.** This is a placeholder until Phases
  1–7 exist and a real two-party use case shows up — building it earlier
  would be exactly the "correct unused wrapper that argues for its own
  use" hazard CLAUDE.md already names.

## 13. Prior art — the steal-list

Full research (two independent passes) is in this session's transcript, not
reproduced here. The mechanisms actually being reused above:

- **Drizzle** — per-dialect builders, never one flattened struct (§7)
- **Ecto** — changesets as standalone validation, independent of the table
  (not yet placed in a phase above — worth a slice once Phase 1 ships:
  input validation as data, separate from persistence)
- **Diesel/sqlx** — compile against the real schema; sqlx's live-check
  idea replaced here by checking against the *type*, no DB round-trip (§8)
- **jOOQ** — explicit per-feature dialect support, stated in types (§7)
- **Ent** — privacy-as-schema, folded into capability-as-type (§9)
- **EdgeDB** — computed fields as first-class schema expressions (§6)
- **PRQL** — pipeline composability as sugar, not a new database (§8)
- **Datomic/XTDB** — the database as an immutable, time-queryable value (§10)
- **Biscuit/macaroons** — attenuable capabilities; reused as a *type*
  instead of a runtime-interpreted token (§9)
- **Certificate Transparency/Sigstore** — signed append-only logs for
  provenance, without blockchain consensus (§11)
- **Unison** — content-addressed identity, reused as a schema hash
  instead of a function hash (§11)
- **dbt/Malloy** — accuracy comes from shrinking an agent's task to
  *selection* over a closed typed vocabulary, not open-ended generation —
  the design principle behind §3's whole approach to agent-written queries

From `AUTONOMOUS_SYSTEMS_AND_STATE.md`'s independent review:

- **typed transitions as the only public mutation surface** — `db.update`
  is an implementation primitive, `reserve_inventory(order, qty)` is what
  an autonomous caller should ever see (its §2, §4.1)
- **idempotency/causality/provenance as structural columns, not remembered
  ones** — pulled forward into Phase 1's reserved version column and
  Phase 4's named-but-unbuilt columns above (its §4.4, decision #6)
- **static capability vs. live mandate as two different mechanisms** —
  fixes an overclaim in this doc's original Phase 7 (its §4.5, §6.2)
- **snapshot/branch/correction as four distinct operations**, never one
  cheap copy — fixes an unsafe promise in this doc's original Phase 8
  (its §4.6, §6.3)
