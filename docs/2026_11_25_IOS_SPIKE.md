# The iOS spike: slice 0

For the UI lead, before any spike code. Ticket avra-8sb5.110. It covers three things: (a) what
std-ui already holds for a native target, (b) how Avra's scheduler and the app's run loop share
the main thread, and (c) how an app could be declared. Nothing here is built except the
measurements, which ran on the Mac host (macOS 26, Apple silicon). Simulator numbers are not
taken yet, so every figure is a relative one.

Where it stands: step A (`ios-sim`) builds `--target arm64-apple-ios-simulator`. On a simulator a
program prints, runs tasks, traps a runaway task at its guard page with exit 2, and calls
Foundation (`tools/ios_sim_witness.sh`). A hello binary is 89 KB, and one with tasks is 132 KB.

## (a) What std-ui already holds for a native target

| Piece | What it is | What a UIKit or SwiftUI host does with it |
|---|---|---|
| `tree/node.av` | The neutral tree. `Prim` has 23 interaction contracts (text, button, field, list, item, dialog, alert, switch, slider…), plus `Attribute` and `Node`. Every target answers every `Prim`, or the build names the target. | This is the vocabulary a native host should map to its views, one `Prim` to one control. |
| `tree/identity.av` | One identity per node: its parent and its step (a key, or the site it was written at). A `NodeId` number lasts as long as the node does. | Stable keys for cell recycling and for diffing a SwiftUI `id`. |
| `tree/rows.av` | `windowed`: a list builds only the rows in its window. The target says where the window is. | `UITableView`/`UICollectionView` reports its visible index paths, and the 10k rows of slice 2 build only what is on screen. |
| `tree/sink.av` | One walk of a tree, three operations (`opened`, `words`, `closed`). | The first-paint walk for a host. |
| `tree/controls.av` | The controls on a screen in reading order, each with its path and what happens when it speaks. | The a11y order, and what a headless witness reads back. |
| `a11y/name.av` | A node's announced name: its `label`, else its own words, else `hidden`. | `accessibilityLabel` and `isAccessibilityElement`. |
| `place/` (the solver) | CSS flexbox over the `Layout` vocabulary, checked against Firefox by `tools/layout-oracle`. Units appear only in what a target's `Measure` answers, in sixtieths. | UIKit measures text and controls (`sizeThatFits`), our solver places them, and the host sets frames. This is the doc's "our solver places, UIKit measures". |
| `native/sources.av` | The native loop. An app's inbox is a `Channel<Msg>`, sources are tasks that park and post an `Act`, each act is a turn, and the screen is painted at most once per frame (`window_ms`). | This is the seam (b) is about: it already assumes the app's loop is an Avra task. |
| `native/net.av` | `@std/http` as the native network. | Works as is on iOS (sockets), once the package C is built for the SDK (gap 2). |
| `headless/headless.av` | The target with no host: the screen is the tree in memory, and a test speaks to a control by its words through the app's door. | The model for the spike's witness: the same door, with an iOS host in front of it. |
| `terminal/` | A real non-web sink: tree, then lines in a width, then cells, with focus and keys through the one door, all running on `native/sources`. | The nearest existing model of a native realizer. It is Avra-owned end to end, and its run loop is ours. |
| `web/web.av` + `realize/dom/` | The page host. `live` diffs a paint into `Patch`, `wire.av` writes it as bytes with the generated `OP`/`ROWS`/`TAGS` table (`host_table`, checked by `make ui-host`), and the page echoes events through the host fn `avra_ui_event`. | See below. |

**Gap 1: the wire speaks DOM.** A `Patch` creates an `HtmlTag`, sets an `HtmlAttrName`, ships
CSS (`Style`) and CSS variables. A UIKit host reading that stream would have to recover
"button" from `<button>` plus classes. That means re-implementing a browser's reading of its own
markup, which is the very thing the doc rejected SwiftUI for. Two ways to keep "the same patch
stream":

- **Spike as briefed:** both hosts read the web wire, and the spike records what each host had to
  reverse. Cheap, but it measures a shape we would not ship.
- **Lean:** the same differ (`live`, the identity, the windowing) emits a **neutral** patch: create
  `Prim`, set `Attribute`, place, remove, listen. Its op and code table is generated the same way
  (`@derive(Codes)` and a `host_table` twin). The web wire becomes one projection of that patch,
  UIKit another, SwiftUI a third. That follows the "one source of truth, many projections"
  principle (P12). This is a std-ui change, so for the spike I would **write the host against a
  neutral frame**, list it as the std-ui change wanted, and not change std-ui yet.

**Gap 2: package C for the SDK.** std-ui's closure links `std_io.o`, `std_io_watch.o`,
`std_net.o` and `std_time.o`, all built for the Mac. An iOS build needs them built per SDK,
exactly as `wasm_objects` does for wasm. The runtime half is done (`make apple-runtime`), but the
manifest half (an `[link]` objects list per platform) is not.

## (b) THE design question: the scheduler and the main run loop

The facts:
- The runtime is cooperative on one OS thread. The OS stack is the main fiber, and tasks are
  fibers that switch only where they wait. Refcounts are plain, not atomic, so **no Avra value
  may be touched from a second thread**.
- When nothing is ready, the scheduler blocks in `kevent` (`poller_wait`).
- iOS requires `UIApplicationMain` on the main thread. It never returns, and from the iOS 27 SDK
  the scene lifecycle is mandatory. UIKit is main-thread only, and so is its text input: a
  `UITextField` delegate must answer synchronously.
- wasm already has a **hosted** mode: `AVRA_HOSTED` hands the scheduler's idle to the host
  (`avra_host_idle`), which suspends the stack and returns to the browser's event loop.

Measured on the Mac host, each the mean of 20k round trips over three runs (`build/spike-bench/`):

| Seam | Cost |
|---|---|
| Task to task over a channel (Avra, `--release`) | **0.19 µs** per round trip |
| Thread to main queue to thread (`dispatch_async_f` and a semaphore) | 3.4–6.1 µs |
| Thread to run-loop source (`CFRunLoopSourceSignal` + `WakeUp`) to thread | 4.6–7.4 µs |
| Thread to pipe in a kqueue, watched by `CFFileDescriptor`, to thread | 31–33 µs |
| `kevent` with zero timeout, nothing ready | 12.4 µs (this macOS; higher than expected, to recheck on the simulator) |

### Option A: the run loop hosts the scheduler, on one thread (the wasm model, natively)

UIKit owns the main thread's OS stack. Avra's program body and every task run as fibers on that
same thread.
- A run-loop source calls `avra_turn(budget)`, which runs ready fibers until all are parked or
  the budget (say 4 ms) is spent, then returns to the run loop.
- The kqueue fd is a run-loop source (`CFFileDescriptor`), so I/O wakes the loop. The next
  deadline is a `CFRunLoopTimer`.
- **A tap** runs the UIKit action on the main stack. It posts the act into the app's inbox
  (`App.door.send`), which is plain Avra on the same thread, and the turn runs. The handler
  itself runs in a task.
- **A task's wake** is either a fd or timer the run loop already watches, or a post from inside
  a turn.
- **What blocks:** nothing blocks the thread. A busy task is cut at the budget by the
  preemption tick, then the loop draws.
- **Text input** answers synchronously. `shouldChangeCharacters` can run the field's handler to
  completion within the call, if the handler does not wait.

Cost: about 0.2 µs per task hop, nothing crosses a thread, and no copies are made. The cost
is in the runtime: a `poller_wait` that returns to the host instead of blocking (the hosted path
already exists for wasm). One extra `kevent` per wake (12 µs here) can be dropped by reading
the events `CFFileDescriptor` reports. The risk is that a task doing heavy CPU work stalls the
UI up to the budget.

### Option B: Avra on its own thread, UIKit on main

The scheduler runs as it does today, blocking in `kevent` on a second thread.
- **Frames** go to main as owned bytes through `dispatch_async` (3–6 µs plus a copy).
- **Taps** go to Avra through an `EVFILT_USER` or pipe in the kqueue (5–30 µs).
- **What blocks:** nothing on main, but **synchronous answers are impossible**. A text field's
  delegate cannot ask Avra and wait without risking a deadlock. Measuring also goes the other
  way: the solver on the Avra thread asks UIKit for sizes. CoreText is thread-safe, but UIKit
  controls' `sizeThatFits` is not.

Cost: two thread hops per interaction, a copy per frame, and a second "who owns this value"
boundary. Text input, the hardest part, gets an asynchronous echo with a race between keystrokes
and the echoed text. That race is the bug class SwiftUI and React Native are known for.

### Option C: Avra owns main and pumps the run loop

`main` calls `UIApplicationMain` from a fiber, and the scheduler's idle runs
`CFRunLoopRunInMode` with a timeout. This is not viable: `UIApplicationMain` never returns, and
iOS expects to own the main stack's base. It is option A with the stacks swapped, and gains
nothing.

### Lean: Option A

The main thread is UIKit's, the program and its tasks are fibers on it, and the run loop drives
`avra_turn`. It is the wasm hosted mode, generalized:
- **What a native target answers:** "idle: return to the host until a source fires", with the
  kqueue fd and the next deadline given to the host's loop.
- **What `native/sources.av` already does:** it keeps its loop as written. Its inbox and frame
  task are unchanged, and only the bottom of the scheduler changes.
- **Measured before slice 1 ships:** the turn budget, and whether the preemption tick can end a
  turn.

## (c) How an app is declared: a first proposal (nothing built)

An app is a program plus a **bundle**: the files a target's loader needs beside the binary. The
concept is general. An iOS `.app` is one; others are a macOS `.app`, an Android APK's manifest,
and a wasm page's HTML and host JS, which the page build already writes by hand.

A manifest row, read by every bundling target:

```toml
[bundle]
id      = "dev.avra.board"   # CFBundleIdentifier / Android applicationId
name    = "Board"            # CFBundleName / label
version = "0.1.0"            # defaults to [package].version
icon    = "assets/icon.png"  # optional; each target makes its sizes
scenes  = ["main"]           # the scene names a program's `app` declares; default one
```

What the compiler generates for an Apple target, from the row and the program:
- **`<name>.app/`** holds the binary, `Info.plist`, and the icon set if one is declared.
- **`Info.plist`** holds `CFBundleExecutable`, `Identifier`, `Name`, `Version`,
  `PackageType=APPL`, `MinimumOSVersion` (the triple's release from `targets.av`),
  `UIDeviceFamily`, and `UIApplicationSceneManifest` with one `UISceneConfiguration` per scene,
  its delegate class being the runtime's.
- **The host shim:** an app delegate and a scene delegate in C via the Objective-C runtime, so no
  Swift is needed. It calls the program's entry on scene connect and hands the window to the
  realizer. It is runtime code, and lands like `avra_tick.c`, outside `runtime/*.c`.
- **Signing:** ad hoc on the simulator, which is what the witness does. A device needs a team and
  a profile, which is out of scope.

The key shape: a platform row in `targets.av` names its **bundle kind** (`None`, `AppleApp`,
later `AndroidApk` and `Page`), and `avra build` writes the bundle when the program's manifest
has a `[bundle]` and the platform has a kind. A program with no `[bundle]` builds a bare binary,
as today. Questions for the ruling:
1. Is the scene list declared in `[bundle]`, or derived from the program's `app` declaration?
   The lean is derived, with the row naming only the bundle's identity.
2. Does `avra run --target …-simulator` boot, install and launch, as the witness does? The lean
   is yes, so `run` means the same on every target.

## Asks for the ruling before slice 1

1. **Option A** for the scheduler, as a runtime change: hosted idle for native targets.
2. **Neutral frame or web wire** for the spike's patch stream, given gap 1.
3. **`[bundle]`** as the manifest row, with the bundle kind on the platform row.
