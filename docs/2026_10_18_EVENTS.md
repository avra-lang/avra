# Events: one model, validated per platform

Ticket avra-8sb5.59 (UI). DRAFT. Folds the owner's rulings of 2026-10-18.
Ground: `2026_10_15_MEMORY_AND_REPRESENTATION.md` Part 6 — an `on` seat IS a
fn field (`on click(x: int)` ≡ `click: fn(int) -> void? = null`), and
`.59` broadcasts. No code changes here; this is the shape.

## Today

`tree/node.av` keeps `EventKind` (Press, Input, Change, Submit, Dismiss;
`@word` + `@code` 1..5) by hand, and `tree/view.av` reads it by module
name. It is a second copy of what the components already declare. Keys are
data on the box (`keys: [bind(...)]`).

## Rulings

1. A shortcut is a `key` sub-component (APPROVED).
2. Events stay GENERIC. `on` is a seat on ANY component: a worker's
   `on message`, a trainer's `on epoch`, a button's `on press`. The seat's
   type says what it is (a fn seat is a call; a channel seat is a send —
   Part 6). UI is one client.
3. A seat a HOST delivers is validated against that platform's REAL events,
   from a table that is never hand-kept.
4. Weigh `key "ctrl+s" { save() }` as a general component rule.

## 1. The host vocabulary is derived (no hand list)

The program's host events are exactly its components' declared host seats.
Wire codes are DENSE small ints minted per program at build time (the
compiler knows every seat), one varint byte; a build fingerprint in the
handshake catches an older page and reloads its state instead of
mis-dispatching. The client keeps a node table by id; the existing Listen
patch sets a per-node SEAT BITSET there, and one delegated listener per DOM
event type checks the bit and sends (id, code). Zero bytes per node in the
HTML. `EventKind` and `@code` are deleted. (Cost of the bitset on the 100k
bench: to be measured when built.)

## 2. A platform's vocabulary is a TYPE, so validation is ordinary checking

A seat that a platform delivers names its form per target:

    on press @host(web: .Click, terminal: .Enter)
    on move  @host(web: .Mousemove)

`.Click` is a variant of the platform's event ENUM, so the check is the
compiler's existing variant check, did-you-mean included — no new
machinery, no string tables:

- **web**: `enum DomEvent`, GENERATED from the W3C `webref` event list
  (`w3c/webref`, branch `curated`, `ed/events.json`: 444 entries, 316
  distinct types today, each with its interface — `MouseEvent`,
  `KeyboardEvent` — and the element types it fires at). A tool
  (`tools/host_events.py`) regenerates `std-ui/.../dom_event.gen.av` from a
  PINNED webref commit; `make host-events` regenerates and diffs, so the
  table cannot drift from the source of truth and cannot be edited by
  hand. Same shape as `wire.gen.js` today.
- **terminal**: the decoder's own vocabulary. `terminal/keys.av`'s `Key`
  enum (Next, Back, Enter, Erase, Char, End, PageUp... Click, Wheel, Paste,
  FocusIn...) IS the table; nothing is generated, so it cannot disagree
  with the decoder.
- **a new platform** (native window, wasm host, TTY over ssh) supplies one
  enum; the seat's `@host(<target>: .Variant)` argument is checked against
  it.

The owner's case: a raw-element component (`dom_element`) declares its
seats OPEN over the web enum: `on <DomEvent>`. Then `on mouse_mv { ... }`
is the compile error

    no DOM event `mouse_mv` — did you mean `mousemove`?
    help: the web events are DomEvent (generated from the W3C webref list)

and, because webref carries each event's target elements, `on submit` on a
`div` is refused too ("`submit` fires at `form`"). The payload type of an
open seat comes from the event's interface (`MouseEvent` fields) — a v2
generated from the same source (WebIDL); v1 delivers the payload the
platform adapter already decodes.

Checked WHERE: at the component's declaration, for every platform it
names, regardless of the build target — a misspelling in a library is one
error in the library, not a surprise on the first terminal build. A seat
with no form for the build target is a WARNING at the use ("`hover` is
never delivered on the terminal"), because a missing form is a contract
fact (P9), not a mistake.

Seats between components (`on message`, `on epoch`) carry no `@host`: they
are fn-typed seats checked by type alone, exactly as today.

## 3. DOM → seats

No element carries a code list. The delegated listener per DOM event type
(table: seat → DOM event is the `@host(web: ...)` data itself, so the
mapping lives beside the declaring component and is the same value the
check read) tests the node's bit and sends (id, code). `press` on a web
button maps to `click` (which also covers Enter/Space on a focused button
natively). Broadcast (`heard_twice`) lets two `on press` on one node
attach in order.

## 4. Keys as a component

    key "ctrl+s" { on press { save() } }

An ordinary child: a `chord` argument (parsed and checked at the literal;
a duplicate chord in one scope is a check refusal) and one `press` seat.
Scope is tree position: it fires while its parent is on the focus path or
active. Terminal and web both resolve it by walking the tree, so there is
no side binding table and `Chord` stops living on the box. Implementation
lands on `ui-keys` (data already there: `tree/chord.av`, `bindings.av`),
replacing `keys: [bind(...)]`.

## 5. Should `key "ctrl+s" { save() }` be a general rule?

The owner asks why the component nests. Options:

- **A. Keep `{ on press { ... } }`.** Explicit, additive, but one extra
  level for the commonest case.
- **B. Infer: a component with exactly ONE event seat takes its block as
  that seat's body.** Short, but: (a) adding a second seat later silently
  changes the meaning of every existing use (a library change turns user
  code into something else, or an error far from the cause) — non-additive,
  against P9; (b) the reader can't see WHICH event (P7); (c) the count is a
  property of the component's *current* declaration, which the user may
  not have read (P1: an LLM guesses the rule right and the library breaks
  it).
- **C. Declare it: the component names its default seat.** The author
  writes `on press default`; the block of a use with no settings lines is
  that seat's body. Same short form, none of B's hazards:
  adding a seat changes nothing, because the default is named, not
  counted. `button "Save" { save() }` and `key "ctrl+s" { save() }` both
  work; `on press { ... }` stays valid everywhere.

**Recommend C.** It is a GENERAL rule of the component model (any
component, UI or not: `worker { reads: q }` could default `on message`),
not a `key` special case, and it is opt-in. Grammar fact to settle with the
owner: a block that holds only statements (no `name: value` or `on` lines)
is the default seat's body; a block that holds settings keeps today's
meaning. The two are disjoint at the first line, so the parser needs no
lookahead beyond the first token — but it is new surface, so it is the
owner's call.
