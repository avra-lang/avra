# Events: one model, validated per platform

Ticket avra-8sb5.59 (UI). DRAFT. Folds the owner's rulings of 2026-10-18.
Ground: `2026_10_15_MEMORY_AND_REPRESENTATION.md` Part 6 — an `on` seat IS a
fn field (`on click(x: int)` ≡ `click: fn(int) -> void? = null`), and
`.59` broadcasts. No code changes here; this is the shape.

## Today

`tree/node.av` keeps `EventKind` (Press, Input, Change, Submit, Dismiss;
`@word` + `@code` 1..5) by hand, and `tree/view.av` reads it by module
name. It is a second copy of what the components already declare. Keys are
data on the box (`keys: [bind(...)]`).

## Rulings

1. A shortcut is a `key` sub-component (APPROVED).
2. Events stay GENERIC. `on` is a seat on ANY component: a worker's
   `on message`, a trainer's `on epoch`, a button's `on press`. The seat's
   type says what it is (a fn seat is a call; a channel seat is a send —
   Part 6). UI is one client.
3. A seat a HOST delivers is validated against that platform's REAL events,
   from a table that is never hand-kept.
4. Weigh `key "ctrl+s" { save() }` as a general component rule.

## 1. The host vocabulary is derived (no hand list)

The program's host events are exactly its components' declared host seats.
Wire codes are DENSE small ints minted per program at build time (the
compiler knows every seat), one varint byte; a build fingerprint in the
handshake catches an older page and reloads its state instead of
mis-dispatching. The client keeps a node table by id; the existing Listen
patch sets a per-node SEAT BITSET there, and one delegated listener per DOM
event type checks the bit and sends (id, code). Zero bytes per node in the
HTML. `EventKind` and `@code` are deleted. (Cost of the bitset on the 100k
bench: to be measured when built.)

## 2. A platform's vocabulary is a TYPE, so validation is ordinary checking

A seat that a platform delivers names its form per target:

    on press @host(web: .Click, terminal: .Enter)
    on move  @host(web: .Mousemove)

`.Click` is a variant of the platform's event ENUM, so the check is the
compiler's existing variant check, did-you-mean included — no new
machinery, no string tables:

- **web**: `enum DomEvent`, PROVIDED at compile time from the W3C `webref`
  event list (`w3c/webref`, branch `curated`, `ed/events.json`: 444 entries,
  316 distinct types today, each with its interface — `MouseEvent`,
  `KeyboardEvent` — the element types it fires at, and whether it bubbles
  there). This is a TYPE PROVIDER (owner ruling): the pinned webref file is an
  ASSET of the package, and a provider case, once the `Expands` trait lands,
  turns it into the enum while the compiler resolves — no generated file to
  keep, nothing to edit by hand. UNTIL THEN a script
  (`tools/src/commands/host_events.av`) writes `std-ui/.../dom_event.gen.av` from the same
  pinned file, and `make host-events` regenerates and diffs it (the shape of
  `wire.gen.js` today); the provider replaces the script without changing a
  line that uses the enum.
- **terminal**: the decoder's own vocabulary. `terminal/keys.av`'s `Key`
  enum (Next, Back, Enter, Erase, Char, End, PageUp... Click, Wheel, Paste,
  FocusIn...) IS the table; nothing is generated, so it cannot disagree
  with the decoder.
- **a new platform** (native window, wasm host, TTY over ssh) supplies one
  enum; the seat's `@host(<target>: .Variant)` argument is checked against
  it.

The owner's case: a raw-element component (`dom_element`) declares its
seats OPEN over the web enum: `on <DomEvent>`. Then `on mouse_mv { ... }`
is the compile error

    no DOM event `mouse_mv` — did you mean `mousemove`?
    help: the web events are DomEvent (generated from the W3C webref list)

and, because webref carries each event's target elements, `on submit` on a
`div` is refused too ("`submit` fires at `form`"). The payload type of an
open seat comes from the event's interface (`MouseEvent` fields) — a v2
generated from the same source (WebIDL); v1 delivers the payload the
platform adapter already decodes.

Checked WHERE: at the component's declaration, for every platform it
names, regardless of the build target — a misspelling in a library is one
error in the library, not a surprise on the first terminal build. A seat
with no form for the build target is a WARNING at the use ("`hover` is
never delivered on the terminal"), because a missing form is a contract
fact (P9), not a mistake.

Seats between components (`on message`, `on epoch`) carry no `@host`: they
are fn-typed seats checked by type alone, exactly as today.

## 3. DOM → seats: a hybrid, from the same declared data

The owner asked whether one listener per DOM event type is enough: some
events do not bubble, and a delegated handler can swallow what a page needs.
So the host is HYBRID, and every choice below is read off the seat's
declaration and the webref row, never written by hand:

- **Delegate at the root, in the CAPTURE phase.** A capture listener on the
  root sees an event on its way DOWN to the target, whether or not that event
  bubbles, so `focus`, `blur`, `load` on an element and `mouseenter` are
  delegated too. One listener per event type still; the node table (a seat
  bitset set by the existing Listen patch) says who hears it.
- **Declared effects, applied synchronously.** `preventDefault` and
  `stopPropagation` cannot wait for a round trip to Avra, so they are part of
  the seat: `@host(web: .Submit, prevent: true)`. The JS applies them in the
  listener before sending (id, code); the program never decides them late.
- **A direct listener only where delegation cannot work.** Passive `scroll`,
  `touchstart` and `wheel` registrations (`{ passive: true }` is a property of
  the listener, not of the event), and events fired only on `window` or on a
  media element's own target (`resize`, `popstate`, `storage`, `ended`). The
  webref row says where an event fires, so the host table marks each event
  `Delegated` or `Direct(target)`; a seat's `@host` form picks nothing extra.

The mapping (seat to DOM event) is the `@host(web: ...)` value itself, so it
lives beside the declaring component and is the same value the check read.
`press` on a web button maps to `click` (which also covers Enter and Space on
a focused button natively). Broadcast (`heard_twice`) lets two `on press` on
one node attach in order.

## 4. Keys as a component

    key "ctrl+s" { on press { save() } }

An ordinary child: a `chord` argument (parsed and checked at the literal;
a duplicate chord in one scope is a check refusal) and one `press` seat.
Scope is tree position: it fires while its parent is on the focus path or
active. Terminal and web both resolve it by walking the tree, so there is
no side binding table and `Chord` stops living on the box. The standalone
`key` stays for shortcuts that belong to no control (PR #946).

**A shortcut on a control (owner ruling).** Any control may carry the chord
itself, and it fires THAT control's own press:

    button "Save" { shortcut: "ctrl+s", on press { save() } }

NAMING (settled): the setting is `shortcut:`. `key:` is already every
component's sibling IDENTITY (`item { key: r.id }`, `Stand.key`, the
keyed-list law of #938), and one word for two things would read a shortcut
as a list key. `key:` stays identity. The chord is parsed once and the node hears it through the same
`Key` machinery, so `shortcut:` is sugar for a `key` sibling whose press is
the control's press: live while the control or anything in it has the focus,
and a duplicate chord in one scope is the same refusal.

## 5. The default seat is an ANNOTATION (owner ruling)

The owner's question was why `key "ctrl+s" { on press { save() } }` nests.
Options weighed: keep it (A); infer the sole seat (B: non-additive, hides
which event runs, depends on a count the user never read); name it (C).
Ruling: C, spelled as an ANNOTATION on the seat, which needs no new grammar:

    component key(chord: string) {
        @default on press
    }

    key "ctrl+s" { save() }
    button "Save" { save() }

A block of statements — no `name: value` and no `on` lines — fills the
`@default` seat; a block with settings keeps today's meaning, and
`on press { ... }` stays valid everywhere. Adding a second seat later changes
nothing, because the default is named, not counted. At most one `@default`
per component (a `check` law, spoken at the declaration). It is a general rule
of the component model, not a `key` special case: any component, UI or not
(`worker { reads: q }` could default `on message`).

Grammar fact left to the parser's owner: a statements-only block is told from
a settings block at its first line (`name:` or `on`), which needs no
lookahead past the first token.
