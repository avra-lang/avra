# Spread `..` — everywhere you would expect, one law

Status: design for owner approval, no code. Epic: avra-8sb5.89 (nodes).
Base: main dbef52a1; probes ran on the tree compiler of `batch-nodes-3` (eb432a03).
PROBED = run; PROPOSED = not run.

## 0. The answer

`..e` contributes the entries of `e` at its place, inside the literal or the
argument list it stands in. Left to right, **the later entry wins**. One typing
law serves every seat (§2). The spelling is the one the language already has
(`type B = { y: int, ..A }`, and `T { ..${inits} }` in a template), so nothing
new is learned — only more seats take it.

| seat | spelling | status today | proposal |
|---|---|---|---|
| record literal | `P { ..base, x: 1 }` | PROBED refused: "expected `}` to close the trailing block" | phase 1 |
| `with` | `base with { x: 1 }` | PROBED works | becomes sugar for the line above (§4) |
| list literal | `[..xs, 3]` | PROBED refused: "expected `]` to close the list" | phase 2 |
| map literal | `{ ..m, "b": 2 }` | PROBED refused | phase 3 |
| call arguments | `f(..opts)` | PROBED refused: "expected `)` to close the arguments" | phase 4, a RECORD into named seats |
| list into variadic | `f(..xs)` | PROBED refused; no variadic seat exists | DEFERRED (§5) |
| patterns | `[first, ..rest]`, `P { x, ..rest }` | no list or record pattern exists to extend | DEFERRED (§6) |
| type declarations | `type B = { y: int, ..A }` | works; `...A` refused with its own voice | unchanged |

## 1. The paradoxes, and how each collapses (P6)

**`with` vs `P { ..base, x: 1 }`.** One of them would be a second spelling. They
are one construct: `base with { x: 1 }` is defined as `T { ..base, x: 1 }` where
`T` is `base`'s type. `with` stays as the single-source update sugar a reader
wants, the literal is the general form (two sources, a spread in the middle), and
the compiler keeps ONE node: `Expr.With` is deleted, its meaning a `means()`
template over `StructLit` (the template machinery of step 6 — see
`docs/2026_10_16_FOLD_AND_MEANS.md`). Nothing a user wrote changes.

**`[..a, y]` vs `a.concat([y])` / `flatten`.** `concat` is a method that is
right in a chain (`xs.map(f).concat(ys)`); the literal is right when a written
element is mixed in (`[x, ..xs]`, `[..a, 0, ..b]`). They lower to the same single
sized allocation. The idiom rule `style.concat_literal` says: a `concat`
or `flatten` whose operand is a list literal becomes a spread (`[x].concat(xs)` →
`[x, ..xs]`); and a spread literal with no written element (`[..a, ..b]`) is
spelled `a.concat(b)`. Each form owns the territory the other cannot read well —
the rule is the boundary, not a preference.

**A `List` into seats.** A list has no static length, so it cannot fill seats
(`f(..xs)` with `f(a, b)` is unknowable at compile time). What CAN be spread into
seats is a RECORD, whose fields are known: that is named arguments (§3.4).

## 2. The one typing law

> `..e` is accepted where `e`'s type owns the seat's entries: the entries `e`
> contributes are exactly the entries the seat could have written by hand, each
> typed as if written. An entry that the seat cannot take is refused at the `..`,
> naming it.

Per seat (PROPOSED):

- **record literal `T { … }`**: `e : T` (nominal: the named type, never a
  lookalike — P9). Every field of `T` is filled exactly once after the override
  order below, so `type.struct_fields` still holds ("every declared field
  appears exactly once") counted AFTER the spread, not before.
- **list literal `[…]` of `X`**: `e : List<Y>` where `Y` is accepted by `X`
  through the same door a written element uses (`agreed`), so `[..ints, null]`
  lifts like `[1, null]` does.
- **map literal of `V`**: `e : Map<string, V'>` with `V'` accepted by `V`.
- **call arguments**: `e` is a record `R`; every field of `R` names a seat of the
  callee, its type is accepted by that seat, and no seat is filled twice.

Same door as a written entry, so a spread can never be a path around a law the
written form obeys. THE FAILURE TO AVOID: a spread typed by its own looser rule
(structural, "extra fields ignored") — that is a second type system.

## 3. Semantics

### 3.1 Override order

Left to right; later wins — TypeScript's order, and the one an author expects.
`P { ..a, x: 1 }`: `x` is 1. `P { x: 1, ..a }`: `x` is `a.x`. A written field
that a LATER spread of the same record type fully overwrites is dead; it is
refused (`type.spread_shadows`: "`x` is written, and the `..a` after it
overwrites it") rather than ignored, because a dead write is a mistake the
language can see. For maps the same order; an overwritten key KEEPS its first
place (the map law: insertion order, overwrite keeps the place). Lists have no
override — a spread appends in place.

### 3.2 Evaluation and ownership

Operands are evaluated once, left to right. A record spread copies the fields it
contributes (structural sharing: a managed field's box is retained, not cloned,
spec 11.5), a list or map spread builds a NEW container sized once (the runtime's sized array),
so no alias is created and the memory pass sees an ordinary owned result. A
`mut` operand is read, never written through (a spread is a read).

### 3.3 Precedence

`..` takes a whole expression up to the next `,`, `}`, `]` or `)`, as TypeScript's
spread does: `{ ..opts ?? defaults, x: 1 }` spreads `opts ?? defaults`. It is not
a binary operator; it appears only as an entry. A third dot is refused with the
voice that already exists ("a spread is written `..R` — two dots") — PROBED.

### 3.4 Named arguments

`f(..opts)` with `opts : R`: sugar for `f(a: opts.a, b: opts.b)` over exactly the
fields `R` declares, each read once. A positional argument before it and a named
one after it compose as written; a seat written twice (by hand and by the spread)
is refused, like a duplicate named argument today. Defaults fill the seats no
entry names, as today.

## 4. What dies

- `Expr.With` (the node, its builder, its typing and lowering arms): `with` is a
  template over the spread. The deletion is measured when phase 1 lands, not
  claimed here.
- The hole-only spelling in the struct-literal grammar (`sp:".." vn:HOLE`): the
  template run-hole `..${inits}` becomes ONE case of the general `..expression`
  — a code-list operand — so the grammar has one rule, not a hole rule beside an
  expression rule.
- Every head-plus-tail `concat` in the compiler's own source (`[x].concat(xs)`),
  by the idiom rule. Count taken at phase 2.

## 5. Variadics — deferred

`fn f(..rest: List<int>)` would let `f(1, ..xs)` and `f(1, 2, 3)` both fill it.
It touches mono (arity), the seat law, and named arguments; it is a language
feature of its own, with its own design. Not decided here.

## 6. Patterns — deferred

`[first, ..rest]` and `P { x, ..rest }` presuppose list and record patterns, which
do not exist (`pattern` has variants, literals, `_` and binders only; struct
destructuring in `let` is refused — CLAUDE.md "The subset today"). Their
exhaustiveness (`[]`, `[x, ..rest]`) is a design round of its own. Spread in a
pattern is the LAST phase, after the patterns it extends exist.

## 7. Phases (each lands green and deletes or adds nothing it cannot test)

1. Record literal spread + `with` as its sugar; `Expr.With` dies. Witness: every
   `with` test passes unchanged through the template; new cases for override
   order, the shadowed write, a nominal mismatch, a managed field.
2. List literal spread + `style.concat_literal`.
3. Map literal spread.
4. Named-argument spread.
5. (Separate designs) variadics; list and record patterns, then spread in them.

Each phase needs: grammar rule edit (`..` entry in the seat's rule, no new token),
one typing arm per the law in §2 through the shared agreement door, one lowering
(the existing `Alloc`/`push` shapes — no new IR variant is expected, to be
confirmed per the IR protocol in CLAUDE.md), a diagnostic kind with a golden
(`type.spread_*`), and a mutation witness per phase.

## 8. Open questions for the owner

1. `with` as sugar (above) or `with` retired outright once the spread exists? The
   doc recommends sugar: a single-source update reads better as `x with { … }`
   than as a literal restating the type, and it costs nothing once the node is a
   template.
2. Should a spread of a DIFFERENT record type be accepted when every field it
   contributes belongs to the target (TypeScript's structural reading)? The doc
   says no (P9: boundaries are contracts, and the nominal types are the
   contract); a conversion is written out.
3. Variadic seats: want them at all, or is a list argument the permanent answer?
