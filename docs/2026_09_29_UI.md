## 0. The verdict on WEB_UI v5

WEB_UI's constitution is strong: proved/derived/measured, record + profile,
drafts, segment-commit event turns, identity paths, the placement plan,
the inspector, the gallery, a11y as a subsystem. Keep all of it. It has
seven defects, ranked by cost of fixing later:

| # | Defect | Why it matters |
|---|---|---|
| 1 | **Scoped to the web.** "Native must stay possible" is how native becomes impossible. Slice 1 names the vocabulary `@std/web`. | The node vocabulary is the most expensive thing to rename once apps exist. It must be platform-neutral from the first commit. |
| 2 | **A constitution with no writing surface.** ~60 laws, ~25 surface words, and the canonical example (§24) is ceremony. | P1 is measured on what a model writes. §24 makes every destructive button hand-write `ask(confirm(…))`: the exact omission LLMs make. |
| 3 | **Category errors survived the review.** | `state … at .server` (server truth is a model, never `state`); `.tab` (web-only word); `on .web { hover }` (hover is a capability iPads and Macs have too); `State<T>` (a new type where a word suffices). |
| 4 | **The screen is treated as the product.** | Within a decade, most operations of most apps come from agents and OS assistants. Pixels are one projection of intent. |
| 5 | **No cross-target runtime architecture.** | No op protocol, no layout semantics, no realizer contract. Without them, "iOS later" is a rewrite. |
| 6 | **The tour contradicts it.** | AVRA_TOUR §9 writes `on appear { self.robots = fleet_client.robots()? }`, which copies truth into state: refused by WEB_UI §16 row 1. The flagship example teaches the anti-pattern. |
| 7 | **Doc form.** 700 of 2 100 lines are resolved threads. | A normative doc holds rules. History moves to a decision log (T15's own rule: "move rules, not history"). |

## 1. The thesis

> **An app is one program of intent — data, actions, views — and every
> surface it appears on is a compiled projection with a receipt.**

A web page, an iPhone screen, a watch complication, a Siri phrase, an
agent's tool list, a terminal UI and a printed invoice are projections of
the same declarations. WEB_UI's thesis ("where code runs is compiled, not
chosen") is one axis of this one. The other axis: **how intent is realized
is compiled, not chosen**, with the same three kinds of decision
(proved · derived · measured), the same plan artifact, and the same
override at every boundary.

```
 intent        @model · @action · view · screen · state          (one program)
   │
 semantic      a tree of interaction contracts: role, content,   (@std/ui)
 tree          affordances, layout intent, style roles
   │
 plan          placement (build · server · device · worker · gpu)
   │           + realization per target                          (a diffable artifact)
   ▼
 op stream     create · set · insert · move · remove · listen …  (the UI ABI, §4.2)
   │
 realizers     html · dom · uikit · appkit · android · tui · test (small, per target)
               + projections: agent tools, OS intents, widgets, voice, print
```

## 2. The writing surface

### 2.1 Hello

```avra
use @std.ui.{app, text}

app hello { text "Hello" }
```

```
$ avra run hello.av                 # web, dev server, opens the browser
$ avra run hello.av --on ios        # simulator
$ avra run hello.av --on terminal   # the same tree, in the terminal
```

One line of intent, three realizations, zero configuration. That is the
cold-start bar.

### 2.2 A real app, every target

```avra
use @std.ui.{app, screen, list, link, text, toggle, picker, button, form, title, toolbar, icon}

@model
type Board = { name: string where it.length in 1..80, owner: User }

@model
type Card = { title: string where it.length in 1..200, done: bool = false, board: Board }

enum Show { All Open Done }

@action(auth: member_of(b), impact: .routine)
fn add_card(b: Board, title: string) -> Card { Card.insert(board: b, title: title) }

@action(auth: member_of(c.board), impact: .routine)
fn set_done(c: Card, done: bool) -> Card { c.update(done: done) }

@action(auth: owner_of(b), impact: .destructive with { safeguard: .trash(days(30)) })
fn delete_board(b: Board) -> Board { b.trash() }

state appearance: Appearance = .system at .account    // follows the user to every device

app boards {
    name: "Boards"
    icon: embed("icon.svg")
    home()
    settings()
}

screen home() {
    title "Boards"
    icon .grid
    list Board.mine() { b ->
        link board(b) { text b.name }
    }
}

screen board(b: Board, state show: Show = .all) {    // the route IS the signature
    title b.name
    toolbar {
        picker show
        button "Delete board" { delete_board(b) }      // safeguard discharged by default (§3.4)
    }
    list b.cards.filter { show.admits(it) } { c ->
        toggle c.title {
            value: c.done
            on change { set_done(c, it) }
        }
    }
    form add_card(b)                                   // fields + validation from the action
}

screen settings() {
    title "Settings"
    icon .gear
    form {
        picker "Appearance" { value: appearance }
    }
}
```

No fetch, no loading flag, no store, no route table, no API layer, no
per-platform file, no manifest, no confirmation dialog written by hand.
Each still exists — in the plan, printed:

```
$ avra explain screen board
board(b: Board, state show: Show = .all)
  route     web /board/{b}?show=open · ios boards://board/{b} + universal link · android app link
  reads     b · b.cards filtered by show — live · device replica (§3.8)
  writes    set_done      speculative (.routine)
            add_card      speculative (.routine) · form derived: title 1..200
            delete_board  pending until receipt (.destructive)
                          discharge (derived): undo toast, 30 d trash — ios: destructive role
  realizes  web      server HTML 3.8 KB → island 6 KB ±2 (estimate)
            ios      UIKit: navigation item, table, switch cells
            android  Views: toolbar, RecyclerView, MaterialSwitch
            terminal list, [x] toggles, a menu for the toolbar
  agents    tools set_done · add_card · delete_board (mandate required: .destructive)
            ios App Intents "Add a card to <board>" · android AppFunctions · MCP · WebMCP
```

### 2.3 The words

A model has to learn TEN words. Everything else (`list`, `button`,
`toolbar`, `form`) is an ordinary imported component (COMPONENT_EXPANSION),
found by `use`, documented by its `///`, and never reserved.

| Word | Is |
|---|---|
| `app` | the root: name, icon, top-level screens, targets, reach |
| `screen` | a navigable destination: a fn whose signature is its route |
| `view` | a reusable piece of UI that may own `state` |
| `state` | a place: in a body (owned here), in a parameter (owned by the caller) |
| `at` | the state policy profile (WEB_UI §3.1, §4.3) |
| `@model` | data with identity (the ORM) |
| `@action` | the only door to authoritative change (AUTHORITY) |
| `draft` | a branch of truth that knows its base (WEB_UI §4.6) |
| `task` | async work owned by a view's life (WEB_UI §6.3) |
| `animate` | a write that carries its transition (WEB_UI §6.4) |

`page` retires into `screen` (one word across targets; the tour already
uses `screen`). `State<T>` retires into `state` parameters (§3.2).

## 3. The collapses

Each row is a place where WEB_UI (or the industry) chose a side. P6 says
the forced choice means the model is wrong.

### 3.1 URL state IS the screen's parameters

- Forced choice elsewhere: a route table + query-string parsing + a
  separate state store + deep-link config per platform.
- **Here:** `screen board(b: Board, state show: Show = .all)`.
  - Required parameters form the path; `state` parameters form the query.
  - A model parameter encodes as its identity; the codec is derived, or
    the type is refused at the screen (WEB_UI §16 "a profile's type fits
    it").
  - Writing `show = .open` inside the screen REPLACES the navigation
    entry. That is `.url` state, with no `at .url`.
  - `link board(b)` and `go board(b)` are typed calls. A broken link is a
    type error. A renamed screen renames every link.
  - One declaration projects: web routes + history, iOS universal links
    (+ `apple-app-site-association`), Android app links (+
    `assetlinks.json`), state restoration on every native target, and the
    agent's "open" tool.
- The `.url` profile retires; `at .url` on a body `state` is refused with
  "a screen's URL is its `state` parameters — move `show` into the
  signature".

### 3.2 A `state` parameter is a binding

- **The law:** a `state` parameter is a place owned by whoever called you.
  For a view, the caller is a parent view. For a screen, the caller is the
  navigator, which stores it in the route (§3.1). One word, one meaning.

```avra
view stepper(state n: int) {
    row {
        button "−" { n = n - 1 }
        text "${n}"
        button "+" { n = n + 1 }
    }
}

view cart_line(l: Line) {
    state qty: int = l.qty
    stepper(qty)                  // a place: bound
    stepper(l.qty + 1)            // refused: "has no place to write — pass the state it reads"
}
```

- Retires WEB_UI's `State<T>` seat type, and sidesteps F3005 (a `mut` seat
  is never assigned whole) without a wrapper type: the compiler lowers a
  `state` seat to the `Cell` it already is ("an identity is a `Cell`").

### 3.3 Server truth is never `state`

- **Two kinds of value in a view, never interchangeable:**
  - an OBSERVATION: a model query, a `@get` api fn, any read-only
    idempotent call. Read in render. Suspends while pending, fails to the
    nearest `failed { }`, stays live.
  - a PLACE: `state`. Written by the view, its caller, or the navigator.
- So `state … at .server` is a category error and retires. Server truth is
  a `@model`; a view observes it; an `@action` changes it.
- The HTTP verbs map onto the same split: a `@get` fn is an observation
  (cacheable, prefetchable, usable in render); a `@post` fn is an action.
  An api the program declares needs no hand-written client on any target.
- The tour's §9 becomes:

```avra
screen fleet() {
    title "Today: ${fleet_api.robots().length} robots"   // observed, live
    for r in fleet_api.robots() { robot_row(r) }
}
```

### 3.4 Safeguards are discharged by default, visibly

- WEB_UI §7.2's law stays: every invocation site discharges its action's
  safeguard.
- What changes: the DEFAULT discharge is derived from the action's impact
  record and the target's idiom, printed by `explain`, and overridable.

| Impact + safeguard | web | iOS | Android | terminal | agent |
|---|---|---|---|---|---|
| `.destructive` + `.trash(d)` | undo toast | undo toast, destructive role | snackbar with Undo | `undo` hint line | mandate |
| `.destructive`, no recovery | confirm dialog naming the object | action sheet, destructive role | alert dialog | typed `y/N` | mandate |
| `.reversible` | undo toast | undo (shake-to-undo registered) | snackbar | hint | mandate |
| `.external` | "Sending…" → receipt wording | same | same | spinner line | mandate + budget |

- `button "Delete board" { delete_board(b) }` is therefore complete.
  Writing `ask(confirm(…))` replaces the derived discharge. An explicit
  `discharge: .none` needs a waiver (AUTHORITY §10).
- Why this is sound: the obligation is the action's; the site only chooses
  HOW. Deriving the how is P12 applied to safety, and it removes the most
  common omission instead of refusing it after the fact.

### 3.5 Capability, not platform

- `on .web { hover { … } }` is wrong: iPadOS, macOS and Android desktop
  have hover; touch-only browsers do not.
- **Environment queries** name the capability: `when hover { }`,
  `when compact { }`, `when keyboard { }`, `when reduced_motion { }`,
  `when pen { }`. They work on every target and on the server (as a CSS
  media/container query on the web; as a trait on native).
- `on .ios { }` stays, for real product divergence only (a platform
  feature, a platform convention). `explain` lists each as "adapted".

### 3.6 Native look and brand look are one mechanism

- Forced choice elsewhere: Flutter and Compose Multiplatform draw their own
  pixels (one brand, uncanny on iOS); React Native and SwiftUI use the
  platform (native, harder to brand).
- **Here:** controls are native realizations of semantic roles; their LOOK
  is a theme over style roles (WEB_UI §12).
  - `.native` is a theme that maps roles to the platform's own tokens:
    Dynamic Type, system colors, SF Symbols; Material You dynamic color;
    the web's user preferences.
  - A brand theme maps the same roles to your tokens (DTCG / Figma).
  - A theme applies to a subtree: brand the marketing screens, keep the
    settings native. One `theme:` setting, inherited through the
    environment.
- The control stays native either way: text input, autocorrect, IME,
  accessibility and haptics are the platform's, always.

### 3.7 One action, every door

An `@action` is written once and derives every door it can be invoked
through, under ONE authority model and ONE safeguard obligation:

| Door | Derived |
|---|---|
| button, menu item, swipe action, context menu | from `button …{ action(…) }` at the site |
| form | `form add_card(b)`: fields, `where` validation on the client, refusals placed per field |
| keyboard shortcut, command palette | `hotkey .primary + "k"` (`.primary` = ⌘ on Apple, Ctrl elsewhere) |
| CLI | `avra run app -- add-card --board 7 --title …` via `@std/cli` |
| agent (MCP, WebMCP) | a typed tool; approval from impact + mandate (AUTHORITY §11) |
| OS assistant | iOS App Intents (Siri, Shortcuts, Spotlight), Android AppFunctions |
| widget / notification button | an interactive glance (§5.3) invokes it in the background |

No second list to drift. An action that must not appear on a door says
so: `@action(…, doors: [.ui, .cli])`.

### 3.8 The device cache is the same ORM

- Forced choice elsewhere: a server database + a separate client cache
  library (React Query, Apollo, Core Data) + hand-written sync.
- **Here:** the client holds a PARTIAL REPLICA of the models it observes,
  in the same `@std/sqlite` the server uses (a file on native; SQLite-wasm
  over OPFS on the web).
  - The compiler knows every query a screen reads, so the server computes
    exactly that subset and pushes diffs on commit (the Zero / Linear
    model, derived rather than configured).
  - Actions apply speculatively to the replica (as their impact permits)
    and rebase on the receipt (AUTHORITY §3).
  - Offline READS of server-authoritative data are therefore free; offline
    WRITES queue as intents (WEB_UI §7.4).
- `.replicated` stays reserved (WEB_UI §4.5). This is server authority with
  a local replica, not multi-master.

### 3.9 Tests are a realization

- The TEST realizer applies the op stream to an in-memory semantic tree.
  Every interaction test runs headless, in milliseconds, against the same
  semantics every target renders.
- Pixel goldens per target (browsers, simulators) are a second, slower
  layer — never the only one (WEB_UI §9.3).

## 4. Architecture — one core, many realizers

### 4.1 The semantic vocabulary (`@std/ui`)

Platform-neutral data components. Each names an INTERACTION CONTRACT
(WEB_UI §10.1), never a widget.

| Group | Roles |
|---|---|
| content | `text` · `heading` · `image` · `icon` · `video` · `badge` · `progress` |
| input | `button` · `link` · `toggle` · `field` · `picker` · `slider` · `stepper` · `date` · `search` |
| collections | `list` · `grid` · `table` · `section` (keyed, lazy by default) |
| structure | `row` · `column` · `stack` · `scroll` · `spacer` · `divider` |
| navigation | `app` sections · `screen` · `toolbar` · `menu` · `tabs` · `split` |
| layers | `sheet` · `alert` · `popover` · `toast` · `tooltip` |
| escape | `canvas` (+ semantic peer) · `foreign` (a platform view, typed) |

- Realization is a table per role per target, e.g. `toggle`:
  `<input type=checkbox role=switch>` · `UISwitch` · `MaterialSwitch` ·
  `NSSwitch` · `[x]` · "Haptics, on, switch" spoken.
- A role a target cannot realize is refused FOR THAT TARGET, at the node:
  "`canvas` needs a peer on `terminal` — add `peer:` or `on .terminal
  { … }`".

### 4.2 The op stream — the UI ABI

The compiled core never touches a platform. It emits ops; a realizer
applies them.

| Op | Meaning |
|---|---|
| `create(id, role, origin)` | a node, with its `OriginId` (WEB_UI §3) |
| `set(id, prop, value)` | a property: text, value, style role, a11y |
| `insert(parent, id, before)` · `move` · `remove` | structure |
| `listen(id, event)` | route an event back as a turn |
| `focus` · `announce` · `scroll_to` | the imperative, as state (WEB_UI §6.6) |
| `measure(id) → size` | the ONE synchronous call back into the realizer (text, native controls) |

- Batched per committed segment (WEB_UI §6.1): one segment, one patch.
- Versioned by "growth crosses, moving refuses".
- Realizers: `html` (SSR, prints the first tree) · `dom` (JS, small) ·
  `uikit` (Objective-C runtime through the C ABI) · `appkit` · `android`
  (Views through JNI) · `tui` · `test`. Each is a package; each carries a
  byte budget.
- The exact patches of WEB_UI §5.2 are the COMPILER's; the realizer never
  diffs. This is what makes a realizer small enough to write per target.

### 4.3 Layout — one semantics, two engines

- **The semantics:** a named subset of CSS flexbox + grid (`row`,
  `column`, `stack`, `grid`, `scroll`, `wrap`, `spacer`, aspect ratio,
  intrinsic sizing). Chosen because the web must lay out WITHOUT script
  (server HTML, WEB_UI §11.2), and this subset is proven portable (Yoga
  and Taffy implement it).
- **The engines:** the browser on the web; ONE Avra layout engine on every
  other target (first behind the C wall over Yoga's C API, then native
  Avra), placing native views absolutely.
- **The check:** geometry equivalence between engines, within a stated
  tolerance, over the gallery corpus. A layout that differs is a failing
  receipt, not a surprise on a device.

### 4.4 Threads and time

- Event turns start on the platform's main thread: gesture validity, text
  input and `preventDefault`-class decisions are synchronous there
  (WEB_UI §13 gesture law, every target).
- Derived work runs on the cores by the fork law (BEND §4); `parallel { }`
  becomes a Worker pool on the web, threads on native.
- Frame law (WEB_UI §14): a main-thread handler carries `@cost(steps:
  ms(8))` by default, 120 Hz targets `ms(4)`.

### 4.5 The platform co-owns state

WEB_UI §11.5 generalizes unchanged: selection, composition, autofill,
scroll, keyboard, dictation and accessibility actions belong to the
platform on every target. The realizer reports; the core never assumes it
is the only writer.

## 5. Targets

### 5.1 The matrix

| Target | Realizer | Shell (a projection) | Toolchain | Ladder |
|---|---|---|---|---|
| web | `html` + `dom` + WASM | `index.html`, service worker, manifest | none extra | rung 1 |
| terminal | `tui` | none | none extra | rung 1 |
| iOS / iPadOS | `uikit` | `.app` bundle, `Info.plist`, entitlements | Apple SDK + signing | rung 4 |
| Android | `android` | Activity shim, manifest, `.aab` | NDK + SDK | rung 6 |
| macOS | `appkit` | `.app` bundle | Apple SDK | rung 6 |
| Windows, Linux | WinUI / GTK | installer | per platform | later |
| watch, TV, visionOS | templates + focus engine | per platform | per platform | later |
| CarPlay, Android Auto | TEMPLATES only | entitlement | per platform | later |

- `app { targets: [.web, .ios, .android] }` — the build refuses a node a
  declared target cannot realize, and `explain` prints portable · adapted
  · missing per screen (WEB_UI §12).
- **Why UIKit and Views, not SwiftUI and Compose:** both are reachable
  from compiled Avra through the C ABI (Objective-C runtime, JNI), both
  are accessible and mature, and neither makes us run a second diffing
  framework under our own. SwiftUI and Compose are `foreign` islands where
  only they offer a feature.
- **The honest exceptions:** WidgetKit and Live Activities accept only
  SwiftUI; Android widgets use Glance or RemoteViews. Glances (§5.3) are
  restricted enough to translate, so those targets GENERATE Swift / Kotlin
  as a projection and need `swiftc` / `kotlinc`. Printed, never hidden.

### 5.2 Template targets prove the design

CarPlay, Android Auto, watch complications and voice accept no arbitrary
pixels. A semantic-first tree PROJECTS onto their templates (a `list` of
rows with actions is a CarPlay list template); a pixel-first framework
cannot. The same projection answers voice: every node already has a role,
a name and a value.

### 5.3 Glances — widgets, complications, live activities

```avra
glance today() {                      // a pure fn of a snapshot, on a timeline
    refresh: every(mins(15))
    heading "Picked today"
    text "${Harvest.today().sum(it.grams) / 1000} kg"
    button "Stop all" { stop_all() }  // interactive widget = an action door (§3.7)
}
```

- A restricted view: no `state`, no `task`, no arbitrary gesture. Refused
  with the rule's name when it reaches for one.
- Projects to: iOS widgets + Live Activities, Android widgets, watch
  complications, a PWA badge/notification, the lock screen.

### 5.4 Platform APIs — three layers, every target

| Layer | Web | iOS / macOS | Android |
|---|---|---|---|
| L0 generated, typed | WebIDL (w3c/webref) | Objective-C headers (clang) | SDK metadata |
| L1 portable packages | `@std/camera` · `location` · `notifications` · `haptics` · `share` · `biometrics` · `purchases` · `files` · `contacts` — one API, typed errors, each a pause point | ← same | ← same |
| L2 components | `visible { on enter { } }` · `hotkey …` · `drop files { }` · `scanner { }` | ← same | ← same |

- **Reach is declared once** (WEB_UI §13) and projects to: `Info.plist`
  usage strings, the Android manifest, the web's Permissions-Policy and
  CSP — and **the App Store privacy label and the Play Data safety form**,
  derived from reach + `@personal`. A privacy label that is a compiler
  output cannot lie.
- A permission prompt is a pause point answering `Result<_, Denied>`;
  "ask at the moment of use" is the default realization.

## 6. Navigation and app structure

- An `app` lists top-level screens; the platform decides their chrome:

| Form factor | Realization of `app { home()  settings() }` |
|---|---|
| phone | tab bar |
| tablet, desktop | sidebar + split view |
| web | top or side nav by container width |
| watch | vertical pages |
| TV | top tabs, focus engine |
| car | tab template |

- `link board(b)` / `go board(b)` push; the back gesture, the browser's
  history, Android's predictive back and iOS's swipe-back are ONE stack.
- `sheet`, `alert`, `popover` are layers shown while an optional is
  present (WEB_UI §6.6); on the web they are `<dialog>` / Popover API.
- `split { list … detail … }` collapses to a push on compact widths. The
  selection is `state`, so it survives the collapse.
- Icons are semantic names (`.grid`, `.gear`) mapped to SF Symbols,
  Material Symbols and an SVG set, per theme.

## 7. Agents are users

- **Read:** an agent reads the SEMANTIC TREE (roles, names, values,
  identity), never pixels. Computer use without screenshots.
- **Write:** only through actions (WEB_UI §9.3). A visual refactor never
  changes an automation contract; page content never steers a privileged
  tool.
- **Surfaces, derived (§3.7):** MCP server, WebMCP (the web proposal),
  App Intents, AppFunctions.
- **Generative UI:** an agent composes a `dyn View` from the app's
  catalogue; the compiler validates the whole composition (WEB_UI §9.3).
- **Delegation:** mandates bound what an agent may do unattended
  (AUTHORITY §11).

## 8. The dev loop

| Tool | What it does |
|---|---|
| `avra dev` | web + every connected simulator and device, one edit → all targets |
| hot reload on device | a DEV build embeds the evaluator and receives IR over the network; identity by source anchor keeps state (WEB_UI §6.2). Release builds never carry it. |
| gallery | views × states × TARGETS in one grid, side by side (WEB_UI §9.3) |
| inspector | the same rows (WEB_UI §9.4) on every target: an overlay in the browser and on device |
| traces | a bug report IS a trace: deterministic segments + receipts. `avra replay bug.trace --on ios` reproduces it; a fixed bug keeps its trace as a test. |
| state coverage | from the types, the gallery enumerates reachable UI states; small-scope checking runs every sequence of ≤ k actions over the fixtures and asserts no refusal, no unhandled failure, a11y intact |

## 9. The future, made present

## 15. Syntax — one head/body rule

Tour: `2026_09_29_UI_TOUR.md` (v2).

| Rule | Form | Examples |
|---|---|---|
| a DECLARATION's head is its name + params | `word name(params) { config · children }` | `app`, `screen`, `view`, `glance`, `product`, `theme`, `agent`, `deploy` |
| an INSTANCE's head is its props | `word(props) { body }` · one positional prop drops the parens | `toggle(done, title)` · `text "Hi"` · `card_detail(c)` — a view is instanced like any component |
| HEAD = WHAT: data, binding, label, destination, meaning | positional first, named after | `image(c.photo, alt: c.title)` · `link("Edit", to: form(c))` · `map(site)` |
| BODY = HOW: children, look (`key: value`), behaviour (`on event { }`) | bare statements run on the primary event | `button("Delete") { b.delete() }` |
| a control's first prop is a PLACE | state, a `state` param, a model field | `toggle(dense)` · `picker(show)` · `field(c.note.text, "Note")` |
| a NULLABLE head presents | absent → nothing, present → the body | `detail(open) { c -> … }` · `image(c.photo)` · `badge(due?.relative())` |
| a collection head renders by its type's view | `view for T` · a body overrides | `list(b.cards)` · `grid(Board.all())` |
| `on` is events only | platform and capability are VALUES read by `if` | `if hovered { … }` · `if compact { … }` · `if platform is .ios { … }` (lowered to CSS / traits where possible) |
| a destination is a value | a screen call, a row (its `home()`), a `form(…)` | `link(to: i.board)` · `remind(…, open: c)` |

Retired from v1: `when` (clashed with the `when` expression), `on .ios`,
settings carrying meaning (`map { center: … }`), `hotkey` blocks (a
`key:` prop on the control; menus and palettes derive from it),
`catalogue` (the app's views are the catalogue), `task` for sync work.

## 16. Data — homes, doors, flows

**The collapse: a `state` is a one-row model; a model is a table of
state.** Both take `at`; both have a home; both sync by it.

| `at` | Lives | Reaches | Authority |
|---|---|---|---|
| `.view` | memory | this view | this view |
| `.window` | restoration store | this window | this window |
| `.device` | local SQLite | this device, its widgets and extensions | this device |
| `.account` | local replica + server | every device I sign into | server, per principal |
| `.shared` (a model's default) | partial replica + server | everyone `access` admits | server |
| `.room(x)` | relay | everyone in the room, lossy | none |
| external | their system | via receipts, cached by freshness | them |

**Doors are derived from the model's policy.** `@model(access: …,
delete: …, trash: …)` gives `create`, per-field `update` and `delete` as
named actions (AUTHORITY §8: every writer is named — these are, by
`explain`). So `c.done = true`, `toggle(done)`, `form(Card, board: b)`
and `b.delete()` are complete. `trash:` makes delete reversible and
derives its undo. `@action` is written only for LOGIC: several rows, an
external effect, a different impact (`invite`).

- A derived door reaches agents only when listed (`tools: [Card.update]`)
  — agents act through named doors (AUTONOMOUS §4.1).
- `access: .board` inherits the parent's policy; reads are filtered by it,
  so `Board.all()` is "the boards I can read".
- A `@unique` reference derives a one-to-one accessor (`c.note`), made on
  first write, living in ITS row's home (`.account`), readable only while
  the referenced row is.
- `form(T, fixed…)` creates, `form(row)` edits (an implicit draft,
  conflicts merged per field), `form(action, fixed…)` invokes. The
  remaining fields are the inputs, labelled from their names.

**Flows are derived from the homes and the targets** (`avra explain
data`):

| Between | Transport |
|---|---|
| device ⇄ server | replica diffs pushed on commit · outbox offline · silent push wakes a backgrounded app |
| app ⇄ widget / extension / watch | shared container (App Group) · WatchConnectivity |
| tab ⇄ tab | BroadcastChannel |
| my devices | `.account` through the server; with no service deployed, the platform cloud where it exists — a plan diff |
| user ⇄ user | server fan-out · relay for rooms |
| service ⇄ service | imported models and actions; the same doors over the network |
| app → third party | `use @weather` typed from OpenAPI / GraphQL at build; reads cached by freshness, writes are `.external` |

Moving a home (`.device → .account`) is a semantic diff: the build prints
the sync it adds, the auth it now needs, and the MIGRATION of rows already
on devices.

## 18. L1 — `view`, `state`, and the state parameter (design)

The one grammar change Phase 1 needs, sized so a compiler lane can land
it in one slice. Nothing here is built.

**Surface.**

```avra
view stepper(state n: int) {              // a fn answering a View that may own state
    row {
        button "−" { on press { n = n - 1 } }
        text "${n}"
    }
}

view cart_line(l: Line) {
    state qty: int = l.qty                // a place with the view instance's identity
    stepper(qty)                          // hands the place, never a copy
}
```

**Grammar** (`features/views`, a statement feature; `state` is already
reserved by the spec):
- `stmt = "view" n:NAME "(" params ")" "{" body "}"` — params as a
  fn's, each with a third mark beside `const`/`mut`: `( sk:"state" )?`.
- `stmt = "state" n:NAME ( ":" type )? "=" v:expression END` — legal
  only directly inside a `view` body; elsewhere F-new "`state` lives in
  a `view` — a fn's local is `let` or `mut`".

**Meaning, by desugaring** (the compiler's; a user never writes it):
- `view f(params) { … }` is `fn f(cx: ViewCx, params) -> dyn View { … }`.
  `ViewCx` (`@std/ui`) is the view INSTANCE's identity: where its state
  lives, and the parent of every view it calls.
- `state x: T = v` is `let x: Cell<T> = cx.slot(N, () -> v)`: slot `N`
  is the statement's position in the body (static), the seed runs once
  per instance. A read of `x` is `x.get()`; `x = e` is `x.set(e)`;
  `x.f = e` is `x.set(x.get() with { f: e })` (a copy; in-place field
  writes through a Cell are the reuse campaign's).
- `state p: T` as a parameter is `p: Cell<T>`, read and written the
  same way. A call passes a `state` binding (its Cell) or an explicit
  `Cell<T>` (the P8 hatch); any other argument is F-new "`p` is a
  place the caller owns — pass a `state`, not a value" (WEB_UI §5.3's
  law, one voice).
- A view called inside a view body, `g(args)`, is `g(cx.child(M, key),
  args)`: `M` the call site's position, `key` the enclosing `for`'s
  item identity when one is statically known (a `@model` row's id),
  else the iteration's ordinal — the identity path of WEB_UI §6.2,
  first rung. A view called from a plain fn (a route, a test) gets a
  fresh root: `g(root(), args)` — no persistence, which is right for
  a server render.
- `ViewCx.slot` is one runtime row (`avra_view_slot(cx, n, seed) -> ptr`),
  typed at the lowering — the compiler knows `T`; the store is a map
  from identity path to Cells, owned by whoever made the root: the
  naive renderer (P1.2) keeps it across turns, a route drops it.

**What this does NOT do yet:** reactivity. In Phase 1 the naive
renderer re-runs the root view after each committed segment; `state`
persists because the store does. Exact patches (§12 far shelf) read the
same Cells.

**Tests that land with it** (features/views/tests/): a `state` outside
a view is refused; a value passed to a `state` seat is refused; a
stepper's Cell is shared with its caller (write in the child, read in
the parent) in both engines; two calls of one view at two sites hold
two states; the same site across two renders under one root holds one
state; under two roots, two; a `for` over three rows gives three states
that survive a reorder when the rows are model rows and reset when they
are plain data.

**Order:** land `view` + `state` local first (a view with no state
params is already useful and tests the ViewCx plumbing), then the
`state` parameter (touches the fn param grammar and the call seat law),
then the identity key.

## 19. Phase 0b — the library, properly (owner review, 2026-09-29)

Phase 0 proved the seams (tree → realizer → served page) and shipped a
toy: tuple payloads, `Setting`/`look`, hard-coded tokens, a format-string
`page`, five packages, a gallery in std. Phase 0b rebuilds it to
`docs/LIBRARIES.md`. Language first (§19.3); the library after.

### 19.1 The shape

- **The component is the node.** No `Node`, no `Role`, no `XProps`, no
  `leaf`. A component's fields are its props; a tree is `dyn View`.
- **Shared settings by field spread:**

  ```avra
  export type Common = { style: Style = Style {}, attrs: Attrs = Attrs {} }

  export component text(content: string) {
      ..Common
      selectable: bool = true
  }
  ```

- **Props in the head:** `button("Buy", kind: .Primary)`; the body keeps
  children and code slots.
- **Realizers are trait impls, mirrored:** `impl Realize<text> for Html`
  in `realize/html/text.av`. A target missing a component fails to
  compile. The semantic tree for the inspector and diffs is one more
  realizer (`Describe`), never a parallel type system.
- **Style and Theme are data:** `Style` is typed, optional, token-valued;
  `Theme` is token tables as a record (a default const; DTCG via
  `embed`). No realizer holds a value.
- **HTML is a typed `Document` through a `Writer`,** never a format
  string.

### 19.2 The tree

```
packages/std-ui/src/
  view.av                 View, Shows — what users meet
  components/             one file per component: text, heading, image, icon,
                          button, link, toggle, input, picker, column, row, grid,
                          scroll, spacer, divider, region, list, item, table,
                          form, fieldset, dialog, popover, menu, status, canvas, foreign
  style/                  style.av · tokens.av · theme.av (Theme + the default)
  a11y/                   name.av · roles.av · faults.av
  realize/realizer.av     the trait + the walk
  realize/html/           document.av · writer.av · css.av · one file per component
  realize/tui/            layout.av · one file per component
  web/                    screen.av (Screen over @std/http)
  testing/                transcript.av · snapshot.av
```

Mirrored (LIBRARIES rule 9): open `text.av` in any directory and it is
`text`. A component's file holds its fields, docs and a11y contract; a
target's file holds its drawing. A new target is a new directory.

`std-ui_html`, `std-ui_tui`, `std-ui_web`, `std-ui_gallery` fold in or
go (the gallery becomes an `avra` command over `testing`).

### 19.3 The compiler changes, in order

| # | Change | Why beyond UI | Status |
|---|---|---|---|
| C1 | **Field spread** in `type` and `component`: `..Common` | any record family sharing fields: HTTP options, DB configs, CLI flags | **landed** — #59 (`..R`) |
| C2 | **Generic traits**: `trait Realize<T>`, `impl Realize<text> for Html` | `From<T>`, `Encode<Json>`, drivers, codecs, `Respond` generalized | **landed** — #59 |
| C3 | **Props in the head**: `button("Buy", kind: .Primary)` | every component with a head: `@std/cli`, `@std/http` routes, `deploy` | **OPEN** — sugar; the L4 row |

C2's substrate is complete: #67 (dispatch on a `dyn` argument, its
completeness law, defaults in generic traits), #79 (a bound names a
generic trait at its arguments — `fn f<R: Realize<Text>>`), and #87 (a
generic trait's static members — `From<T>` in `@std/convert`). Two
generic-trait shapes are recorded but **not built**, and §19's library
does not need either to type: `dyn Realize<Text>` (C2b — a `dyn` over a
generic trait does not parse) and the generic forwarder `R.from(t)` (`R`
"is not defined"). Both live in `docs/2026_09_30_GENERIC_TRAITS.md`.

Each change lands with its design written here first, then red-team and
review round. The Phase 0 code (on main) keeps working until the library
moves. The rejected props-record draft is parked outside the tree, not
merged.
