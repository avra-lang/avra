# Sync — the proposal, v2

Status: PROPOSAL v2, for the UI lead's ruling (§12). Nothing here is built. The owner read v1 and
set the direction: the word is `share`; a synced place is a live query over a `@std/relation`
model, scoped by a share; and the performance of live queries is the first worry. Two later
directions: a share declares only who may see and change what, leaving storage and transport to
each target's wiring; and a service is its own principal, never a part of a share (§3). This
version owes the edge cases. Every probe was compiled by the committed seed (bootstrap/seed.ll.gz,
unchanged from 13c2fd4 to b2d72c7) and run on Linux x86-64, Xeon 2.1 GHz.

**Cost, in three lines** (§11):
- A write reaches only the subscriptions filed under its before and after keys: 224–265 ns per
  write at 10,000 subscriptions, with 5.25 looked at and 4.51 told. A scan of all of them costs 78 µs.
- At 1,000 writes/s that is 0.03% of one core. The server keeps 125 B per subscription and no
  rows, so 10,000 subscriptions take 1.25 MB.
- A field write is 6.7–7.7 B on the wire and merges in 14–67 ns. A hot key with 100 subscribers
  costs 1.4 µs per write, and its cost is the 90 messages that write sends.

## 1. The author's view

A share is a declared unit of data with members, roles and rules. A synced place is a live query
over the app's own models, read inside a share. Writes stay plain: `c.title = x` is the whole write.

```avra
@model
type Board = { id: id<Board>, name: string }

@model
type Card = { id: id<Card>, @index board: id<Board>, title: string, done: bool = false,
              votes: int = 0, @unique slug: string, rank: int }

/// Who may see and change what on one board (§3).
share board_share(b: Board) {
    sees: [Board.where(id: b.id), Card.where(board: b.id)]
    members: Member.where(share: board_key(b))
    rules: board_rules(b)
}

component board_page(b: Board) {
    state cards: List<Card> = Card.where(board: b.id).ordered(by: .rank) in board_share(b)
    state cursor: Point? = null in board_share(b).room()      // presence: a value, ephemeral

    list self.cards by it.id { c -> card_row { c: c } }
}

component card_row(state c: Card) {
    row {
        checkbox { checked: self.c.done }                             // a register
        field "Title" { value: self.c.title }                         // text: merges by character
        button "+1" { on press { self.c.votes = self.c.votes + 1 } }  // a counter: two +1s make +2
    }
}
```

- **Two forms of place.**
  - Query-backed: `Card.where(…) in s` reads rows of a model that the share's store holds.
  - Value-backed: `state x: T = d in s` is one document the share keeps. `in s` is stored;
    `in s.room()` is ephemeral. A room is a share whose values are ephemeral.
- **No `@sync` type.** The model is std-db's `@model`, declared once; v1's `@sync` is gone. The
  element `c` of a query-backed list is a place, addressed by its `id<Card>`. That answers the UI
  doc's open question about "a place through a `state` list of plain records".
- **Ids** are `id<T>` from the typed-ids lane (avra-lane-typed-ids-proposal). Following
  AUTHORITY_AND_RECEIPTS §3, the invoker mints them and the authority validates them, so a row
  inserted offline has its final id at once.
- **Roles and rules** belong to the auth lane (avra-lane-auth-permissions-proposal, building on
  AUTHORITY_AND_RECEIPTS §1: reads are filtered by the same authority as writes, and authority is
  re-checked at commit). This proposal names where they plug in and designs none of them.

## 2. Live queries: what may be kept incremental

A live query is a std-db read that the server keeps by its KEYS, never by its rows. std-db's
`where` already takes only named equality columns: `Card.where(db, board: b)`, and scope.av's
`Op` has one variant, `Eq`, under the rule "nothing is ever filtered in memory". So the keys are
already in the spelling.

| Query shape | Kept as | Write cost | Verdict |
|---|---|---|---|
| `M.where(k: v, …)` on `@index` columns | an entry under `(M, k=v)` | one index probe per image | kept |
| … plus equality on non-indexed columns | the entry, plus a residual test on the images | the probe, then one compare | kept |
| `.ordered(by: f).first(n)` | the entry, plus the window's **boundary value** (the n-th `f`) | a compare against the boundary; one store read to refill when a row leaves a full window | kept |
| a join along an `@index` foreign key (`b.cards`) | two keyed entries | a probe per side | kept |
| a join on a column with no index | — | — | **refused at compile time**, naming the missing `@index` |
| a range, `!=`, a computed predicate, an unwindowed `ordered` | — | — | **refused at compile time**: it cannot be kept incremental |

- **Membership comes from the change log's before and after images.**
  - A write looks up the subscriptions filed under its before image's key and its after image's key.
  - Each subscription compares `matches(before)` with `matches(after)`. The result is *enter*
    (the after row is sent), *leave* (the id is sent), *update* (the changed fields are sent) or
    nothing.
  - No per-client row cache exists; each client holds its own rows.
- **The change log is the store's.**
  - std-db already counts every write per table, with triggers inside the writer's transaction
    (apply.av: `avra_commits.seq`, `avra_tables.last`).
  - Those triggers grow to row level: one `avra_changes(seq, table, row, before, after)` row per
    write, in the same transaction.
  - So a write from anywhere is seen: an action, a job, a std-queue worker, a migration, or a
    `sqlite3` shell. The owner's v1 review approved database triggers as the door for writes
    that go around Avra.
  - The log is pruned behind the oldest live cursor and a retention bound (§10, reconnect storm).

## 3. A share is who and what; the wiring is the target's

A share declares only WHO may see and change WHAT. Where the rows are stored, how a write waits
offline and how frames travel are not the share's: a web client has no SQLite and a server does,
so the same share runs over different wiring on each target.

```avra
/// Who may see and change what on one board.
share board_share(b: Board) {
    sees: [Board.where(id: b.id), Card.where(board: b.id)]   // what: live queries (§2)
    members: Member.where(share: board_key(b))              // who: membership rows (§3b)
    rules: board_rules(b)                                   // what each role may do: the auth lane's
}
```

### 3a. The wiring, per target

The wiring is one `@std/config` component per target (CONFIG §2.0): typed values with defaults,
overridden by file, env and stage like any setting, and varying by value, never by a branch on
the stage (CONFIG §6.1a). It is handed down by context, as `ctx theme` (UI) and `ctx db`
(DURABLE_QUEUE §10) already are, never looked up by key (CONFIG §2.0a: "no global key lookup").

```avra
/// The server: it holds the truth, so it stores and commits and never queues.
@derive(Decode)
component ServerSync {
    store: Store = .Sqlite(path: ".avra/board.db")
    outbox: Outbox = .None
    transport: Listen = .Sse(path: "/sync")
    file "sync.toml"
    env "SYNC"
}

/// A page: no SQLite; what the browser keeps, and a durable outbox beside it.
@derive(Decode)
component PageSync {
    store: Store = .Indexed(name: "board")          // IndexedDB; `.Memory` keeps nothing past the tab
    outbox: Outbox = .Indexed(name: "board-outbox")
    transport: Dial = .Sse(url: "/sync")
}

/// A phone: SQLite on the device, the outbox a std-queue_store queue.
@derive(Decode)
component DeviceSync {
    store: Store = .Sqlite(path: "board.db")
    outbox: Outbox = .Queue(path: "outbox.db")
    transport: Dial = .Sse(url: "https://board.example/sync")
    stage dev { transport: .Sse(url: "http://localhost:8080/sync") }
}

// Each target's root sets the context once; every share below it reads it.
ctx sync = wired(PageSync.load()?)

// A test hands down its own, with no config file:
ctx sync = Sync { store: .Memory, outbox: .Memory, transport: Simulated { seed: 7, loss: 10, delay: ms(200) } }
```

- **`Store`, `Outbox` and the transport are traits.** The config enums name the library's
  implementations, and `wired` builds them; an app's own implementation is a value of the trait,
  handed down the same way (P8).
- **What the share gets** from the context is the three traits, never which target it is on.
  `board_share` is one declaration, compiled into the server, the page and the phone.
- **Transports**, as before: `Sse` (std-http's SSE feed plus POST), `Peer` (WebRTC on the web, TCP
  on native), `InProcess`, `Simulated` (seeded, so a convergence test is a fixed program shrunk on
  failure, as tools/exact-patches shrinks UI programs; each row of §4's table lands with one,
  covering all interleavings of three replicas, two ops each).
- **A frame** is `{ share, from_cursor, ops, frontier }`. The server is one more peer: durable,
  always reachable, and the one that may arbitrate.

### 3b. Services: their own principals

A service is not declared in a share. It is its own principal, its access is a membership row
granted like a person's, and what it reacts to is a query it subscribes to, like any client.

| | Option | Spelling | For | Against |
|---|---|---|---|---|
| a | **the service subscribes** | `for c in Card.where(done: true) in shares_of(me) { … }` | one mechanism for clients and services; a service is tested over `Simulated` like a page | says nothing about access by itself |
| b | the share lists its services | `share board_share(b) { services: [card_indexer] }` | visible where the share is | access granted by deploying code: unrevocable at run time, unaudited, and code inside a declaration of who and what |
| c | a wiring block grants access | `ServerSync { grants: [card_indexer in board_share] }` | per target, beside the rest of the wiring | access becomes ops config: a stage could grant what another refuses, which is what CONFIG §6.1a forbids for meaning |
| d | **membership as data** | `Member { share: board_key(b), principal: .Service("card_indexer"), role: .Editor }` | granted, revoked and audited by the same action as a person's (AUTHORITY §8: every writer is named); a grant is a change-log write, so revocation reaches live subscriptions like any leave | a grant per share, unless a parent share's row carries it (§10, nesting) |

**Recommend d plus a** (the lead's recommendation). The row says the service may; the
subscription says what it reacts to. A service with no row is a stranger: its subscription is
refused by the server, exactly as a page's would be.

```avra
/// Who belongs to a share, in what role. `Principal` and `Role` are the auth lane's.
@model
type Member = { id: id<Member>, @index share: string, @index principal: Principal, role: Role }

/// Grants the indexer editing on every board of an org: one row on the parent share (§10, nesting).
@action(auth: owner_of(o), impact: .routine)
fn trust_indexer(o: Org) -> Member {
    Member.insert(Member { share: org_key(o), principal: .Service("card_indexer"), role: .Editor })
}

/// The indexer: a principal of its own, reacting to a live query like any client.
fn card_indexer(me: Principal) -> Result<void, Fault> {
    for c in Card.where(done: true) in shares_of(me) {  // every share where `me` holds a row
        c.rank = reranked(c)                            // `c` is a place: an ordinary write, under `me`
    }
}
```

- **`for` over a live query** yields each row as a place when it enters or changes, and never
  ends; a leave is not yielded. `shares_of(me)` is spelling A's `in` over every share where `me`
  holds a row.
- **Its query is kept like any other** (§2). `done` is not a key, so the subscription is filed
  under the board key of every share where `me` holds a row, with `done: true` as the residual:
  a service on 1,000 boards holds 1,000 index entries pointing at one subscriber, about 125 KB at
  §11's measured cost.
- The service's writes go through the share like anyone's. The change log names `me` as the
  writer, and subscribers hear the writes as they hear a person's.
- **Revoking** is deleting the row. The change log's before image takes the service out of the
  share, its live query is told *leave* for every row it held, and its next write is refused as
  `.Revoked`.

## 4. The model: how a row's fields merge

The kinds are unchanged from v1; they are now stated over `@model` fields.

| Field | Merge | Chosen when | Op |
|---|---|---|---|
| `bool`, enum, `int`, record, `T?` | LWW register, stamp `(lamport, replica)` | default | `set(row, field, stamp, value)` |
| `int` written only as `x = x ± e` | PN counter | every write in the program has that shape | `add(row, field, stamp, delta)` |
| `string` written by `field` or marked `@text` | text sequence (Fugue-style) | the writer | `ins(after, chars)` / `del(id, n)` |
| `string` assigned by code | register (a status word must not merge as `"doneactive"`) | default | `set` |
| `@unique`, `@check`, the share's key column, `@owner` writes | **arbitrated** (§5) | the mark | `ask(row, field, value)` |
| `@local` | not synced | the mark | none |

- **Row order** in a query is the query's own `ordered(by:)` column. That column is a register
  like any other, never the client's index.
- **Sequences:** lists of scalars inside a row, and value-backed documents, use the same sequence
  algorithm as text.
- **Fractional position keys** were measured and refused in v1: they grow one octet per ~6.6
  inserts into one gap.
- `avra explain Card` prints each field's choice (P7).

## 5. Arbitrated fields, step by step

1. **Pending.** `c.slug = "q3"` lays a layer over that field only (today's `Overlay`, std-ui
   cache.av) and appends an `ask` to the outbox the target's wiring names (§3a). The view shows
   the new value, with `pending(c.slug)` true.
2. **Order.** The outbox keeps one FIFO per share and per replica. An ask never jumps ahead of a
   converging op written before it, because the server applies each replica's frames in order.
   Offline, asks wait with everything else. Per AUTHORITY §1 they carry INTENT, never authority.
3. **Server transaction.** One transaction runs the auth lane's re-check, the constraint (a
   `@unique` probe, a `@check` predicate, the rule) and the write. The change-log row and the
   idempotency record (the op's stamp) commit atomically with it.
4. **Confirmed(seq).** The layer drops and the value is the server's. Every subscriber, the
   writer included, hears it through the change log.
5. **Lost(reason)**, with `reason: Lost = .Taken | .Refused(rule) | .Revoked | .Removed | .ShareGone`.
   Only that field's layer drops; the row's other fields and every other queued op stand.
   `lost(c.slug)` reads the reason until the next write to that field.
6. **`on refused`.** A hook on the place or on the share: `on refused(r: Refusal) { … }`, where `r`
   carries the place, the value asked for and the reason. With no hook, the theme's default shows
   `lost(…)` beside the control. The library never retries a refused ask: the intent was judged.

## 6. Converging writes: optimistic and confirmed

- A converging write never rolls back, because the local value is a valid final state.
- `pending(x)` stays true until the authority's frontier passes the op.
- A concurrent register write that loses is replaced by the winner on the next paint, and
  `lost(x)` reads `.Superseded` for one turn.
- The default is no indicator, as Linear and Figma do.
- `shown: T?` (UI doc, ruling of 2026-11-18) becomes the optimistic value, and the place becomes
  the confirmed one.

## 7. Presence

Places declared `in s.room()` form a map from each replica to that replica's room values.

- Each entry is an LWW register. It is never logged, never sent to a replica that was not
  connected, and it expires 30 s after its replica's last frame.
- `present(s)` is the map's keys with their principals.
- Using a room value as a durable fact is refused (UI ledger, "presence is not truth").
- Fan-out is costed in §10.

## 8. Persistence and schema change

- **Server:** the model's own std-db table is the truth.
  - Each synced field gains a stamp column, and the row gains `seq`, the change-log sequence of
    its last write.
  - Catch-up is "rows with `seq` > cursor", one index read, so registers need no op log of their own.
  - Tombstones are rows with a `gone` stamp.
- **Native client** (as its wiring names it, §3a): the same tables in a local SQLite file. The
  outbox is std-queue_store: `send` commits before it answers, and ops are deduped by their stamp
  through its own `FlowSeen`.
- **Web client:** whatever the page's wiring names (§3a): IndexedDB, or memory. SQLite over OPFS
  becomes a choice once a web build of std-sqlite exists.
- **Schema:** std-relation's shape verdict decides.
  - `Same` and `Grew` sync across versions: an older replica keeps and forwards ops for fields it
    does not know.
  - `Moved` is refused for a synced model, as std-db's `diff` refuses a moving migration.
  - A frame carries its writer's shape hash.

## 9. Spelling

How others declare synced data:

| System | Model | The synced read | Scope and permission |
|---|---|---|---|
| SwiftData + CloudKit | `@Model class Card { var title: String }` | `@Query(filter: #Predicate { $0.board == id }, sort: \.rank) var cards` | `ModelConfiguration(cloudKitDatabase: .private(…))`; sharing through `CKShare` |
| Zero | `createSchema({ tables: [card] })` | `useQuery(z.query.card.where('boardID', id).orderBy('rank', 'asc'))` | `definePermissions` beside the schema |
| ElectricSQL | the Postgres table | `useShape({ url, params: { table: 'cards', where: "board_id = $1" } })` | the app's proxy in front of the shape endpoint |
| Yjs | none: untyped `Y.Map`/`Y.Array` | `doc.getArray('cards')` after `new WebsocketProvider(url, room, doc)` | the server's, outside Yjs |
| Jazz | `co.map({ title: z.string(), done: z.boolean() })` | `useCoState(Board, id, { resolve: { cards: true } })` | every value is owned by a `Group`; `group.addMember(account, "writer")` |
| Firebase | none | `onSnapshot(query(collection(db, 'cards'), where('board', '==', id), orderBy('rank')), cb)` | `firestore.rules`, a separate language |

Jazz is the closest to a share: its data is owned by a group that has roles. We take that
ownership; we leave its second type system beside the app's.

Our options for the read:

| | Spelling | For | Against |
|---|---|---|---|
| A | `Card.where(board: b.id).ordered(by: .rank).first(50) in board_share(b)` | std-db's spelling today; the keys are syntactic, so the index check is a type check (P1, P10) | equality only, by construction |
| B | `Card.where(it.board == b.id) in board_share(b)` | reads as a predicate | the compiler must extract keys from an expression and refuse the rest after the fact; and `where` gets a second spelling beside std-db's |
| C | a `query cards = …` declaration | names the subscription | a new keyword, against "a library before syntax" |

**Recommend A.**
- B's predicate form is refused, with A's spelling as its structured fix.
- `in s` is the one new piece of syntax this proposal asks for.
- Until it lands, the library call `s.live(Card.where(…))` answers the same place.

## 10. Edge cases, each with a recommended ruling

| Case | What happens | Recommend |
|---|---|---|
| **Offline removal** | A removes card 7 offline; meanwhile B edits its title. | Remove wins over concurrent field edits, and B's edit is `lost(.Removed)`. Restoring is the app's action (trash and undo), never a merge rule. |
| **A row joins or leaves a query** | `c.done = true` under `where(done: false)` | Judged from the change log's images: leave sends the id, join sends the whole after row, and a window refills with one store read. The writer's own view applies the leave at once, optimistically. |
| **Moving between shares** | `c.board = other` moves the card from `board_share(a)` to `board_share(b)` | The share's key column is arbitrated automatically: the auth lane checks leave-on-source and join-on-target in one transaction. Subscribers of `a` hear leave, those of `b` hear join. |
| **Nesting** | org → board → card | A row has exactly one HOME share, its innermost key. Nesting carries roles (the auth lane), never copies of data. An org-level query spans boards through the index. |
| **Deleted share** | the board is deleted | Deletion is an arbitrated action. Clients hear `share_gone`, drop the share's local rows, and refuse its queued ops as `.ShareGone`. An export is the app's action, run before the delete. |
| **Schema change** | a field added; a field renamed | `Grew` syncs both ways. `Moved` is refused at build, with std-db's two-step (add, copy, stop writing, drop) as the help. |
| **Large shares** | a board of 200,000 cards | An unwindowed query on a share is allowed. Its first sync streams pages of 1,000 rows by `seq`, and the view reads `Async` until the last page. Recommend a lint, not a refusal, above a declared size (`share … { expect: 10_000 }`). |
| **Presence fan-out** | 100 members, cursors at 10 Hz | Naively, 1,000 updates/s × 99 receivers = 99,000 messages/s. Coalesced per 50 ms tick, it is one frame per member per tick: 2,000 frames/s of at most 100 × 8 B each (arithmetic, not probed). Recommend the tick, plus a cap: above 200 members a room sends counts, not cursors. |
| **Reconnect storm** | the server restarts and 10,000 clients return | Today's SSE client (runtime/dom/bootstrap.js:637–671) backs off from 250 ms, doubling to 5 s, with no jitter, so the clients return in lockstep. Recommend full jitter. Dedupe catch-up per key: in the probe's shape 10,000 subscriptions sit on 2,000 keys, so 2,000 `seq` range reads. A cursor older than the log's retention gets `cursor-expired` (std-ui feeds.av already has the word) and a paged snapshot, under a concurrency cap. |

## 11. Cost (P4)

The probes are in `scratch-probes/sync/`, and each one's output is quoted below.

**Live queries** (`live/`; memory from `live_memory/`):
- A subscription is `{ key, residual, window }`.
- The index maps each key to its subscription ids, as a `Map<string, List<int>>` (a map's keys
  are strings).
- The log is 100,000 writes, and one in twenty moves a row to another key.
- The scan does the same work with no index.

```
10000 subs over 2000 keys, 100000 writes: index 1581 us  indexed 257 ns/write  looked 5.25/write  told 4.51/write  refills 433 per 1000 writes  |  scan 77531 ns/write (told 45170)
10000 subs over 100 keys, 100000 writes: index 3365 us  indexed 1378 ns/write  looked 105.0/write  told 90.34/write  refills 8670 per 1000 writes  |  scan 73991 ns/write (told 903400)
100000 subs over 20000 keys, 100000 writes: index 17925 us  indexed 573 ns/write  looked 5.25/write  told 4.51/write  refills 433 per 1000 writes  |  scan 841411 ns/write (told 45175)
held 1000000 subs, 200000 keys  —  AVRA_MEM_STATS=1: peak 125 MB in all (list boxes 89, list buffers 27, strings 4, map indexes 4)
```

- **The owner's case**, 10,000 subscriptions at 1,000 writes/s, costs 224–265 ns per write
  (three runs), or 0.26 ms of CPU per second. Each write touches 5.25 subscriptions and tells 4.51.
- **The index is the whole win.** The same work as a scan costs 78 µs per write at 10k
  subscriptions and 841 µs at 100k. Indexed, it grows only from 0.26 to 0.57 µs, and what grows
  is cache misses.
- **A hot key** (100 subscribers each) costs 1.4 µs and 90 messages per write. The cost is the
  messages, which is what the presence tick and the room cap address.
- **Windows** need a store read on 433 of every 1,000 writes in this shape: one indexed read
  each, about 430/s at the owner's rate. This is the cost to watch. The probe moves the boundary
  by one instead of reading the store, so 433 is a count of reads, not their time.
- **Memory** is 125 B per subscription as Avra records (1,000,000 in 125 MB). A packed layout
  would be about 32 B (key 8, id 8, residual 8, boundary 8). No rows are held.
- **Not probed:** the trigger's cost per write in SQLite, the refill read's time, and the wire
  size of an enter frame (the row's size plus about 10 B).

**Registers** (`register/`, from v1):

```
1000 records x 3 fields, 10000 ops: local 24 ns/op  concurrent 14 ns/op  replay 15 ns/op  wire 6.74 B/op  (changed 10000 6000 0)
100000 records x 8 fields, 1000000 ops: local 123 ns/op  concurrent 67 ns/op  replay 28 ns/op  wire 7.70 B/op  (changed 1000000 600000 0)
```

A stamp costs 16 B per field. An op held as an Avra record is 96 B, 12 times its wire form, so a
batch stays packed `Bytes` until it is merged.

**Prior art** (`prior_art.mjs`, the same workloads, from v1):
- Yjs: 17 B per field write, and 11.6 ms per 10k merged ops.
- Automerge: 143 B per change, and 272 ms per 10k merged ops.
- Fractional keys (`order_keys.mjs`): 3.2 B mean for random inserts, unbounded for inserts into one gap.

| Budget | Bound | Measured |
|---|---|---|
| Fan-out per write, 10k subscriptions | ≤ 1 µs | 0.22–0.27 µs |
| Server memory per subscription | ≤ 128 B now, ≤ 32 B packed | 125 B |
| Wire per field write, batched | ≤ 8 B | 6.7–7.7 B |
| Merge per register op | ≤ 50 ns | 14–67 ns |
| A live query the compiler cannot keep incremental | refused at build | — |

## 12. Rulings asked

1. **Live query spelling A**: `Model.where(k: v).ordered(by:).first(n) in share`, with equality on
   `@index` columns and windows only. Anything else is refused at compile time, and the predicate
   form is refused with A as its fix. Recommend: yes.
2. **The change log is row-level std-db triggers** in the writer's transaction (`avra_changes`,
   with before and after images). It is the only source of membership changes, and no per-client
   row cache exists. Recommend: yes.
3. **Arbitration**: writes to `@unique`, `@check` and `@owner` fields and to the share's key
   column are asked of the authority, in outbox order. A refusal drops that field's layer only and
   reaches `on refused`. Every other write converges and never rolls back. Recommend: yes.
4. **A share is who and what, and nothing else** (owner). Store, outbox and transport are each
   target's wiring: one `@std/config` component per target, handed down as `ctx sync`, so one
   share declaration compiles into the server, the page and the phone. A service is its own
   principal: its access is a membership row (d), and its behaviour is a live query it subscribes
   to (a). Recommend: yes, d plus a.
