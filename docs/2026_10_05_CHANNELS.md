## 1. The idea

1. A STREAM is a recipe for values over time. A SOURCE is one running.
   A SINK feeds one. `select` waits on several sources at once, and the
   compiler demands an arm for every end.
2. A running stream lives in ONE block, as a task does. It ends when
   that block does. Nobody writes `close` for the common shapes, and
   nothing counts references.
3. A DECLARED stream (`queue`) has a CONTRACT: delivery, order,
   capacity, lease, what happens to a failure. Its home is bound per
   run. The compiler checks the home against the contract, and the
   effects its consumers reach against the delivery.
4. THE CONTRACT IS THE FAULT MODEL. `avra test --faults` derives
   duplicates, reorders, crashes, expired leases and partitions from
   the terms and runs every consumer under them, seeded.
5. A lawful fold over a stream is a maintained view; the law's status
   (proven, checked, trusted) is printed wherever it licensed anything.

### What v1 claimed and v2 drops

- "Every wait goes through one door, so tests, replay and durability
  are one mechanism." False: data enters through the never-waiting
  take and through `World` rows (43 of the registry's 166 rows carry
  `Reach.World` — PROBED by grep on `core/runtime_api.av`). §10 says
  where the seams really are. There are three, not one.
- "A channel ends when its last writer is done, inferred from uses."
  Replaced by ownership (§5.3).
- "Exactly once is derived, never set." Replaced by a declared demand
  the compiler must discharge (§7), following spec 29.2.
- "The text does not change with the home." True only for a declared
  queue's home and for consumers. A local channel is always local (§6).
- The wasm reactor lowering, the shared-memory ring, trap containment,
  the must-read `send`. Cut; see §18.

### False choices that remain dissolved (P6)

| choice | what holds instead |
|---|---|
| sync / async | a wait parks the task; no colour (spec 13.4) |
| push / pull | `yield` pushes into a `for` that pulls; fused they are one loop |
| close by hand / leak | a running stream is owned by a block and ends with it |
| exactly once / at least once | a demand the compiler discharges per effect, or refuses |
| test / production | the same program; the schedule, the clock and every bound home are the run's |
| batch / incremental | one fold; a law decides whether it can be maintained |

### 2.1 Two tasks, a bounded channel, backpressure — DESIGNED

```avra
use @std.task.{produce, Sink, Source}

fn crawl(urls: List<string>, out: Sink<Page>) {
    for u in urls {
        if !out.send(fetch(u)) { return }   // parks while 8 pages wait
    }                                       // false: the reader is gone
}

fn index(pages: Source<Page>) -> int {
    mut n = 0
    for p in pages {                        // ends when the producer is done
        store(p)                            // and the last page is taken
        n = n + 1
    }
    n
}

let pages = produce<Page>(8) { out -> crawl(seeds, out) }
let indexed = spawn index(pages)
println("${indexed.await} pages")
```

- `produce` runs its block as a task and answers the reading end. The
  channel ends when that block does. Nobody closes it.
- NEW: `for x in <Source>`; a `Source` as a fn's answer (the task law
  narrowed, §5.3). The rest is library.
- PROBED: `Sink<T>` and `Source<T>` as generic records of fn values,
  filled at fn seats, captured by `spawn`, with `send`/`next` as
  inherent methods, compile and run today (a 40-line stand-in with the
  loop written as `while true { let p? = pages.next() else { break } }`
  answers `6 pages`). `channel` and `select` are reserved words today
  (`resolve.reserved`), so the stand-in is named `chan`. A generic fn
  called with a type argument and a trailing block — `made<string>(8)
  { out -> fill(out) }` — also compiles and runs, which is `produce`'s
  call shape.

The same producer as a recipe (DEPENDS-ON COLLECTIONS S3; this is
COLLECTIONS S4):

```avra
fn pages_of(urls: List<string>) -> Stream<Page> {
    for u in urls { yield fetch(u) }
}

for p in pages_of(seeds) { store(p) }                 // one task, one loop
for p in pages_of(seeds).buffered(8) { store(p) }     // two tasks, 8 pages between
```

### 2.2 `select` over a watch, a channel, a timer and a signal — DESIGNED

```avra
use @std.task.{quiet, signals, Source, Sig}

fn dev(saves: Source<Seen>, built: Source<Built>, quit: Source<Sig>) -> int {
    mut dirty = false
    while true {
        select {
            _ in saves -> { dirty = true }
            quiet(ms(50)) if dirty -> {      // 50 ms in which no arm fired
                dirty = false
                rebuild()
            }
            b in built -> report(b)
            _ in quit -> { return 0 }
            saves.ended -> { return 1 }
            built.ended -> { return 1 }
            quit.ended -> { return 0 }
        }
    }
}

let w = watch()?
w.add("src")?
let code = within mins(60) { dev(w.changes(), builds, signals([.Term, .Int])) } catch 2
```

- `dev` is HANDED its sources. That is what lets a test hand it
  scripted ones (§2.8, §10).
- An arm takes a `Source<T>` (one item) or a `Task<T>` (its answer).
  `quiet(d)` and `x.ended` answer tasks.
- A source that can end needs its `.ended` arm (law 7).
- There is no cancellation arm: the `within` cancels `dev` at whatever
  it waits on (§5.4).
- NEW: `select`; `within` answering `Result<T, TimedOut>` (today the
  block answers as written — READ `std-time/src/time.av:62-73`); a
  signals row (nothing in the runtime handles SIGTERM or SIGINT today
  — PROBED grep: the only handlers are the guard page's and the FFI
  fault's); `Watch.changes()`.

### 2.3 One pipeline — recipe DESIGNED; its placements are others' campaigns

```avra
fn scores(lines: TryStream<string, IoError>) -> TryStream<int, IoError or ParseError> {
    lines.try_map(parse).filter(it.valid).map(score)
}

// this task: one loop
let a = scores(read_lines("day.log")).fold(0, add)?

// fed by a declared queue; the sum and the cursor are kept together
let b = scores(events.stream().map(it.item.line)).fold(0, add, kept: "daily-score")?
```

- `fold` is the left fold in every placement. `reduce` is the fixed
  tree (§9). BEND's cores placement of this same chain is
  DEPENDS-ON(BEND §4); nothing in this design places it.
- `try_map` takes a fn answering `Result`. A lambda cannot use `?`
  for this (PROBED by the review: "`?` passes the failure to a caller,
  and a lambda promises none"), so no new typing rule is asked for.
- PROBED: `Result<int, X or Y>` over two type parameters compiles and
  runs (answers `3`), which is what `try_map`'s answer type needs.
- NEW: `Stream`, `TryStream`, the chain verbs over them, `yield`.

### 2.6 The UI loop — DESIGNED for native targets; the web keeps its exports

```avra
// @std/ui, terminal and headless: the loop is the door
export fn mount<V: View>(view: fn() -> V, width: int = 80) {
    let inbox = unbounded_channel<Act>()        // its writers cannot be made to wait
    let ui = app(view, plain, inbox.sink)
    ui.paint()
    for act in inbox.source { ui.turn(act) }    // law 7 as written: a paint follows a turn that ran
}

// an author's handler
on press {
    saving.set(true)
    ui.start(() -> save(draft.get())) { r ->    // a task the app owns; its answer is posted
        saving.set(false)
        saved.set(r)
        true
    }
}
```

- UI_ARCHITECTURE law 7 (READ): "THE LOOP IS ONE DOOR (`App.turn`)…
  whatever may change the state runs through it — a control speaking,
  later a timer or an answer arriving — and a paint follows only when
  it ran." The inbox is how a timer and an answer arrive. `turn` and
  the paint rule are unchanged.
- The inbox is the one `unbounded_channel` in the design: a key press
  cannot be pushed back on. A handler therefore never parks on it.
- ON THE WEB nothing parks: the host calls `host_event` (`web/web.av`,
  as built), which is one `ui.turn`. A task's answer cannot arrive
  there until wasm has tasks (WASM32 step 6 — §5.6).
- Coalescing many turns into one paint per frame would CHANGE law 7.
  It is one arm (`quiet(frame_left)`), offered to the UI lane, not
  decided here.
- NEW: `ui.start` (the owner door fibers §0 plans as `server.spawn
  { }`); nothing else.

## 3. The laws

1. **A stream is a recipe; a source is running.** A `Stream` is a
   value. A `Source` is owned by one block, as a task is.
2. **A running stream ends with the block that owns its sink.**
   `produce(n) { out -> … }` makes that block a task, so "ends" means
   "its work and its tasks are done". A `channel<T>(n)` ends at
   `close()`.
3. **A source's owner leaving stops its producer.** At the owner's
   `}`: sends answer `false`, the producer is cancelled, then joined.
4. **A sink is a handle.** It may be stored, copied, captured, sent.
   It keeps nothing alive. A send after the end answers `false`.
5. **A channel says how much it holds.** `0` hands over. Unbounded is
   `unbounded_channel<T>()`.
6. **Loss is spoken.** A channel that drops counts what it dropped.
7. **A `select` is exhaustive over ends.** An arm taking from a source
   that can end needs that source's `.ended` arm.
8. **Arms take turns.** The scan starts one past the arm taken last.
   `select in order { }` scans as written.
9. **A task answers once.** An arm over a task made outside the loop
   must leave the loop.
10. **A wait that is cancelled fails with `Cancelled`.** The failure
    travels to the scope that asked, which answers it (`within`:
    `TimedOut`). It is never an arm, a parameter, or a `null`.
11. **Cleanup that waits says for how long.** A wait in a `defer` sits
    inside its own `within`.
12. **A failure is the last item.** A `TryStream<T, E>` gives `Err(e)`
    once and ends. Upstream is cancelled. No verb drops it.
13. **No item is left behind.** A consumer that can fail names the
    item's fate: retried, dead-lettered, or dropped by name.
14. **An item is acked when its handler returns `Ok`.** State that must
    survive commits with the ack, or the build says which is lost.
15. **Delivery is discharged per effect.** `exactly_once` is a demand:
    every effect the handler reaches is in the ack's store, or `keyed`,
    or absorbed by a law. Otherwise the build refuses, and under
    `at_least_once` `explain` names each effect that can repeat.
16. **The sender mints the id.** A retried sender sends one item.
17. **A lease has an epoch.** A handler past its lease is a zombie; a
    store write carrying a stale epoch is rejected.
18. **Order is a term.** A fold over `.any` order needs a
    commutativity law.
19. **A law says how it is known.** `proven`, `checked (n)`, `trusted`
    (an extern's promise), `open`. The word is printed wherever the
    law licensed something. `open` licenses nothing.
20. **`fold` is left; `reduce` is the tree.** Neither changes meaning
    with its placement. Floats are never reassociated by a law.
21. **A value crossing a process is plain data.** No identity inside
    it. Its shape may grow; it may not move.
22. **A wait on another machine says how long.** A remote home needs
    the contract's `patience`.
23. **Collecting a stream names its bound.** `.list(max: n)` fails
    with `TooMany` at `n + 1`.
24. **A durable scope resumes at a checkpoint.** Between checkpoints
    every effect is `keyed` by (scope, turn, step), so running the
    turn again does nothing twice.

### Attacks

| attack | what happens | where |
|---|---|---|
| slow consumer | the buffer fills, the sender parks; a lossy channel counts | laws 5, 6 |
| consumer leaves early | at its `}`: `send` answers `false`, the producer is cancelled and joined | law 3 |
| producer forgets to close | `produce`: nothing to forget. `channel`: `flow.never_ends` when the readers are tasks of the same block; otherwise a hang, visible in `avra tasks` | §5.3 |
| a writer parked for ever on something else | its source never ends and its readers wait. NOT DETECTED: the deadlock trap needs every timer and descriptor idle (READ `runtime/avra_fiber.c:587`), which a server never is. `avra tasks` shows the chain | §5.3 |
| a sink stored in a field, a list, a closure, or sent on a channel | a handle; owns nothing (law 4) | §5.3 |
| a source returned from the block that made it | ownership moves to the receiving binding; if nothing receives it, it is settled at the `}` and the handle reads as ended | §5.3 |
| a writer in another process dies | the home between processes is a pipe: the kernel closes it, the source ends with `.Crashed` | §6.3 |
| `select` that starves an arm | a ready arm is passed over at most `arms − 1` times | law 8 |
| a task arm in a loop | refused unless the arm leaves the loop | law 9 |
| a timer in an arm restarts every turn | `after` in an arm inside a loop is refused; `quiet` is the name for that | §5.2 |
| rendezvous: two `select`s, one offering, one taking | the second to arrive claims the first's wait; exactly one side commits | §5.1 |
| a send arm loses to a timer after its value was taken | cannot: a claim is the commit; a claimed offer's arm is the one that fires | §5.1 |
| deadline passes while parked on `next()` | the wait fails `Cancelled`; the `within` answers `TimedOut` | law 10 |
| cancel lands after an arm took an item | at most once: the item is gone, as in any crash. A `Delivery`: unacked, so redelivered | laws 10, 14 |
| a `defer` waits during a cancel | refused outside its own `within` | law 11 |
| duplicate delivery | permitted only where declared; each repeating effect named by `explain`; found by `--faults` | law 15 |
| last-writer-wins `step(s, x) = x` under redelivery | the absorption law (§7.3) fails at `x, y, x`; plain idempotence is not accepted | law 15 |
| slow worker past its lease | redelivered with epoch + 1; the first worker's store write is rejected; its external effect, if not keyed, repeats and is named | law 17 |
| crash between effect and ack | the effect is in the ack's store (atomic), or keyed (absorbed), or it repeats and was named | law 15 |
| retried sender | the same id; the home keeps one | law 16 |
| dual write: a row, then a send | `flow.dual_write` unless the send is the transaction's | §7.4 |
| partition | a send parks to its `patience`, then fails `.Unreachable`; a store home commits locally and relays later; a reader parks to its own deadline | §6.4 |

| two chunks fail in a parallel fold | the earliest in input order is the answer; later chunks are cancelled | §9 |
| old-shape items after a deploy | growth crosses; a moved shape is refused at deploy with the count of items it would strand | §6.4 |
| a handler sends to the inbox its own loop drains | provable in one fn: `flow.self_send`. Otherwise the park traps at once (the sender owns the only source). The UI's inbox is unbounded and never parks | §5.3 |
| `keeps: .all` | refused without `retain:`; unbounded keeping is `keeps: .forever` by name | §4 |
| nullable items | refused: the end is `null` | §4 |

## 4. Types and terms

Authors meet seven nouns. `Wake` and `Gate` are for people writing a
new source; `Home` for people writing a provider.

| type | is | made by | rule |
|---|---|---|---|
| `Stream<T>`, `TryStream<T, E>` | a recipe | a fn with `yield`; a chain; `source.stream()` | a value |
| `Source<T>`, `TrySource<T, E>` | a running supply | `produce`, `channel(n).source`, `.buffered(n)`, `watch.changes()`, `signals`, `every(d)` | an owner: a binding or a list in one block; answerable; never a field |
| `Sink<T>` | a running demand | `channel(n).sink`, `produce`'s block | a handle |
| `Task<T>` | one answer | `spawn`, `after`, `quiet`, `x.ended`, `sink.offer(v)` | as built, plus answerable |
| `queue` | a declared stream with a contract | a declaration | module-wide, like a `const` |
| `Delivery<T>` | `item`, `id`, `attempt`, `epoch` | every queue's source | — |

- NAME CLASHES to settle at build (PROBED grep): `@std/http` exports

## 5. Mechanisms: waiting, `select`, ownership, cancel

### 5.1 Waiting — DESIGNED; its cost is UNMEASURED

TODAY (READ `runtime/avra_fiber.c:125-137`): a `Fiber` has one `next`
link (the run queue or one waiter list), one `parked_fd`, one `timer`
slot. A task can wait on one descriptor and one timer. The only way
one task wakes another is a descriptor edge, which is why `Bell` is a
pipe pair (READ(agent) `std-net/src/net.av:919`).

NEEDED: a task registered on several things, woken by exactly one.

- A WAITER is `{ fiber, tag, set }`. A fiber carries four inline and
  an overflow list. Descriptor lists, the timer heap and gates hold
  waiters, where today they hold fibers.
- A wait SET has one field: the tag that claimed it, or none.
- TO WAKE is to CLAIM: the first waker writes its tag into the set and
  readies the fiber. A later waker finds the set claimed and moves on.
  On resume the fiber unlinks every waiter of the set.
- A GATE is a queue of waiters in memory, with a caller's int beside
  each (`avra_wait_gate(g, tag)`); `avra_gate_claim(g)` claims the
  first unclaimed waiter and answers its tag.

This is a rewrite of the scheduler's waiter structures in both engines,
not an addition (the review is right; v1 said "unchanged").

THE COMMIT. One core, cooperative, so a claim is atomic with no lock.

- Buffered channel: a sender that finds a taker waiting claims it and
  puts the value in the buffer. The channel counts `promised` values;
  a fresh taker may take only when `buffer.length > promised`. So the
  claimed taker finds its value, and a third task cannot steal it.
- Rendezvous (`channel<T>(0)`), two selects: whichever arrives second
  finds the other's waiter in the gate and claims it. If the first had
  an `offer`, its tag indexes the value; the claimer takes it; the
  first resumes with its offer arm fired. If the first's timer had
  already claimed its set, the gate claim fails and the second parks.
  There is no state in which a value is taken and its sender's other
  arm runs.

WHAT A WAIT CAN BE ON. `Wake` is library data:

| `Wake` | row | today |
|---|---|---|
| `.Readable(fd)`, `.Writable(fd)` | `avra_wait_fd` | `avra_fiber_park_fd` |
| `.At(ns)` | `avra_wait_until` | the timer heap |
| `.Gate(g)` | `avra_wait_gate` | none |
| `.Exit(pid)` | `avra_wait_exit` | none; a reap is polled. `EVFILT_PROC` on macOS, a pidfd on Linux |
| `.Sig(set)` | `avra_wait_sig` | none; `EVFILT_SIGNAL`, a signalfd |

- A thread's completion (DNS, `std_net.c:487` — READ(agent)) stays a
  pipe byte: a gate is not thread-safe.
- A completion-based host (io_uring, IOCP, the wasm host) does not say
  "readable". Its adapter owns a one-result buffer and a gate: the
  completion fills the buffer and claims. The protocol above holds.
- A row that BLOCKS the core (a file read, `fsync`, sqlite, DNS before
  its thread) is not a wait. Fibers F4's blocking-row offload is
  unbuilt (READ `FIBERS_DESIGN.md:197`). Until it lands, a disk home
  blocks its core for each `fsync`, and §6 says so in its cost column.

COST OWED before slice 1 lands (CLAUDE.md "MEASURE, THEN CHANGE"):
the yield-to-yield switch is 12 ns today (READ fibers §6b) and the
single-descriptor park must keep an inline fast path; a gate
park-and-claim round trip; allocations per `select` turn, which must
be zero by `make census` (arms register with one row call each; no
list of wakes is built; `ready()` then `take()` are two calls so no
`T?` box is made per look).

### 5.2 `select` — DESIGNED

```
select_stmt = "select" ( "in" "order" )? "{" ( arm | BREAK )* "}"
arm         = ( pattern "in" )? expression ( "if" expression )? "->" body
            | "else" "->" body
```

- An arm's expression is evaluated once on entry, in order. Its type
  is `Source<T>`, `TrySource<T, E>` or `Task<T>`; the pattern binds an
  item, a `Result`, or the answer.
- A guard is read on entry; false removes the arm for this turn.
- `else` runs when nothing is ready. A `select` with `else` never
  parks.
- `select` is an expression; arms agree on a type, as a `match`'s do.

LOWERING. No new instruction: a loop, a switch region and row calls.

```
heads → h0 … hn
loop:
    for i in rotation(cursor): if hi.ready() { v = hi.take(); arm i; leave }
    else-arm, if any → run it, leave
    for each live arm: register its wake with tag i
    k = avra_wait_park()        // −1: cancelled → the failure of §5.4
    goto loop
```

A wake means "look again" for descriptor arms; for gate arms the claim
has already decided.

TIMERS. `after(d)` answers a task that a timer completes (no fiber).
In an arm inside a loop it would restart every turn — Go's
`time.After`-in-a-loop mistake. So that spelling is refused
(`flow.fresh_timer`) and the two meanings have two names: bind
`after(d)` before the loop for a deadline; write `quiet(d)` in the arm
for "d in which no arm fired".

MANY SOURCES. `any(sources: List<Source<T>>) -> Source<Pick<T>>`,
`Pick<T> { at: int, item: T }`; `any(tasks: List<Task<T>>)` forgets a
task once it answers. An ended member is skipped; `any` ends when all
have. This is what h2's per-stream answers, std-process's stages and
`Race`'s dials need (canvas §3, §4, §2). It is a library value over
the same rows: registering N wakes is N row calls.

### 5.3 Ownership — DESIGNED

The task law today (READ(agent) `features/task_law.av`; PROBED: a
record field of type `Task<int>` is `type.task_escape`): an owner is a
binding, a nullable binding, a `List<Task<…>>`, or `Tasks`; each is
joined by a `Deferral.Settle` at its scope's exit, so both engines join
at the same instruction.

EXTENDED, by three rules:

1. A `Source` is an owner type. It holds its producer's task, if any.
2. AN OWNER MAY BE ANSWERED. A fn may answer a `Task`, a `Source`, or
   a record of them: the callee's settle for that value is not
   emitted, and the binding that receives it settles it. An answered
   owner that nothing binds is settled at the end of the statement.
   (Today any answer containing a `Task` is refused.)
3. SETTLING A SOURCE is: mark it left (sends answer `false`), cancel
   its producer, join it. Settles run last-bound-first, as `defer`s do,
   so reader tasks spawned after the source are joined before it.

`produce` is then a library fn:

```avra
export fn produce<T>(capacity: int, body: fn(Sink<T>) -> void) -> Source<T> {
    let ch = channel<T>(capacity)
    let work = spawn {
        defer ch.sink.close()
        body(ch.sink)
    }
    ch.source.owning(work)
}
```

`.buffered(n)` on a recipe is `produce(n) { out -> for x in self { if
!out.send(x) { return } } }`.

Every holder, answered:

| holder of a `Sink` | counts? | what happens |
|---|---|---|
| the `produce` block and tasks under it | the block is the owner | the channel ends at the block's end, after its tasks are joined |
| a fn it is passed to, three calls deep, or through a `dyn` | no: a parameter is borrowed | nothing |
| a record field, a `Cell<List<Sink<T>>>` registry, a stored closure | no: a handle | `send` answers `false` after the end; the registry prunes on `false` |
| sent over another channel | no: a handle | the same |
| a task parked for ever elsewhere | — | the channel does not end; not detected |
| another process | the home is a pipe | the kernel closes it |

A bare `channel<T>(n)` has no owning block for its sink, so it ends
only at `close()`. `flow.never_ends` refuses the one shape the
compiler can see: a block that joins tasks reading the channel to its
end while it is open. That check is syntactic: a `spawn` in the block
captures `ch.source` (or passes it to a seat) and no `close()` or
`defer … close()` placed after those spawns precedes the block's end.

### 5.4 Cancel — DESIGNED; the cost is UNMEASURED

Ratified (READ `FIBERS_DESIGN.md:27`, `:119-123`): "Cancellation
arrives only at a pause point, as a failure on the `Result` channel…
so `?`, `defer` and `errdefer` already handle it."

Not ratified, because fibers did not say: how that failure leaves a fn
whose signature has no `Result` (`sleep` answers nothing; `next()`
answers `T?`; `.await` answers `T`).

THIS DESIGN'S ANSWER, which is open question 3:

- `Cancelled` belongs to the TASK, not to any fn's declared error set.
- "May pause" is a fact folded over the call graph (fibers §4 names
  it; F7 builds it for `atomic`). A fn that may pause is lowered with
  one extra answer bit. After each call to such a fn the compiler
  emits the test it emits for `?`: if set, run this frame's `defer`s
  and `errdefer`s and return with the bit set.
- The bit is set at `avra_wait_park` answering −1. It is consumed at
  the scope that asked: `within` turns its own deadline into
  `.Err(TimedOut)`; a `race` drops the loser; a settle joins.
- So no signature changes and no fn is coloured, and the price is a
  branch after every call that may pause, in fns that may pause.

The alternative that follows fibers literally: every waiting verb
answers `Result<T, Cancelled>` and every caller writes `?`. That is a
colour by another name, and it changes `sleep`, `.await` and every
`@std/net` verb.

ALSO DECIDED HERE:

- `within d { body }` answers `Result<T, TimedOut>` (or widens the
  body's error with `or TimedOut`), per fibers §4 ("a scope with a
  deadline (`TimedOut`)" — READ). TODAY it answers as written and a
  park past the deadline fails its own verb (READ `time.av:62-73`);
  `avra_fiber_sleep` and `avra_task_join` ignore the deadline
  (READ(agent) `avra_fiber.c:803`, `:722`). Both stop being true the
  day parks go through `avra_wait_park`.
- A wait inside a `defer` running under a cancel fails at once, unless
  it is inside a `within` written in that `defer`; that scope's
  deadline is its own. A wait in a `defer` with no such scope is
  refused (`flow.unbounded_cleanup`). HTTP's GOAWAY-then-linger is the
  wanting site.
- A cancel that lands after an arm took an item: the item was taken.
  A `Delivery` is unacked and comes back.
- A TRAP STILL ENDS THE PROCESS. `avra_trap` exits 2 (CLAUDE.md; READ
  `avra_fiber.c:587`). Spec 2.3 wants "panics kill tasks, not
  programs" (READ(agent)); fibers §13 chose fail-fast per core. A
  shared refcounted heap cannot be unwound from an arbitrary
  instruction, so v2 makes no claim to contain one. Isolation is a
  process (§8).
- PARTIAL DEADLOCK IS NOT DETECTED. The trap fires only when nothing
  at all can wake. `avra tasks <pid>` prints each parked task's wakes
  and, for a gate, the source it belongs to.

### 5.5 Reentrancy — DESIGNED

A parking `send` inside the loop that is the channel's only reader is
`flow.self_send` when both are in one fn (the source in the `for` or
arm head and the sink in its body are ends of one binding). Through a
call it cannot be seen at build; at run time the park knows the
sender's task owns the source and traps at once, on the first full
send. That is load-dependent, which is why the UI's inbox does not
park at all.

### 5.6 wasm — DEPENDS-ON(WASM32 step 6)

WASM32 (READ): `avra_fiber.c` is excluded from the wasm archive;
"Fibers are step 6 of the epic: on wasm `spawn`/`within`/`Tasks`
become compiler-generated state machines (or asyncify), and the socket
poller is the JS event loop"; a module's exports are "the `export fn`s
its entry file declares".

- So on wasm today: everything that never parks links and runs
  (`post`, `taken`, a channel as a queue drained inside one export
  call). Everything that parks is refused by name, as `spawn` is
  (`tools/wasm-refuses/fiber`).
- v1's "a root loop is a reactor" was step 6's state machine under
  another name. Cut. `select` on wasm arrives with step 6, and this
  design adds nothing to it but the requirement that the wait rows
  have a wasm body then.

## 6. Homes

A HOME is where a stream's items sit between the writer and the
reader. Fibers §8's PLACEMENT is where work runs, with the proof each
placement demands (READ `:265-275`). They are different axes: a
crossing happens when the writer's and the reader's placements differ.

### 6.1 The table

| home | maturity | mechanism | cost | crosses | delivery | fails how |
|---|---|---|---|---|---|---|
| this task | DEPENDS-ON(COLLECTIONS S3) | a fused loop over `Walk` | a loop | anything, borrowed | exact | the body's failure |
| another task | DESIGNED | a ring in a `Cell`, two gates, the rows of §5.1 | a gate park when full or empty; UNMEASURED | anything: a copy of the value or of its handle (fibers §8: "copies cross"); a dying unique value is moved by the store (REUSE D6 — READ :46) | at most once | cancel; `false` |
| another process on this machine | SKETCHED | a pipe or socketpair made BEFORE the fork (fibers §13's group); items encoded | an encode, a pipe write, a decode | plain data | at most once | the kernel's EOF → `.Crashed` |
| a child process | built (std-process), to migrate | kernel pipes parked in the scheduler | a pipe write | octets, framed | at most once | exit status; EPIPE after the reader left is a clean end (process research §4.2 — READ(agent)) |
| a peer | built (std-http), to migrate | a socket; h2 windows | the wire | octets, framed | at most once | the connection's error |
| a store table | SKETCHED | rows in the program's own store; the cursor is a row | a transaction | plain data | at least once; exactly once for writes to the same store | redelivery after the lease |
| a disk log | SKETCHED | append-only file, a cursor file per reader | an `fsync` per batch, which BLOCKS the core until fibers F4's offload | plain data | at least once | a torn tail is cut at the last whole record |

| a device | DEPENDS-ON(BEND §5) | — | — | flat numbers | — | — |

No home delivers exactly once. `exactly_once` is discharged at the
consumer (§7).

### 6.2 What changes with the home, honestly

- A local channel (`channel`, `produce`) is always in this process. It
  cannot be bound elsewhere.
- A `queue` is declared, module-wide, and bound per run. Its source
  always gives `Delivery<T>`, in process too, and its `send` always
  answers `Result`. So moving a queue's home changes no source text.
  Moving from a channel to a queue does: that boundary is real, and it
  is where an item gains an id and a fate.
- CONSUMER text is the same over both: `for`, `select`, chains.

### 6.3 Processes and cores

Fibers §13 as built (READ): "ONE PROCESS PER CORE, SHARING NOTHING";
"Cross-core shared state (`Shared<T>`, atomics) is a later slice"; "A
CORE THAT CRASHES STOPS THE SERVER (fail-fast)… Restart is policy for
a process manager above." BEND §4.5 (READ) is a different thing: a
work-stealing pool of threads with atomic retains, unbuilt, behind
borrow hole H3.

This design follows fibers §13 and adds only pipes:

- A `worker … on: .cores` is a cores group forked at program start,
  before any other task exists (the constraint `avra_fiber_forked`
  enforces today). Each core holds one end of a socketpair made before
  the fork; the queue's items are dealt over them.
- A dead core is the kernel's EOF. The supervisor learns as it does
  today (`avra_cores_heard`).
- No shared-memory ring. v1's is cut: neither cited document has one,
  and a ring gives no EOF.
- Forking a live, multi-task process mid-program (`on .cores { chain
  }`) is NOT designed here. That placement is BEND's.

THE CROSSING PREDICATE. Today (READ(agent) `features/checks.av:1578`;
PROBED by the review: "`type.isolated` … captures `c`, which is
`Cell<int>`") `identity_in` judges a lambda's CAPTURES at an
`isolated` seat. Needed and not built: the same walk over an ITEM
TYPE. It finds identities (a `Cell`, a task, a pointer, a fn value, a
`dyn`). It does not find a descriptor held as an `int` (fibers §13
records that it "fails loud (EBADF)"), and it cannot find authority
that is plain text (a token in a `string`). v1's "a crossing value
carries no authority" claimed more than any check can do, and is cut
as a law.

### 6.4 Other machines — SKETCHED; the decisions a real design owes

DECIDED:

- CAP. A `queue.send` returns `Ok` only when the home has accepted
  the item. Under a partition a remote send parks to the contract's
  `patience`, then fails `.Unreachable`: consistency over
  availability. A producer that must stay available binds the queue to
  a store table in its OWN store (`tx.send` commits locally) and a
  relay worker forwards: available, at least once, later. A reader
  parks; its staleness is its own deadline. No type hides this.
- LEASES. A taken item is leased for `lease`. Its `Delivery.epoch`
  rises on each redelivery. A store home rejects a write carrying a
  stale epoch (AUTONOMOUS_SYSTEMS :171-173 — READ: "work claims with
  leases; monotonically increasing epochs or fencing tokens"). An
  external effect cannot be fenced unless it is `keyed`.
- SHAPE. An item carries its shape's fingerprint and field count. A
  reader takes the slots it knows, in slot order; trailing fields it
  does not know are ignored. So a shape may GROW across a rolling
  deploy and may not be renamed, reordered or shrunk — CLAUDE.md's
  crossing law for `@std/meta`, applied to the wire. A moved shape
  needs a declared `upgrade fn`, or the deploy is refused with the
  count of old items (AUTONOMOUS_SYSTEMS :449 — READ: "Exact hash
  equality is one compatibility mode, not the only one").
- REQUEUE. An unacked item never left its home; its cursor did not
  move. Nothing is "put back", so order is not disturbed.

OWED: the `Home` trait (take a batch with a lease, ack, send with an
id, declare which terms it keeps); the wire format; authentication;
multi-region; the first provider.

### 6.5 Projections — DEPENDS-ON(the `deploy` block; COMPONENT_EXPANSION §11)

`project()` is "designed now, built with its first consumer"
(COMPONENT_EXPANSION §11 — READ(agent)); `deploy` is unbuilt
(COST_MODEL — READ(agent)). When both exist a queue projects its
provider resource, its dead letter, alarms on lag and dead-letter
depth, and its shape. Access rules are NOT derived from "who writes"
(v1 mis-cited AUTHORITY §8, which is about writers of authoritative
state). Nothing more is designed.

## 7. Delivery and effects — DESIGNED in process; remote rides §6.4

### 7.1 The ack

An item is ACKED when the handler (`each:`, or the body of a `for` or
arm that bound the `Delivery`) returns `Ok` or finishes. The ack
advances the reader's cursor in the home. A handler that fails, is
cancelled, or dies leaves the item unacked; it is redelivered after
its lease with `attempt + 1` and `epoch + 1`.

### 7.2 Effect contracts

An effect is a call that reaches a `World` row. It declares what it
promises:

```avra
extern fn charge(keyed id: string, cents: int) -> Result<Receipt, PayError>   // the provider dedupes on id
extern fn smtp_send(m: Email) -> Result<string, SmtpError>                    // promises nothing
```

- `keyed` is a SEAT mark: two calls with equal values there have the
  effect of one and answer alike. It rides `SeatMark` beside `mutable`,
  `settled`, `unshared`, `consumed` (CLAUDE.md "A SEAT'S PROMISES ARE
  ONE CHANNEL"), so it is part of the fn's type.
- On an `extern fn` it is the author's claim about a provider. Its
  status is `trusted`, and every print says so.
- An Avra fn is keyed, DERIVED, when every effect it reaches receives
  that seat's value at a `keyed` seat.
- A fn whose only effects are writes in store `S` is IN `S`.
- `receipted` (an effect whose outcome can be asked for again by id,
  for the "outcome unknown" case) is SKETCHED: it needs a second fn
  and a reconcile step, and AUTHORITY_AND_RECEIPTS is unratified.

### 7.3 Discharge

For each effect a handler reaches, one of:

| the effect is | under redelivery | printed |
|---|---|---|
| in the ack's store, and the handler runs in that store's transaction with the cursor | atomic: both or neither | exactly once |
| `keyed`, fed `delivery.id` or a value derived from it | absorbed by the provider | exactly once (`trusted` for an extern) |
| absorbed by a law | harmless | exactly once (`proven` or `checked`) |
| none of these | repeats | at least once ⚠, naming the effect |

- `delivery: .exactly_once` is a demand: every effect must be in the
  first three rows, or `flow.not_exactly_once`. Spec 29.2 (READ):
  "`exactly_once` — events are delivered exactly once, requires
  idempotent consumers or transactional delivery." This is that
  requirement, checked.
- THE ABSORPTION LAW, for a handler that is a pure step on kept state:

  ```avra
  law seen_stays_seen {
      for s: State
      for x: Item
      for y: Item
      step(step(step(s, x), y), x) == step(step(s, x), y)
  }
  ```

  With `step(step(s, x), x) == step(s, x)` this gives absorption after
  any sequence, by induction: a state where `x` is absorbed stays one
  after any `y`. Plain idempotence is not enough: `step(s, x) = x`
  satisfies it and gets `x, y, x` wrong.
- A PURE FOLD has no effect to repeat, but its state can be lost or
  double-counted. In memory: a crash loses the state while the acks
  stand, so `explain` prints "at most once: the sum is not kept". With
  `kept: "name"` the state and the cursor are one record in the home's
  store: exactly once. v1 admitted §2.3's remote fold as "pure"; that
  was wrong.

### 7.4 Ids and the dual write

- THE SENDER MINTS THE ID (AUTHORITY_AND_RECEIPTS :69 — READ: "Ids
  are minted by the invoker (UUIDv7), validated by the authority").
  `send(v, id: …)`. With no `id:`, inside a handler the id is derived
  from the handler's own delivery id and the send's position, so a
  re-run sends the same ids; outside one it is a fresh UUIDv7 and
  `explain` says a retried caller will send twice.
- A fn that writes store `S` and sends to a queue outside a
  transaction of `S` is `flow.dual_write` (AUTONOMOUS_SYSTEMS :356 —
  READ: "commit business state and the intent to perform an effect
  together"). `tx.send(q, v, id:)` is the fix: if `q`'s home is a
  table in `S`, the item is a row in the same commit; if not, the row
  goes to `S`'s outbox and a relay worker, itself at least once and
  keyed by the id, forwards it.

## 8. Failure and supervision — failure DESIGNED, supervision SKETCHED

- Law 12, for `a.try_map(f).buffered(8).try_map(g).fold(…)` when `g`
  fails: the fold answers `Err`; the consumer's source is settled;
  the task running `a.try_map(f)` is cancelled at its next send and
  runs its `defer`s; what it held unread is dropped (a channel) or
  never acked (a queue).
- A per-item failure that should not end the stream is a value at the
  stage: `.try_map(parse).skipping(bad_lines)` sends each `Err` to a
  sink as a `Dead` and goes on.
- SUPERVISION IS OF PROCESSES AND OF HANDLERS, never of a trapped
  task.
  - A handler FAILING (an `Err`) is retried by `retries`/`backoff`,
    then dead-lettered. The queue outlives the handler: it is
    module-wide.
  - A handler TRAPPING ends its process (§5.4). For a `worker … on:
    .cores` that is one core; the group's supervisor sees the EOF. What
    it does next is the decision fibers §13 left "for a process manager
    above". OWED: whether the cores supervisor restarts a core, with
    `restart: backoff(from, to)` and `give_up: n in d` (the process
    research's vocabulary, READ(agent) §2.2), or stays fail-fast.
  - Links, monitors and hot upgrade are not designed. Erlang has them
    because each process owns its heap; here a process is the unit.
- TRACES. A `Delivery` carries its id, the sender's site and the
  parent trace: three words, always present, because a queue item has
  them anyway. An in-process channel item carries nothing; a task's
  parent links its trace. v1's "compiled out unless read" is cut:
  nearly every program reads a failure's trace.

## 9. Laws and placement — the licence table DESIGNED; the placements DEPEND-ON(BEND)

BEND's ladder (READ §3.2): rung 1 exhaustive, for finite small
domains, says `proven`; rung 2 generated cases says `checked (n
cases)`; rung 3 SMT, "a later slice", says `proven`; else `open` "and
the gate is red". "`proven` is only spoken by rungs 1 and 3."

So `add` over three unbounded `int`s is `checked` today. v1 printed
`(proven)`; that was wrong. (The law is true: PROBED, `add(add(MAX, 1),
-1)` and `add(MAX, add(1, -1))` both answer 9223372036854775807, so
`int` wraps and addition associates.)

| status | may license a change of result shape (a tree, an unordered fold, a skipped dedupe) | what a false law does | how it is caught |
|---|---|---|---|
| `proven` | yes, silently | cannot be false | — |
| `checked (n)` | yes; `explain` marks the site `checked` | the transformed answer differs from the plain one on inputs the cases missed | `avra test` runs every licensed transformation BOTH ways on every input it sees and compares; `--faults` does it under every schedule. A `deploy` may demand `laws: .proven` |
| `trusted` | only what it states (an extern's `keyed`) | the provider does not dedupe; an effect repeats | not by this toolchain |
| `open` | nothing | — | the gate is red |

- `fold(init, f)` is the left fold, in every placement. Without a
  law it stays one lane and `explain` says why.
- `reduce(init, f)` is BEND §4.3's fixed tree (READ: "A REDUCTION TREE
  IS FIXED BY THE DATA LENGTH, never the worker count… floats do not
  reassociate"). It is the same tree on one task. A stream has no
  length, so the tree is over chunks of a constant size written in the
  program. `reduce` on one core and on sixty-four are the same bits;
  `fold` and `reduce` over floats are different answers and different
  words.
- An associativity law lets the compiler run a `fold` as a `reduce`.
  It is never accepted for a float operator: rung 2 refutes it.
- Among parallel chunks that fail, the answer is the failure earliest
  in input order; chunks after it are cancelled.
- LAWS CHOOSE HOMES: a fold with a commutativity law may read `order:
  .any`; a handler with the absorption law may take `at_least_once`
  without a key. Both ride the table above.
- SIMD, GPU kernels, `par`, `on .cores` over a stream: NOT DESIGNED
  HERE. BEND §4–§5 is "assessment + design proposal… Not ratified"
  (READ(agent) header), nothing of it is built (no `law` feature
  exists; PROBED: `let law = 3` runs), and it is blocked on borrow
  hole H3 (BEND §2.4 — READ(agent)). What this design owes that
  campaign is one fact: a chain over a `Stream` is a `Pipeline` whose
  stages are pure or not by `Reach`, in chunks.

### 10.2 `avra test --faults`

The contract's terms are the fault model. For every declared queue
and its consumers, with no test written:

| term | fault injected |
|---|---|
| `delivery: .at_least_once` | each item delivered twice: adjacent, and with others between |
| `lease` | the lease expires mid-handler; a second handler runs beside the first with `epoch + 1` |
| the ack | the consumer is killed at every point between an effect and its ack, then the item redelivered |
| `order: .any`, `.by(k)` | items permuted (across keys only, for `.by`) |
| `overflow` not `.park` | the buffer filled; drops as the policy says |

| a home | unreachable for a window; a send fails `.Unreachable` |
| a writer | ends early; a reader sees the end mid-batch |
| a `checked` law | every licensed transformation run both ways |

ORACLES, also derived:

1. No item left behind: at quiescence every sent id is acked or in a
   dead letter.
2. The declared delivery: under `exactly_once`, each effect model saw
   each id once.
3. Laws: both ways agree.
4. Every `spec` the author wrote passes under every schedule tried.

Schedules are seeded; a failure prints its seed, and is shrunk to the
fewest faults that still fail. BEND's own table promises "the
deterministic scheduler simulates N nodes × G devices in one process

Limits, stated: it explores schedules of the in-process model, so a
provider's real behaviour is covered only as far as its declared
terms; exhaustive exploration is bounded by a budget (`--faults=1000`).

## 11. Durable scopes — SKETCHED

Fibers §8 (READ :283-285): "`durable "name" { }` checkpoints at its
`}` per iteration; a failed child… restarts from the last checkpoint."
That is a checkpoint-and-restart model. v1 put a replay journal on
top of it and cited that line as if it supported one. v2 keeps fibers'
model, because it is the one that survives a deploy.

- A CHECKPOINT is the scope's live variables at the loop's `}`. They
  must be plain data (law 21). It is written to the scope's home with
  the turn number.
- RESUME reads the last checkpoint and runs the turn again from its
  top.
- So every effect in a turn may run twice. Law 24: inside a durable
  turn every `World` reach must be `keyed`, in the scope's store, or a
  take from a home that KEEPS (which is recorded as a cursor, never as
  content). A clock or random read is a step whose answer is written
  to a small step table and read back on the re-run. Anything else is
  `flow.unkeyed_in_durable`.
- The key the runtime feeds a `keyed` effect is (scope name, turn,
  the step's ordinal in the turn). A `select`'s fired arm is a step.
- VERSION SKEW. A new build resumes at a checkpoint, so only the live
  variables' SHAPE must be compatible, and growth is (§6.4). A turn in
  flight is run again by the new code; its recorded steps are matched
  by ordinal and callee; a mismatch discards the turn's records and
  relies on the keys. `avra build --deploy` reads the home and reports
  "3 scopes are mid-turn at fulfil.av:41; this build changes step 2 of
  that turn".

OWED: a lease on the scope's name so two processes cannot both resume
it (the epoch of §6.4); retention of finished scopes; signals and
queries into a parked scope; child scopes and compensation ("committed
work is compensated, never rolled back", AUTHORITY_AND_RECEIPTS :159
— READ); whether a step table entry has a size bound; float bits when
a scope resumes on another architecture.

## 12. Live folds, batches, time, protocols

### 12.1 Live folds — the insert-only half DESIGNED; retraction DEPENDS-ON(relations)

- `s.scan(init, step)` is the running fold: a stream of states. No
  law needed. Over a `Source` with `overflow: .latest` it is what a
  view binds (`stream { }`, §2.7).
- A MAINTAINED view needs changes that can be taken back:

  ```avra
  law sub_undoes_add {
      for a: int
      for b: int
      sub(add(a, b), b) == a
  }

  let owed = orders.changes()
      .group(it.account)
      .live(0, add: it.total, undo: sub)        // Source<Map<Account, int>>, one change per item
  ```

  `changes()` gives `Change<T>`: `.Added(v)`, `.Removed(v)`. With an
  inverse law (`proven` or `checked`, §9's table) a removal is one
  `undo`. With no inverse it re-folds from the kept items, which needs
  `keeps`; with neither it is refused.
- WHAT GIVES `Change<T>`: a queue with `keeps` and tombstones, and a
  relation's watched query. The second is SHARING_MODEL's
  `Relation<T>` ("durable and incremental (the Db)", READ(agent)
  §4.5), unbuilt. The compiler's own query kernel does early cutoff
  over memoised queries at compile time (`query/memo.av`); it is not a
  runtime library and v2 does not claim it can be shipped as one.
  Whether it should become `@std/query` is a decision for the store
  campaign.

### 12.2 Batches and time — batches DESIGNED; event time SKETCHED

- `.batch(n, within: d)` gives lists of up to `n`, flushed after `d`
  with fewer. It is a `select` over the source and `after(d)` bound
  per batch.
- `.at_once(n)` runs up to `n` calls of a waiting stage and gives
  answers in input order; it starts item `k` only while `k − oldest
  unfinished < n`, so at most `n` answers are held and one slow call
  blocks the head. `.at_once(n, order: .any)` gives them as they land.
- `merge(a, b)` is `any([a, b])` over sources. `zip` needs one side
  running: `a.zip(b.buffered(1))`.
- EVENT TIME is not designed. Owed: where an item's time comes from
  (`by: it.at`), a watermark per source, `late:` policy, tumbling and
  sliding windows, and whether a window's close is a retraction
  (§12.1) or a new item.

### 12.3 Protocols — `ask` DESIGNED; sessions NOT DESIGNED

- `svc.ask(q) -> Result<A, AskError>` is a typed request and reply:
  the request carries a reply sink's id and what is left of the
  asker's `within`; the handler runs inside it; expiry answers
  `TimedOut` at the asker and the outcome there is unknown
  (AUTONOMOUS_SYSTEMS — READ: "There is no general exactly-once remote
  call"), which is what the id is for.
- A SESSION TYPE (a channel whose type is a protocol with states and
  choices) needs a value that cannot be used after a step. Avra's
  consumed seats are inferred and "may not enter type identity"
  (REUSE §34 — READ(agent)). Without a typestate the compiler could
  only check a protocol at run time. Not designed, for that reason.

## 17. Open questions for the owner

1. **Arms: `x in source ->` (here) or the spec's `x = source.receive()
   ->`?** Recommend `in`: an arm that cannot lose data, and an end the
   compiler can demand.
2. **May an owner be answered by a fn, and is a producer cancelled at
   its source's owner's `}`?** Both narrow fibers §4b. Recommend yes:
   they are what make "nobody writes close" a mechanism instead of an
   inference. Without them `produce` must be a keyword.
3. **How does `Cancelled` leave a fn with no `Result`?** Recommend the
   task-owned bit placed by the may-pause fact (§5.4): no signature
   changes; one branch after each call that may pause. The literal
   reading of fibers §0 makes every waiting verb answer `Result`.
4. **`Stream` and `Source` as two types?** Recommend two (spec 18.6
   has two). UI_DERIVATIONS writes `Stream<Robot>` for "a source, not
   a container"; under this design a fn answers the recipe and the
   view runs it.
5. **Rotation instead of the spec's non-deterministic arm choice?**
   Recommend rotation.
6. **`|>`.** PLATFORM_MAP §4 Q2 is still open: a send
   (`order |> orders`), an application (spec 28.7), or nothing?
   Recommend nothing for now: chains are methods and a send is `send`.
7. **A trap ends the process.** Spec 2.3 says tasks; the tree says
   process. Recommend keeping the tree's answer and supervising
   processes; confirm, since it bounds §8.
8. **Does a `checked` law license a change of result in a release
   build?** BEND §9 leaves it open. Recommend yes, marked, with
   `laws: .proven` available to a deploy, and both-ways checking in
   every test run.
9. **Coalesced paint.** It changes UI law 7. The UI lead's call.
