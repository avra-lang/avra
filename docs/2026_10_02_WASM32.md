# The wasm32 target

`avra build --target wasm32 <program>` emits a `.wasm` that runs under a
WASI preview1 host (Node's `node:wasi`, and later the browser host the UI
lane builds). The spike that measured the ground is
`2026_09_29_WASM32_SPIKE.md`; this is what landed.

## Spelling and toolchain

The target is `wasm32-unknown-wasi`. `wasm32` and `wasm32-wasi` are the
same request. Debian's `clang --target=wasm32-unknown-wasi` finds its own
crt, libc and compiler-rt builtins; `wasm32-wasip1` does not, because the
packages install builtins under `lib/wasi/`. The pieces:

    apt-get install -y lld-22 wasi-libc libclang-rt-22-dev-wasm32

`node` runs the result. `make wasm-check` skips, spoken, when a piece is
absent — a check that examined nothing is not a check that passed.

## What the target changes

- **The module carries the target.** `avra_llvm_set_module_target` sets the
  triple and data layout before any body is emitted, so pointer width and
  every layout below follow it, and `avra emit`'s text a reader inspects
  names what it was built for.
- **The entry is `__main_argc_argv`**, which wasi-libc's `crt1-command`
  calls. The host's own `main` is unchanged.
- **The host's code-generation shortcuts are skipped**: the hot-leaf
  bitcode (its 64-bit pointer layout contradicts wasm32), the ELF section
  discipline, and `merge-functions` (its COMDATs lower only as
  `SelectionKind::Any` on wasm).
- **A settled static's pointer cell is a 32-bit pair.** `ptrtoint ptr to
  i64` has no wasm data relocation, so cells are `{i32, i32}` little-endian
  on a 32-bit target, and a box's header length is the target's own ABI
  size — never the compiler's `sizeof`.
- **A non-host target reads from its own store.** A held row is the host's
  object code, so a wasm build must re-read what it cannot reuse; the store
  root folds the target in.

## The runtime

`runtime/*.c` compiles for wasm32 except `avra_fiber.c` and
`avra_cores.c`, which the Makefile excludes from
`build/wasm32/libavra_runtime.a` — a fiber switches stacks and a core
forks, and wasm can do neither. A program that does not reach them links
none of them. The POSIX host section (`avra_spawn_*`, `avra_exec_self`) is
compiled out on wasm with stubs that answer 127, and the loader-slide and
allocator instruments return their wasm truth. `__builtin_return_address`
has no wasm implementation, so `AVRA_CALLER()` is NULL there.

Fibers are step 6 of the epic: on wasm `spawn`/`within`/`Tasks` become
compiler-generated state machines (or asyncify), and the socket poller is
the JS event loop. M1 — a synchronous host event that calls the program —
needs none of that.

## The host surface

The whole import surface today is **WASI preview1**, because the runtime's
own libc calls (`write`, `malloc`, `clock_gettime`) cross there. The UI
lane's seam adds one non-WASI import module, `avra:rt`, for the rows that
are ours (`avra_dom_frame`, and later a binary frame), while libc stays on
WASI; the module also exports `avra_event` for the bootstrap to call.

## Proof

`make wasm-check` builds `tools/wasm-fixtures/loop` (a `println` loop over
a list) and `tools/wasm-fixtures/struct` (a struct and a fn call) three
ways — evaluated (`avra run`), native, and wasm32 under Node — and requires
all three stdouts identical.
