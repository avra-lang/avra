# WARM == COLD: a warm check works out exactly what its edit reached

A warm check is right when it answers what a cold check of the same tree answers, and cheap when it
works out only what the edit reached. The tree holds the first half already (`wisp store_fuzz`,
`tools/witness_program_edit.sh`: byte for byte, exit, words, product); this differential holds both,
and holds the second to the question, not to a count.

Two clauses, from the plan wrong-answers wrote:

1. **A warm edit's work equals what the edit reached, never more.**
2. **Every known past fix, taken back as a patch, is caught.**

## The oracle: two cold frontiers

A cold check of the tree before the edit keeps frontier F0; a cold check of the tree after it keeps
F1. A frontier is a record per question: its answer, each whole read with the answer it saw, and each
part read with the part's name and hash. Two cold checks of one tree keep one frontier, read for read
(`wisp determinism`, keeper `determinism`); that is what makes F0 and F1 comparable at all.

**What the edit reached, R**, is every question F1 holds that F0 does not, or whose record differs:
its answer, a whole read's question or the answer it saw, or a part read's question, part name or part
hash. A part read's whole answer is left out — a part read whose part held is proved, never worked out
again. Inputs are left out: an input is read afresh, never worked out.

**What the warm check worked out, W**, is every question a warm check over F0's store worked out,
inputs aside, in one process (work ahead off), so the set is that process's.

**Clause 1 is `W == R`, as sets.** `W ⊆ R` is "never more"; `R ⊆ W` is soundness — a reached
question not worked out again stands on a read that moved. A count could hold while two errors
cancel; the set cannot.

Beside it, as the tree already holds: the warm check's exit, words and findings are the cold check's
of the same tree, byte for byte; and the frontier the warm check keeps is F1.

## The edits

The cost harness's warm edits (`wisp cost edits`, one table) over the cli, a fixed small set every
gate runs, and `store_fuzz`'s model operations over its `packages` fixture.

## Clause 2: the regression corpus is one

`tools/store-fuzz/` holds a patch per store bug, each taking one fix back out of the tree; each known
warm-answer fix joins it as a patch of its own, naming the edit that exposes it. For each patch a
compiler is built from the tree with the patch laid on, and the differential, over that patch's edit,
must refuse. A patch that no longer lays on, or that names no edit catching it, is refused by name:
renewed against the tree, never dropped.

## The instruments

- `avra cache frontier <dir>`: the frontier kept at `dir`, a record a line in place order — question,
  answer, whether an input, then its reads as the record holds them. Read off the store at rest, as
  `avra cache check` reads it.
- `avra check --worked <file>`: the questions this process worked out, one a line, inputs aside.
- `wisp warm_cold`: for each edit, the two cold checks and the warm one, in fresh exports at one
  place, held to clause 1 and to warm == cold; `--patches` runs clause 2.

## Where it runs

In the gate, as a keeper over the fixed edit set — a check nobody runs holds nothing. Clause 2 builds
a compiler per patch (minutes each), so its patches are dealt across the gate's runners as a slice of
their own, every patch on every gate.

## Its cost

Nothing in a shipping run: `--worked` and `cache frontier` are a check's flag and a cache verb, read
only where asked. A gate pays three checks of the cli per edit, and a compiler per patch.
