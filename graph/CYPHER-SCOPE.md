# The query language: scope, gaps, and what "complete" means

Written 2026-10-28. The target is a 4B model that writes queries the engine accepts, so the
language must be the Cypher a model already knows — not a dialect it has to unlearn. This
file is the scope, the gap list, and the order. Each row of the gap list is a slice with a
conformance test; the language is complete when every row is green.

## 1. Scope: the READ surface, over a declared schema

**In scope — the whole read path of Neo4j-5-style Cypher:**

- clauses: `MATCH`, `OPTIONAL MATCH`, `WHERE`, `WITH`, `UNWIND`, `RETURN`,
  `UNION [ALL]`, and read-only `CALL { … }` subqueries
- modifiers: `DISTINCT`, `ORDER BY … [ASC|DESC]`, `SKIP`, `LIMIT`
- patterns: several labels on a node (`:A:B`), alternative types (`:A|B`), variable length
  (`*`, `*2`, `*1..3`), named paths (`p = (…)-[…]->(…)`), `shortestPath`
- predicates: `= <> < > <= >=`, `IS [NOT] NULL`, `IN`, `STARTS WITH`, `ENDS WITH`,
  `CONTAINS`, `AND OR XOR NOT`, pattern predicates, `EXISTS { … }`
- expressions: property access chains, list and map literals, list and pattern
  comprehensions, `CASE` (simple and searched), arithmetic, `[]` indexing and slicing
- aggregation: `count(*)`, `count(x)`, `count(DISTINCT x)`, `sum`, `avg`, `min`, `max`,
  `collect`
- functions over values the model declares: `coalesce`, `size`, `head`, `last`, `tail`,
  `keys`, `properties`, `labels`, `type`, `toString`, `toInteger`, `toFloat`, `toBoolean`,
  `abs`, `round`, `range`, `reverse`, `split`, and the string verbs `@std/text` already has

**Deliberately out, each a written law rather than an omission:**

| not supported | why |
|---|---|
| `CREATE MERGE SET DELETE DETACH REMOVE DROP FOREACH` | "a query only reads; it cannot write the graph" — the product's boundary |
| `CALL <proc>`, `LOAD CSV` | "a query reads the graph, never a file", and a procedure is a second authority |
| dynamic property access `n[expr]` | a property is DECLARED; the engine types every read, so a name is a schema fact, never a variable |
| temporal and locale function libraries | the value model declares its encodings (`iso_date`, `unix_millis`); a temporal type is a separate decision |

A widening never weakens typing: every accepted query still resolves every label and
property against the catalog, and is still held to the plan budget.

## 2. What the engine has today

| piece | state |
|---|---|
| grammar | `MATCH`/`OPTIONAL MATCH`, patterns with `*`, property maps, `WHERE` with `AND OR NOT`, `= <> < > <= >=`, `CONTAINS`, `IS [NOT] NULL`, calls as predicates, `RETURN … AS`, `LIMIT` |
| refuses by name | writes, procedures, `WITH`, `ORDER BY`, `SKIP`, `DISTINCT`, `UNION`, `UNWIND` (`cypher/src/parser.av`, `REFUSALS`) |
| plan IR (`src/query/plan.av`) | `Scan Seed Filter Follow Search Project Expect Resolve Satisfy Holds Count Derive Sum` |
| output shapes | `Rows Status Count Quantity Derived` |
| guards | parser tests, admit tests, as-of tests, predicate tests |

## 3. The gap list, cheapest first

Each row is one slice: grammar rule → compiler to the plan IR → executor → a conformance
test that runs the query against a small world and checks the rows.

| # | feature | needs | why here |
|---|---|---|---|
| 1 | dotted property chains `a.b.c` | desugar in the compiler to `Follow` + `Filter`; no IR change | the most-written non-subset form; a model reaches for it constantly |
| 2 | `ORDER BY`, `SKIP`, `DISTINCT` | `ReadOnlyPlan` gains `order`, `skip`, `distinct`; the executor sorts and cuts | pure output shaping; no new control shape |
| 3 | `WITH … [WHERE] [ORDER BY] [SKIP] [LIMIT]` | a pipeline: the plan becomes stages over a bag of bindings (`WITH` renames, projects, aggregates and cuts) | the one structural change; everything after it is easier |
| 4 | `UNWIND` | a stage that multiplies rows from a list | needs 3 |
| 5 | `CASE`, list/map literals, comprehensionns, indexing | expression grammar + an expression evaluator over declared values | expression surface, no control shape |
| 6 | `count(*)`, `count(DISTINCT x)`, `avg`, `min`, `max` | aggregation forms beside `Count`/`Sum` | needs 3 to aggregate over a stage |
| 7 | `UNION [ALL]` | the plan holds an ordered list of branches with one output shape | needs 3 |
| 8 | alternative types `:A|B`, several labels `:A:B` | pattern compile only | cheap, common in generated questions |
| 9 | named paths, `shortestPath`, `EXISTS { … }`, read-only subqueries | sub-plan references | last: they make the language a superset of our plan IR |

## 4. Training pairs: generated by the compiler, never written by hand

The generator is the gym, extended — it already samples a schema, builds an executable plan
and renders a question from that plan:

```
invented schema  →  sample a plan (typed, over the declared schema)
                 →  execute it on the world          (gold answer + provenance)
                 →  render the question from the plan (already exists, planner/render)
                 →  render the QUERY from the same plan, in the widened language
                 →  keep only pairs where the query re-executes to the same rows
```

Rules for the generator:

- **No hand-written pair** and no fixture text: the schemas are invented, the words come
  from the renderer, and `extract/test_provenance.py` refuses fixture data in any corpus.
- **A pair is kept only if it executes**: the query is run against the world and its rows
  must equal the plan's. A query that does not run is not training data; it is a gap in the
  language, and it says which one.
- **The query is rendered from the plan, not paraphrased**: the plan knows the model, the
  hops, the filter and the projection, so the query is a projection of the plan — the same
  relationship the planner's own `Plan.cypher` already has.
- **Difficulty is shaped by the sampler**: hop count, filter count, aggregation, `WITH`
  depth, and how many sibling relations the question could have meant. That is how the
  corpus covers the decisions the model actually gets wrong.
- **The held-out set is schemas the training schemas never saw**, so the adapter is measured
  on the skill, not on the vocabulary.

## 5. Order of work

1. Rows 1–2 of the gap list, with conformance tests. Small, independent, and they remove
   two of the four dialect habits the model showed.
2. Row 3 (`WITH`). The one structural change; do it with its own test suite before anything
   depends on it.
3. Rows 4–9 in the order given.
4. Re-measure `planner/bench/llm_cypher.py` after each slice: legal count and correct count
   are the two numbers that move.
5. Only when the language rows are green does the pair generator run and the adapter train —
   a model trained against a partial language learns to avoid the parts that are missing.
