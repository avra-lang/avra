How the compiler remembers its work

A compiler answers thousands of small questions — what type is this?, what does this file declare? — and when you edit one line it should only redo the work that line touched. This is the place those answers are kept.

STEP 1One question, one answer

Think of a library card catalogue. Every card has a key (the title) and a reference (where the book sits). The store has exactly the same two halves, and keeping them apart is the whole design.

The first half is the action table: key → a short fingerprint. The second is the content store: fingerprint → the bytes.

STEP 2The key is itself a hash

A key is not the question in plain words. It is a fingerprint of four things, so a change to any one of them is a different question with its own answer.

STEP 3On disk

.avra-cache/obj/ · bin/

Object files and linked binaries stay ordinary files, named by content.

.avra-cache/store/

One store per tree, for every compiler — because an answer says which compiler built it.

STEP 4Writing: frames, and a full stop

Answers are appended to the live segment as frames. The last thing in every frame is a commit marker: the frame's length and a truncated hash of its bytes. A frame is only believed once its marker checks out.

STEP 5A crash, mid-sentence

Kill the compiler while it is writing and the last frame may be short, or complete except for its marker. Either way it is a torn frame, and that segment is read up to — not including — it.

STEP 6Two compilers at once

There is no lock between writers. Each process appends to its own segment, so two runs never contend. A reader, opening the store, merges every segment into one picture.

STEP 7Finding a needle

Scanning a segment for one key would cost as much as the work it saves. So each sealed body carries an index: a 256-way fan-out, then sorted key fingerprints, then offsets. It is built once, when the body is sealed — never re-built when a reader opens it, and never touched by the live tail.

STEP 8Is the answer still true?

An answer is only as good as the inputs it read. So each record carries what it read, and each input has a small revision that moves when it changes. Checking is three rules:

  • push-dirty — when an input changes, everything that read it becomes suspect (ids only; nothing is decoded yet).
  • pull-verify — a suspect answer re-checks itself, root-down, before it is trusted.
  • early cutoff — if a recomputed answer comes out identical, its readers never wake up. Work stops where the change stops mattering.

STEP 9Housekeeping, and going back in time

Left alone, the segments would grow forever. Compaction folds a sealed body plus every live segment into one new, clean body — and while it copies, it decides what is worth keeping.

Three still fail today — and each failure is a named piece of work, not a mystery: no body content yet a flipped byte inside a sealed body has nothing to flip until compaction writes bodies; whole-store miss a rebuild recomputes everything until the per-query code hash lands; no conflict line two different answers for one key is not reported yet.

The shape, in one breath. Content-only keys → two tiers → an append-only live tail with commit markers → a sealed, indexed body → verification by revisions with early cutoff → compaction that collects what is reachable and keeps a window of history. Nothing in it needs a daemon, and every file is a file you can look at by hand.
