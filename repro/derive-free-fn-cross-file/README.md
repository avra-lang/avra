# `@derive`-generated free fns: undefined across files, fine standalone

Filed against the compiler's derive/expand machinery. Minimal, deterministic,
re-run against `avra-docs` at commit `d199ea9` (bootstrap-built with the
DbRow/Kernel/Db changes from this same slice; the bug predates and is
independent of those changes — see `compiler/db.av`'s own doc comment on
`@derive(Unwrap)`, which this package reproduces standalone for the first
time with a committed artifact).

## The claim

`compiler/db.av` says `@derive(Unwrap)` — a helper fn generated per
dense `DbRow` variant — was "attempted and abandoned": correct via
`avra expand` on the file alone, but with "a DIFFERENT SUBSET... resolve
as undefined" once compiled as part of the whole package. No repro was
ever committed for that finding (checked: `git log --all -S"derive(Unwrap)"`
finds only the doc comment itself, never an attempt).

## What this package shows, deterministically, every run

Two derive traits, same shape (one `Directive` per enum variant, same
`quote` mechanics), differing in ONE way:

- `Unwrap` (`src/rows.av`) generates a free-standing top-level fn per
  variant: `fn a_of(r: Row) -> int { ... }`.
- `UnwrapImpl` (`src/rows_impl.av`) generates an `impl` block per
  variant instead — the shape `compiler/rows_derive.av`'s shipped
  `Rows` trait actually uses: `impl RowImpl { fn as_A() -> int { ... } }`.

`src/dense.av` applies `Unwrap` to a 16-variant enum; `src/consumer.av`
(a DIFFERENT file) calls all 16 generated fns. `src/dense_impl.av`
applies `UnwrapImpl` to a 3-variant enum; `src/consumer_impl.av` (a
different file) calls all 3 generated methods.

```
cd /path/to/avra-docs
export LLVM_PREFIX=/opt/homebrew/opt/llvm   # or wherever llvm lives

# standalone: every generated fn/method resolves, both shapes
build/avra expand repro/derive-free-fn-cross-file/src/dense.av | grep -cE '^fn [a-p]_of'
# -> 16 (the 17th `fn .*_of` match is `hand_written_of`, not generated)

build/avra expand repro/derive-free-fn-cross-file/src/dense_impl.av | grep -c '^    fn as_'
# -> 3 (expand's printer also echoes each generated method as a stray
#       top-level `fn as_X()` beneath its `impl` block — a rendering
#       quirk of `expand`, not a resolve failure; `avra check` below is
#       the real signal)

# as part of the package: the FREE-FN shape's 16 generated names are
# ALL undefined; the IMPL shape's 3 generated methods all resolve.
build/avra check repro/derive-free-fn-cross-file 2>&1 | grep -oE "error\[[a-z._]+\]: [^\n]*" | sort | uniq -c
```

Zero errors mention `RowImpl`, `as_A`/`as_B`/`as_C`, or
`consumer_impl.av` — the impl-block shape's cross-file calls all
resolve clean in the same run. `dense.av`'s own hand-written (never
derived) `hand_written_of`, called from `consumer.av`, also resolves
clean — ruling out a general free-fn-across-files problem. The
defect is specific to a FREE-STANDING FN GENERATED BY A DERIVE,
referenced from a file other than the one carrying the annotation.

## What this does NOT reproduce

`compiler/db.av`'s comment describes a DIFFERENT SUBSET failing each
time, correlated with the annotated file's own size — consistent with
a self-referential `expanded()` re-entry serving a smaller view
mid-derive (see that file's doc comment, and `compiler/expand.av`'s
`fn expanded`). This package fails ALL 16 free-fn names, every run,
deterministically — a cruder symptom of a possibly related but not
confirmed-identical mechanism. Worth checking against `expand.av`'s
recursion guard directly before assuming the two are the same defect.

## Why this lives outside `packages/`

It fails `avra check` by design. `packages/` is scanned by `make gate`,
`make idioms`, `make fmt-lossless`, and `seed-check`
(`packages/cli`'s own dependency graph) — a permanently-broken package
inside it would trip one of those. Nothing here is a dependency of
`packages/cli`, and none of the gate commands walk `repro/`.
